# M03-L04：模块、可见性与公共 API 初识

> **本节核心问题：** 一个任务对象应该公开所有字段，还是只公开允许调用者依赖的操作？

## 工程推进：建立模块边界

**从哪里来：** 上一节 M03-L03 已交付「明确缺失语义的查询 API」。

**当前问题：** 上层不能直接修改所有内部字段。

**本节决策：** 通过 pub 方法暴露稳定行为而非表示。

**完成产物：** 最小公共业务接口。**验证证据：** 跨模块直接写私有字段会被拒绝。

**为什么下一节需要它：** M03-L05 将面对「实体和状态定义好后，增删查仍可能失效。」。

## 学习目标

- 用内联 `mod` 按职责组织相关类型和函数，并理解模块形成嵌套路径。
- 判断模块成员默认的私有边界，以及 `pub` 对模块路径和条目的作用。
- 通过公开方法提供可使用的功能，同时把状态字段和辅助方法留作内部实现。
- 阅读私有成员诊断，并从调用方视角检查 API 是否暴露了不必要的表示细节。

## 先修与环境

完成 M03-L03，能用 `Option` 表达查询可能缺失，并区分函数签名和调用行为。本节使用已学过的结构体、方法、枚举和模块，不展开多文件路径、`use` 重命名或 crate 发布流程。

## 场景：为任务领域定义公共 API

任务列表的客户端需要读取状态和执行操作，却不应该随意改写内部存储。模块把实现放进命名空间；`pub` 让指定路径可用，但并不意味着所有内部字段都应公开。

**先预测：** 如果 `Task` 的字段私有，模块外能否直接使用 `task.state`？用公共只读方法能否实现相同的合法查询？

## 核心知识点一：模块为相关定义建立路径

模块把相关定义放进同一命名范围。`mod` 声明一个模块；下例把任务状态和对外操作放在 `task_api` 下面。`client` 是另一个模块，通过从 crate 根开始的路径使用公开接口：

```rust
/// Exposes task operations while keeping the state representation internal.
pub mod task_api {
    enum State {
        Open,
        Closed,
    }

    pub struct Task {
        pub id: u32,
        state: State,
    }

    impl Task {
        /// Creates an open task with the supplied identifier.
        pub fn new(id: u32) -> Self {
            Self {
                id,
                state: State::Open,
            }
        }

        /// Closes the task through the public interface.
        pub fn close(&mut self) {
            self.state = State::Closed;
        }

        /// Reports whether the task is closed.
        pub fn is_closed(&self) -> bool {
            matches!(self.state, State::Closed)
        }

        /// Reopens a task for an internal workflow.
        fn reopen(&mut self) {
            self.state = State::Open;
        }
    }
}

/// Uses only the task API exposed to sibling modules.
mod client {
    fn print_task() {
        let mut task = crate::task_api::Task::new(17);
        println!("{} {}", task.id, task.is_closed());
        task.close();
        println!("{} {}", task.id, task.is_closed());
    }

    /// Runs the client-side example.
    pub fn run() {
        print_task();
    }
}

/// Runs the module API example.
fn main() {
    client::run();
}
```

模块路径像 `crate::task_api::Task` 一样从 crate 根逐层命名。模块与条目默认私有；若外部模块要沿路径访问一项内容，路径上需要可见的模块和条目。这里 `task_api`, `Task`, 字段 `id` 和三个调用方法是公开的；`State`, 字段 `state` 与方法 `reopen` 都留在实现内部。

## 核心知识点二：`pub` 选择调用方可依赖的成员

把模块标成 `pub` 不会自动公开模块中的所有成员。类型公开以后，它的方法仍需各自写 `pub` 才能让其他模块调用。反过来，公开的字段允许调用方直接读写该字段；若状态需要维持规则，就让字段私有，通过方法控制变更。

```rust
/// Exposes a small counter API without exposing its stored value.
pub mod counter {
    pub struct Counter {
        value: u16,
    }

    impl Counter {
        /// Creates a counter at the requested starting value.
        pub fn new(value: u16) -> Self {
            Self { value }
        }

        /// Reads the current value.
        pub fn value(&self) -> u16 {
            self.value
        }

        /// Advances the counter by one without exceeding u16::MAX.
        pub fn advance(&mut self) {
            if self.value < u16::MAX {
                self.value += 1;
            }
        }
    }
}

/// Uses the counter without reaching into its representation.
fn main() {
    let mut counter = counter::Counter::new(4);
    counter.advance();
    println!("{}", counter.value());
}
```

使用者能够创建计数器、读取当前值和请求它前进一步，但不能直接把内部 `value` 改成任意数字。公开方法定义可用操作，私有字段保留实现调整空间。`pub` 决定可见性，并不自动保证 API 设计合适；应只公开调用方确实需要的能力。

## 核心知识点三：诊断指出越过边界的访问

同一 crate 的兄弟模块仍需遵守成员可见性。下面的调用无法编译：`reopen` 是私有方法，`client` 不能调用它。保留状态边界的调用者应使用已公开的方法；若产品确实需要重新打开任务，模块作者再按契约增加公开操作。

```rust
/// Exposes a task with one public state transition.
pub mod task_api {
    enum State {
        Open,
        Closed,
    }

    pub struct Task {
        state: State,
    }

    impl Task {
        /// Creates a closed task.
        pub fn new_closed() -> Self {
            Self {
                state: State::Closed,
            }
        }

        /// Reopens a task for an internal workflow only.
        fn reopen(&mut self) {
            self.state = State::Open;
        }
    }
}

/// Attempts an operation unavailable to outside callers.
mod client {
    pub fn reopen_task() {
        let mut task = crate::task_api::Task::new_closed();
        task.reopen();
    }
}

fn main() {
    client::reopen_task();
}
```

编译器应报告 `reopen` 是私有方法。不要通过把 `State` 和所有状态细节都公开来消除诊断；先判断调用方是否应该完成该操作，再决定增加一个符合业务契约的公开方法，或移除非法调用。

## 核心知识点四：设计接口时从使用方式倒推

面对一个候选公开结构，逐项问：调用方要完成什么任务？哪些名字必须出现在调用点？哪些数据仅用于维护内部规则？公开可变字段会不会让调用方构造出不合法状态？从最小可用接口开始，能降低后续调整内部表示时影响调用方的范围。

## 检查顺序

1. 从 `crate::...` 路径逐层检查访问位置所在的模块。
2. 检查路径中的模块、类型、字段和方法是否都对调用方可见。
3. 区分“调用方需要的操作”与“模块内部保存的表示”，不要仅为了消除隐私错误而公开所有成员。
4. 编译一份合法调用和一份刻意非法调用；确认合法版本能使用公开 API，非法版本命中预期的私有成员诊断。

## 与 Java / Go 对比：模块边界与封装

Java 倾向用 package 与可见性修饰符，Go 按标识符首字母大小写决定包外可见性。Rust 通过模块树、路径和 `pub` 定义对外接口。与其为消除 private 诊断直接把每个字段改为 public，不如先考虑调用者是否真的需要访问内部表示。

## 原理推导与反例辨析：建立模块边界

**问题：** 上层不能直接修改所有内部字段。

**原理与推导：** 模块可见性是建立稳定契约的工具：不公开内部字段，允许实现改变而不影响依赖公共行为的调用方。

**示例与证据：** 使用本节原有代码或实验验证：跨模块直接写私有字段会被拒绝。

**反例：** 把所有字段声明为 pub，即使业务入口仍正确，其他模块也可能绕开校验直接写入非法状态。

**独立练习：** 把一个类型的字段改为私有，只暴露构造和受控修改方法；尝试在外部模块直接修改字段并观察编译失败。

**复盘：** 复盘时区分“防止外部越权访问”和“自动验证所有业务规则”。

## 检验理解与本地练习

**预测 → 验证：** 在示例调用模块中直接读私有字段，记录编译器诊断；再改为通过公开方法访问，确认外部只依赖稳定 API。为修改操作补一个测试，避免只检查“代码能编译”。

**验收标准：** 能解释模块路径、条目可见性与内部表示三者的区别，公共 API 只暴露必要能力。

## 实践迁移：不让公共 API 暴露内部表示

**先预测：** 调用方需要“把提醒标记为已读”，但直接公开 `status` 和 `attempts` 字段会导致什么隐患？

**动手改造：** 将字段保留为私有，只公开读取状态、申请状态转换的最小方法；保持原有模块路径的可见性规则。

**反例与边界：** 从另一模块故意访问私有字段，保留拒绝诊断；不要为修好测试无差别加 `pub`。

**验收证据：** 展示内部可修改字段的实现与外部只能通过稳定接口访问的用例。

## 本节小结

- 从业务需求定义字段与状态，而不是先暴露一堆可随意修改的值。
- 用类型、匹配与方法签名标出合法操作和不允许的路径。
- 编译检查发现结构问题，行为测试验证业务承诺；两者都不可省略。
