# M03-L02：枚举与 `match`

> **本节核心问题：** 任务只能处于一个状态时，如何让编译器帮你发现漏处理的状态？


## 原理深化与独立练习

多个布尔标志可能产生无效组合：running=true 与 finished=true 同时出现。枚举把可表达状态限定为 Queued、Running、Finished；match 的穷尽性让新增状态主动触发检查，而不是静默沿用旧默认分支。

**进阶练习：** 给任务状态添加 Cancelled，先观察未覆盖的 match 如何报错，再决定其是否允许重试。分别断言允许和拒绝的状态；最后加入 _ 通配分支，说明它为何可能掩盖未来新增状态的业务决策。

**从哪里来：** 上一节 M03-L01 已交付「带不变量的领域结构体」。

**当前问题：** 单靠布尔字段无法表达互斥任务阶段。

**完成产物：** 类型安全的任务状态。**验证证据：** 新增状态会要求显式审核分支。

## 把非法状态从业务判断里移到类型定义中

一条异步任务可以排队、运行或结束。如果用字符串表示状态，`"runnning"` 这样的拼写错误可能直到某个运行分支才暴露；如果用数个布尔量表示，甚至可能出现“既排队又已完成”。

枚举不是为了少写几行 `if`，而是在数据建模时就排除不可能的组合。`match` 的穷尽性检查让新增状态变成明确的编译期提醒，而不是让某个旧分支悄悄漏掉处理。真正重要的是先讲清状态间的互斥与转移规则。

想象将来增加 `Cancelled`：哪些地方应该拒绝取消？哪些日志要记录？当枚举迫使你回到这些问题时，它就是在帮助维护业务，而不仅仅是换一种语法。

## 学习目标

- 用枚举表达一个值只能属于若干明确状态之一。
- 定义无数据变体和携带数据的变体，并通过 `Enum::Variant` 构造它们。
- 用 `match` 按变体分支处理值，绑定变体携带的数据。
- 识别穷尽性错误；新增变体时检查所有相关 `match` 是否仍覆盖完整。

完成 M03-L01，能定义命名数据结构、调用方法，并阅读方法与字段的类型诊断。本节延续“一个值有一种明确类型”的模型，不展开泛型枚举、Option 或错误传播。

## 场景：任务从 Queued 进入 Running 或 Finished

不应同时用多个布尔值表示互斥状态：`is_running = true` 与 `is_finished = true` 可能出现矛盾。一个枚举值在同一时刻只能属于一个变体；携带失败次数等数据时，变体自身也能表达附加信息。

**先预测：** 给 `TaskState` 新增 `Cancelled` 后，原本没有 `_` 兜底的 `match` 是否需要新增处理？

## 用枚举表达互斥状态

结构体把同时存在的一组字段组合起来；枚举则表达一个值在若干互斥选项中恰好取其一。变体归属于枚举类型，并通过双冒号构造：

**阅读代码前先预测：** 这段枚举声明的价值不是少写几个布尔量，而是限制一个任务同一时刻只能处在一种状态。观察变体是否携带额外信息，以及这些数据属于哪个变体。

```rust
/// Represents the mutually exclusive states of a scheduled task.
enum TaskState {
    Queued,
    Running,
    Finished,
    Failed { attempts: u8 },
}

/// Returns a short action label for a task state.
fn action_for(state: TaskState) -> &'static str {
    match state {
        TaskState::Queued => "start",
        TaskState::Running => "wait",
        TaskState::Finished => "none",
        TaskState::Failed { attempts } => {
            if attempts < 3 {
                "retry"
            } else {
                "inspect"
            }
        }
    }
}

/// Prints one action for each kind of task state.
fn main() {
    println!("{}", action_for(TaskState::Queued));
    println!("{}", action_for(TaskState::Failed { attempts: 2 }));
}
```


**运行或编译后观察：** 加入新的 `Cancelled` 状态后，让 `match` 的全部处理点重新编译。编译器能提示漏分支，但实际允许哪些状态迁移仍要靠业务测试定义。
前三个变体不携带额外数据；`Failed` 变体有一个命名字段 `attempts`。同一变量不能同时是 `Queued` 和 `Running`；编译器会把每个变体都视为 `TaskState` 类型的不同形态。调用点写 `TaskState::Failed { attempts: 2 }`，而不是把状态名称和数字分开传递，因而两者始终绑定在一起。

## `match` 逐个处理变体

`match` 是表达式。每个 arm 的模式指出它负责的输入，箭头后的表达式给出该分支的结果；所有 arm 的结果须兼容函数声明的返回类型。上例通过 `TaskState::Failed { attempts }` 取出变体数据，再按计数决定动作。

对状态这类每个变体都需要不同动作的类型，逐一列出变体能让代码意图清楚。若漏掉 `Finished`，编译器会报告 `match` 不穷尽，而不是悄悄选择错误的默认动作。用 `_` 可以接收其余所有形态，但它也会接住以后新增的变体，可能令匹配仍能编译、却没有为新状态设计专属行为。

```rust
/// Represents the possible delivery states.
enum DeliveryState {
    Waiting,
    Sent,
    Failed,
}

/// Reports whether a delivery has reached a terminal state.
fn is_terminal(state: DeliveryState) -> bool {
    match state {
        DeliveryState::Waiting => false,
        DeliveryState::Sent => true,
        DeliveryState::Failed => true,
    }
}

/// Prints whether the delivery is terminal.
fn main() {
    println!("{}", is_terminal(DeliveryState::Sent));
}
```

把匹配补全为新枚举变体时，要确认每个 arm 的结果类型一致；本函数所有分支都返回 `bool`。如果其中一个分支返回字符串而其他分支返回布尔值，编译器会报告不匹配。

## 区分“已列全”与“剩余默认处理”

`_` 是通配模式，表示没被前面 arm 匹配到的任何值；它不创建变量，也不检查剩余值属于哪个状态。它适用于有意共享处理方式的输入。例如仅判断“是否需要停止”时，可以让若干状态落入同一结果；若每个状态未来可能有不同业务行为，显式列出当前所有变体会保留编译器对新增状态的检查。

阅读诊断时先把 `match` 里的已列模式和枚举定义中的变体一一对应，再找遗漏项。不要靠增加 `_ => false` 来掩盖真正应该处理的新状态；也不要删除状态变体来让匹配通过。

## 检查顺序

1. 找出枚举定义声明的所有变体。
2. 检查每个值通过正确的 `Enum::Variant` 构造；带数据的变体是否提供了规定字段。
3. 检查 `match` 模式覆盖每一种相关形态，绑定的数据类型与后续操作一致。
4. 比较各 arm 的结果类型；运行 `cargo check` 后再用行为测试覆盖每个变体和数据边界。

## 与 Java / Go 对比：枚举与穷尽性

Java 的 enum 可以定义封闭选项，Go 常用具名常量模拟状态；Rust 的枚举还能让不同变体各自携带不同类型的数据。`match` 的穷尽性检查在新增变体时强迫相关调用点重新考虑逻辑。

**注意：** 使用 `_` 兜底能让匹配完整，却可能掩盖后来新增状态的业务决策。适合的策略取决于是否希望新状态显式触发代码审查。

## 原理推导与反例辨析：枚举生命周期

单靠布尔字段无法表达互斥任务阶段。 枚举用互斥变体描述状态集合，`match` 的穷尽性让新增变体成为需要审核的设计变更。

用数个布尔值分别记录 `queued`、`running` 与 `finished`，可能产生三者同时为真的无效组合。枚举把这些状态约束为一个互斥选择，`match` 又要求调用方讨论每一种合法情况。

两个布尔状态可能出现同时运行且完成的矛盾组合；粗暴使用 `_` 则可能在后续扩展时吞掉新状态。 添加一个 `Cancelled` 变体并重新编译调用代码，观察未覆盖的 `match` 分支是否收到诊断。然后用业务断言保证合法转换；穷尽匹配不能替你证明从 `Finished` 转回 `Queued` 一定符合需求。

要把这一结论落到可验证的行为上，添加 Cancelled 状态，先预测编译诊断，再为每种状态指定动作并写完整断言；说明为何选择列出明确变体。 复盘应证明非法状态不能被构造，而不是只证明分支语法正确。

## 检验理解与本地练习

**预测 → 验证：** 给 `TaskState` 增加一个变体，先尝试不更新 `match`，观察编译诊断。再补全分支，并针对失败次数不同的情况写行为测试。

**验收标准：** 能解释状态为什么互斥，指出哪个分支读取了变体携带的数据，并说出 `_` 的收益与风险。

## 实践迁移：加入新状态后的穷尽性

**先预测：** 任务从 Queued / Running / Finished 增加 Cancelled 时，原有 `match` 应自动得到一个有意义的默认分支吗？

**动手改造：** 为状态机添加明确的新变体，并逐个检查状态展示与可执行动作的 `match` 分支。

**反例与边界：** 构造带数据的变体，确认字段被正确读取；不要用 `_` 隐藏需要业务审核的新状态。

**验收证据：** 保留新增变体前的穷尽性诊断，更新所有公开状态的行为断言。
