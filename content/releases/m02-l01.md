## 一次重试计数为何需要先想清数据类型

接口偶尔超时后，开发者给请求处理器加了一个重试计数器。熟悉 Java 的人可能顺手写出可变变量，却发现 Rust 默认不允许重新赋值。这个限制不是要求你把所有数据都写死，而是让每个变化显式出现：哪些值是一开始决定的配置，哪些值确实要随着循环改变？

`let` 绑定默认不可变，`let mut` 表示允许改动；类型推断解决的是“当前表达式是什么类型”，并不能总是推断出最终业务需要多少位整数。尤其是读取外部数字时，提前确定 `u8`、`u32` 或 `u64` 的范围，比等到溢出后再补类型转换更安全。

当计数器的范围、初始值和增长时机都说得清楚时，变量声明其实已经成为业务约束的一部分。

## 场景：统计重试次数与解析请求参数

你在重写一个后端请求处理流程：重试次数从 3 增加到 4，而收到的字符串参数 `"42"` 需要转换为 `u32`。第一个问题是**绑定是否会重新赋值**，第二个问题是**数值的目标类型是什么**。先不要给所有变量加 `mut`，也不要把所有整数改成 `i64`。

**阅读路径：** 预测是否编译 → 判断类型由何处确定 → 找出是否需要显式转换 → 在本地复验。

## 变量绑定默认不可重新赋值

`let` 把一个值绑定到名字。默认绑定不可再次赋值：

```rust
/// Prints a value from an immutable binding.
fn main() {
    let attempts = 3;
    println!("attempts = {attempts}");
}
```

若程序确实要更新同一个绑定，写出 `mut`：

```rust
/// Shows a binding that is intentionally updated.
fn main() {
    let mut attempts = 3;
    attempts += 1;
    println!("attempts = {attempts}");
}
```

可变性属于绑定，不代表所有值都必须声明为可变。先看后续代码是否要给这个名字重新赋值；若没有，保留不可变绑定可以让意图更清楚。将第一段中的 `attempts` 再赋值会得到编译错误；仅在打印前声明 `mut` 不会改变输出，只会放宽该绑定可被重新赋值的规则。

## 从上下文推断类型，必要时明确标注

Rust 在编译时需要知道值的类型。类型能从字面量和使用上下文确定时，可以省略标注：

```rust
/// Demonstrates type inference for scalar values.
fn main() {
    let retries = 3; // 整数默认类型是 i32。
    let ratio = 0.75; // 浮点数默认类型是 f64。
    let enabled = true;
    let marker = 'R';
    println!("{retries}, {ratio}, {enabled}, {marker}");
}
```

当需求需要限制范围或接口需要固定类型时，显式写出类型：

```rust
/// Demonstrates explicit annotations for scalar values.
fn main() {
    let port: u16 = 8080;
    let temperature_c: i16 = -5;
    let sample_rate: f32 = 0.5;
    println!("{port}, {temperature_c}, {sample_rate}");
}
```

整数类型的有无符号和位宽会影响可表示范围，例如 `u8` 是 0 到 255，`i16` 可以表示负值。不要只按“数字大小”挑类型：先看值域、接口要求和后续运算。浮点数有 `f32` 与 `f64`；本课不讨论精度策略。

推断不是猜业务意图。如果字面量存在合适的默认类型，编译器通常可以选定它；若泛型调用等上下文仍允许多个类型，编译器会要求补充信息。类型标注就是程序员为编译器补足约束：

```rust
/// Demonstrates an explicit, lossless integer conversion.
fn main() {
    let parsed: u32 = "42".parse().expect("示例输入是有效的 u32");
    println!("{parsed}");
}
```

此例把输入固定为 `u32`，因此 `parse` 的目标类型明确。生产代码如何处理解析失败会在错误处理单元讨论；这里的 `expect` 仅用于已知有效的教学字面量。

## 不同整数类型不能隐式互换

`u8` 和 `i64` 是不同类型。Rust 不会因为当前数值可以装进目标类型，就悄悄转换：

```rust
/// Demonstrates a parse operation with a known-valid teaching literal.
fn main() {
    let discount_percent: u8 = 10;
    let displayed_percent: i64 = i64::from(discount_percent);
    println!("{displayed_percent}");
}
```

若直接把 `discount_percent` 赋给 `i64`，会得到类型不匹配错误。用 `From` 明确表达这个无损转换；转换是否合法应由类型和契约共同决定，不能仅凭某个测试值推断。

## 与 Java / Go 对比：变不变、转不转

| 任务 | Java / Go 常见思路 | Rust 要关注的约束 |
| --- | --- | --- |
| 重新给变量赋值 | 根据声明和作用域使用变量 | `let` 默认不可重新赋值，必要时加 `mut` |
| 将文本变成数字 | `parseInt`、`strconv.ParseUint` 等 | `parse` 需要可确定的目标类型，失败必须被处理 |
| 整数类型间传值 | 依语言规则做转换或强制转换 | `u8` 与 `i64` 不自动互换，显式转换表达意图 |

不要混淆“绑定是否能重新赋值”和“值是否被拥有/借用”：所有权会在 M04 单独学习。


## 原理推导与反例辨析：定义数值契约

**问题：** CLI 的数值输入需要稳定类型和可变状态。

**原理与推导：** Rust 的 `let` 默认不允许重新赋值，但允许遮蔽重新绑定；类型推断依赖上下文，整数的不同位宽不会自动互换。

**示例与证据：** 对照本节现有代码或实验，核验：零值、u8 上界与非法混合运算可验证。

**反例：** 把 `mut` 当成 Java/Go 的万能变量声明，或以为 `u16` 能直接赋给 `u32`，会误判绑定和类型边界。

**独立练习：** 写出只读、可变更新和 shadowing 三种计数器，预测每种绑定的类型与输出；增加显式数值转换并解释何处可能溢出。

**复盘：** 分别用一行话说明“变量可变”和“值的类型”是两条不同的设计约束。

## 原理实证与迁移练习

显式把 u8 转为 u16 后，255 递增可得到 256；输入 255 合法，256 超出 u8 范围，abc 不是数字。shadowing 产生新绑定，不等于 mut。另用预期编译失败的 m02_immutable_binding.rs 复现 E0384，修复时只为真正需要重赋值的绑定添加 mut。

## 检验理解与检查流程

先预测每个绑定能否再次赋值，再运行 `cargo check` 看类型和可变性诊断；若程序可编译，再运行它确认值。检查问题时，分别问：这个名字是否要重新绑定？值的目标类型是什么？上下文是否足以唯一确定类型？避免一次性给所有变量加 `mut` 或随意扩大整数类型来掩盖根因。

**先预测再执行：** 将 `let attempts = 3;` 后面接上 `attempts += 1;`，会发生编译错误还是输出 4？为什么？再把 `let port: u16 = 8080;` 换成超出 `u16` 范围的值，观察类型边界诊断。

**验收标准：** 可以区分绑定可变性与整数值域，并能说明 `"42".parse()` 为什么有时需要 `::<u32>` 或明确的变量类型。


## 实践迁移：配置计数器的类型契约

**先预测：** 请求重试次数来自 `u8` 字段，累计值却是 `u32`。把二者直接相加会隐式扩大类型吗？

**动手改造：** 写一个最小配置计数器，让 `let` 与 `let mut` 的职责可见，再用明确转换连接两种整数类型。

**反例与边界：** 测试零、最大 `u8`，并观察故意去掉转换后的编译诊断；不要把类型问题改成 `as` 任意截断。

**验收证据：** 给出变量的实际类型、能/不能重新赋值的例子，以及检查结果。

## 本节小结

- 先看是否需要重新赋值，再决定是否添加 `mut`。
- 类型推断依赖约束，不能替开发者猜测业务接口意图。
- 数值转换需遵守目标类型和值域，不能只凭某个样例恰好能表示就忽略契约。
