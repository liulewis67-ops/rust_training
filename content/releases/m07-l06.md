# M07-L06 检查：为运行时策略流水线选择分发方式

> **模块毕业任务：** 一个发布策略列表需要运行时混合不同实现、按顺序评估，并保留第一项拒绝理由。怎样兼顾泛型接口与 trait object？

## 工程推进：执行策略链

**从哪里来：** 上一节 M07-L05 已交付「可替换的配置解析器」。

**当前问题：** 多个策略必须按运行时顺序执行并短路。

**本节决策：** 以 dyn Trait 组合 Gate 并返回首个拒绝。

**完成产物：** 顺序稳定的策略流水线。**验证证据：** 交换 Gate 次序改变首个错误。

**为什么下一节需要它：** M08-L01 将面对「策略执行产生多条事件，既要索引也要有序展示。」。

## 学习目标与先修

完成 M07-L01–L05 后，独立选择 `T: Trait` 与 `dyn Trait` 的 API 形状，判断运行时异构集合、短路错误传播和 dyn compatibility 的限制。

## 场景：发布流水线中的可插拔 Gate

管理员可以在运行时为不同项目排列多个发布门禁。单个具体策略用泛型调用很自然；但一个 `Vec` 要混装 `MinimumNumber`、`ChannelIs` 和未来新增的实现，需要运行时可统一调用的 trait object。

**先预测：** 当 `gates` 为空时程序应返回什么？若第一项拒绝，后续的 gate 是否还应该执行？

## 独立任务

团队要检查构建工件是否满足发布条件。单个静态调用可以由具体策略类型决定；新需求改为：管理员在运行时组合不同策略，列表可以存放未来新增的策略类型；按配置顺序检查，第一项拒绝后立即返回其原因；空策略列表表示没有额外限制。

在下面的 API 中实现 `evaluate_pipeline`，让异构 `Gate` 实现通过 trait object 保存在同一列表中。不要用 enum 把已知实现类型写死，也不要为这个列表再引入一个仅转发调用的 wrapper 类型。保留 `evaluate_one<G: Gate>` 作为单一具体类型的泛型对照。

```rust
/// Describes one release condition over a build record.
trait Gate {
    /// Accepts the build or explains why this gate rejects it.
    fn evaluate(&self, build: &Build) -> Result<(), String>;
}

/// Holds metadata checked by release gates.
struct Build {
    number: u32,
    channel: String,
}

/// Requires a minimum build number.
struct MinimumNumber(u32);

/// Requires a specific release channel.
struct ChannelIs(String);

/// Checks one concrete gate through static dispatch.
fn evaluate_one<G: Gate>(gate: &G, build: &Build) -> Result<(), String> {
    gate.evaluate(build)
}

/// Checks a configured heterogeneous gate pipeline.
fn evaluate_pipeline(gates: &[Box<dyn Gate>], build: &Build) -> Result<(), String> {

    Ok(())
}
```

为 `MinimumNumber` 与 `ChannelIs` 实现 `Gate`。在答案说明中交代为什么单个 `G` 适用于一个具体类型，而 `Box<dyn Gate>` 支持混合类型的运行时策略列表；再指出 trait 为何可用作 dyn，以及添加泛型方法或原生 async 方法会怎样影响 dyn compatibility。说明动态分发提供的灵活性和间接调用代价，不作未测量的总体性能结论。

## 原理推导与反例辨析：执行策略链

**问题：** 多个策略必须按运行时顺序执行并短路。

**原理与推导：** 运行时策略链用有顺序的 trait object 列表组合多种 gate；短路意味着第一个拒绝结果决定后续是否继续执行。

**示例与证据：** 对照本节原有代码或实验核验：交换 Gate 次序改变首个错误。

**反例：** 把策略顺序交给无序集合，或在一次拒绝后继续执行产生副作用的 gate，会违反链式验证的契约。

**独立练习：** 配置三个可记录调用的 Gate，验证全部通过、第一道拒绝和中间拒绝三类情况的调用序列。

**复盘：** 复盘要明确为什么需要动态分发、固定顺序和短路，而不是将三者混为同一个概念。

## 分阶段验收

1. 为两个具体策略实现 `Gate`，每一项都返回明确的通过或拒绝原因。
2. 保留 `evaluate_one<G: Gate>` 的单类型泛型版本，确认泛型调用能工作。
3. 在 `Vec<Box<dyn Gate>>` 放入不同具体类型，严格按配置顺序遍历。
4. 首个 `Err` 原样返回；全部通过或空列表时返回 `Ok(())`。
5. 检查 `Gate` 的方法为何满足 dyn compatibility；如果加入原生 `async fn` 或泛型方法，必须重新审查接口。
6. 记录动态分发的间接调用代价，但不臆测整个系统的实际吞吐差异。

**与 Java/Go 对比：** Java/Go 的接口集合通常支持不同实现的统一持有；Rust 显式区分编译期的泛型实例与运行时的 trait object。两者可以在同一系统共存，并非某一方始终更优。

## 公开行为契约

- 单条策略可以使用 `evaluate_one`，成功和拒绝原因符合策略自身条件。
- `MinimumNumber` 与 `ChannelIs` 可同时存放在 `Vec<Box<dyn Gate>>`，按列表顺序检查。
- 首个失败原因原样返回，不继续覆盖它；全部通过时返回 `Ok(())`。
- 空切片不增加限制，返回成功。

## 检验理解

**先预测后验证：** 把拒绝 channel 的 gate 放在拒绝 build number 的 gate 前面，与交换顺序相比，最终错误文本有何变化？为什么不能把两个错误汇总后再返回，否则就违反“第一项拒绝立即退出”的合同？

## 自查要点

确认管线逐项调用每个 gate，首个错误原样返回；单个具体 gate 仍可通过泛型 `evaluate_one` 检查。不要将不同策略硬编码成闭合类型集合，也不要把 `dyn` 当作没有间接调用成本的静态分发。

## 分层提示

1. **定位提示**：`gates` 的元素类型已经是 `Box<dyn Gate>`，循环可直接调用 trait 方法。
2. **控制流提示**：`Result` 的 `?` 可在首个 `Err` 时返回，空循环自然返回最终 `Ok(())`。
3. **设计提示**：泛型和 trait object 可以同时存在于一套 API 中，各自服务于不同类型选择时机。
4. **参考方案**：逐项执行 `gate.evaluate(build)?`，循环正常结束后返回 `Ok(())`；核对错误值没有被改写。

## 自查清单

- [ ] 泛型单策略与 dyn 异构策略集合都可以正常评估。
- [ ] 列表顺序决定首个错误，任何错误不会被覆盖或吞掉。
- [ ] 空策略列表返回 `Ok(())`。
- [ ] 没有用 enum 锁死可扩展的策略类型或加入无价值 wrapper。
- [ ] 能解释 `Gate` 为何可构建 trait object，哪些方法会破坏对象兼容性。

## 实践迁移：配置顺序决定第一个拒绝原因

**先预测：** 发布策略列表中，第一个 Gate 已拒绝，而第二个 Gate 也会拒绝。执行器应该返回哪个错误？

**动手改造：** 使用泛型单策略和动态分发多策略两种入口，先写出期望顺序，再实现首个错误立即返回。

**反例与边界：** 测试空列表、全部通过、调换策略顺序及带不同具体类型的策略；不要通过 enum 封闭可插拔集合。

**验收证据：** 保留每次配置下的返回值和对 dyn compatibility 的解释，证明短路没有被忽略。

## 参考实现

```rust
impl Gate for MinimumNumber {
    fn evaluate(&self, build: &Build) -> Result<(), String> {
        if build.number >= self.0 {
            Ok(())
        } else {
            Err(format!("build {} is below minimum {}", build.number, self.0))
        }
    }
}

impl Gate for ChannelIs {
    fn evaluate(&self, build: &Build) -> Result<(), String> {
        if build.channel == self.0 {
            Ok(())
        } else {
            Err(format!("channel {} does not match {}", build.channel, self.0))
        }
    }
}

fn evaluate_pipeline(gates: &[Box<dyn Gate>], build: &Build) -> Result<(), String> {
    for gate in gates {
        gate.evaluate(build)?;
    }
    Ok(())
}
```

`evaluate_one<G: Gate>` 在每次调用时使用一个确定的具体类型；`Box<dyn Gate>` 则允许同一个列表保存不同实现并在运行时分发。`Gate` 的方法签名固定且不返回 `Self`、没有泛型或原生 async 方法，所以可用作 trait object。循环中的 `?` 保留并立即返回第一项错误；空列表直接得到 `Ok(())`。

自查时构造通过的、首项拒绝的、后续拒绝的和空策略列表；比对精确的首个错误文本。`Box<dyn Gate>` 可用是因为 `Gate::evaluate` 的接收者和返回类型固定，没有要求 trait object 实例化未知的 `Self`。

例如使用 `Build { number: 12, channel: "stable".into() }` 和 `[MinimumNumber(10), ChannelIs("stable")]` 应得到 `Ok(())`；将 `ChannelIs("beta")` 放在 `MinimumNumber(20)` 前面时，应原样返回 channel gate 的错误，即使后一个 gate 也会拒绝。
