# M01-L01 练习：Rust 解决的问题与路线选择

本节为开放回答。先独立写下判断，再主动展开下方公开参考答案和自评规程；自评只帮助发现遗漏，不生成平台成绩。

## 练习一 · 预测：两种需求是否该选 Rust 候选？

### 题面

回忆正文中的两种需求：

1. 长期维护、内存受限的日志解析工具；团队有 Rust 经验，性能和资源门槛尚待原型测量。
2. 两周内上线的内部报名页面；请求量低，公司已有成熟的 TypeScript 模板和托管方式。

分别预测：Rust 是否值得进入候选名单？每个决定写出一条来自需求的理由，以及一项仍需验证或无需额外引入的条件。不要只写“更快”“更安全”或“Rust 更适合后端”。

### 作答契约

- 每个场景各给一个候选决定。
- 至少一条理由必须对应题面中的真实约束或团队条件。
- 至少指出一个证据缺口，或说明为什么现有方案已经满足已知目标。
- 明确将未测量的性能描述为假设。

### 分层提示

1. 圈出每个场景的交付期限、运行限制和现有团队能力。
2. 哪个场景明确需要控制资源？哪个场景首先受交付期限影响？
3. 把“进入候选名单”与“已经证明更合适”区分开。
4. 查看参考答案，再按契约检查是否把假设误写成事实。

### 参考答案

日志工具值得把 Rust 列入候选：内存限制和长期维护是明确约束，团队也具备 Rust 经验；但题面没有性能基准，仍应在代表性日志和目标设备上测量峰值内存、解析速度、构建耗时与依赖支持。报名页面暂时没有明显的 Rust 特有约束，复用现有 TypeScript 技术栈更直接回应两周交付与接手成本。以后若出现现有方案无法满足的量化目标，再比较实现选择。

### 自评规程

- 两个决定各自引用了真实约束：2 分。
- 识别出日志工具需要测量，且没有断言 Rust 必然更快：1 分。
- 报名页面把团队已有能力和时间约束纳入选择：1 分。
- 给出的结论与理由矛盾，或使用绝对性能/安全保证：该场景不得分。

## 练习二 · 修复：改写这段站不住脚的决策说明

### 题面

一位同事写道：

> “这个服务偶尔有并发 bug，所以重写成 Rust 后所有安全问题都会消失，性能也肯定更好。我们不需要复现问题或做基准。整个服务应该一次性迁移，这样以后就不用测试了。”

请将这段说明修复成一个可以进入评审的短决策记录。保留“Rust 可能值得评估”的可能性，但纠正没有证据支持的保证，并写出两项下一步调查或实验。

### 作答契约

- 明确目前已知的事实不足以直接批准整体重写。
- 准确描述编译期所有权/类型检查可以帮助发现哪一类问题，同时说明仍需测试和安全评审。
- 设计至少两项能推翻当前假设的验证步骤。
- 给出比较或分阶段试点方案，不得把语言选择当成不用测试的理由。

### 分层提示

1. 找出原文中的“所有”“肯定”“不需要”等绝对表达。
2. 先确定 bug 的实际类别；并发数据竞争与业务逻辑错误不是同一问题。
3. Rust 编译器能提供哪些保证？哪些风险仍要通过设计和运行验证？
4. 参考答案列出一份评审可用的改写结构。

### 参考答案

“目前有偶发并发问题，问题类型和触发条件尚未确认。Rust 的所有权和类型系统可以在编译期阻止若干数据竞争和无效引用问题，但不能保证业务行为正确、没有逻辑竞态或没有安全缺陷。先用日志与可重复测试定位故障，并确认现有方案是否能修复；再对一个边界清楚的组件制作 Rust 原型，用同一组输入测试正确性、峰值资源、构建与部署成本。如果原型无法满足兼容或交付要求，就停止或调整试点。是否迁移整个服务应由这些结果和长期维护成本决定。”

可接受其他写法，只要区分了已知事实与假设、提出可复核的比较方法，并且没有把 Rust 说成绝对安全或自动更快。

### 自评规程

- 修掉了绝对性能、安全保证：1 分。
- 准确说明 Rust 的编译期保证有明确边界：1 分。
- 下一步验证可以重现并比较真实故障或工作负载：1 分。
- 迁移建议包含范围控制和停止/调整条件：1 分。

## 练习三 · 实现：写一份可验证的技术选择记录

### 题面

设备团队每天解析约 800 MB 的遥测日志；目标 ARM Linux 设备离线工作，解析进程的常驻内存上限为 64 MB。现有 Node.js 版本在代表性数据上的峰值为 110 MB。团队有一名有 Rust 经验的工程师、三名维护 TypeScript 服务的工程师，六周后要试点。设备构建流程和日志解析依赖能否支持交叉编译尚未调查。

请实现一份 4 段的决策记录：

1. 建议当前下一步，而不是直接宣告最终赢家。
2. 指出满足哪个硬约束是首要目标。
3. 设计至少三项公平的对比测量或兼容性检查。
4. 写出一个会让团队保留现有实现、调整方案或停止试点的结果。

### 作答契约

- 记录以题面已有数字为事实，不编造 Rust 的测试结果。
- 将 Rust 作为值得试点的候选是合理的，但应说明团队维护成本。
- 测量使用同一份代表性日志、目标设备和等价的解析契约。
- 至少一项检验不能通过简单换语言获得的工程条件，例如依赖支持或 ARM 交叉编译。
- 设置停止条件，例如经修复后的现有流式实现可稳定低于内存门槛，或 Rust 依赖/交付链不兼容。

### 分层提示

1. 现有程序距离 64 MB 上限还有多少？它当前满足硬要求吗？
2. 先把目标设备、离线条件和依赖调查列成独立风险。
3. 比较峰值内存、解析正确性/吞吐、二进制启动/体积、构建和维护成本。
4. 参考答案是一份可以在六周试点前评审的记录，不是“Rust 必然胜出”的结论。

### 参考答案

“建议在六周试点前制作一个边界清楚的 Rust 解析器原型，并并行检查现有 Node.js 版本能否通过流式处理满足 64 MB 上限。110 MB 的现有峰值高于门槛，所以现在需要解决内存问题；这只说明当前版本不达标，不证明 Rust 版本已达标。用同一目标设备、同一组代表性与边界日志，对比峰值内存、解析正确性和吞吐、启动时间/二进制体积，以及 ARM Linux 的构建与依赖可用性。记录谁负责后续工具链、依赖和线上排障。若现有版本经流式改造可以稳定达标，或 Rust 依赖不能在目标设备交付，就重新比较范围，不推进整体迁移。”

### 评审规程

每项 0–2 分：

- **依据**：引用 64 MB 门槛和 110 MB 实测，不虚构 Rust 测量值。
- **验证**：测量条件可比较，覆盖正确性和资源目标。
- **交付风险**：覆盖 ARM/离线依赖或构建链。
- **维护方案**：说明团队投入与持续责任人。
- **反证条件**：至少给出可以停止或缩小 Rust 试点的结果。

答题只需给出有证据链的方案，不按“最后选 Rust 还是 Node.js”这一项打分。答案风格不同但满足契约时应接受。

## 整体校验说明

三题分别练习证据预测、修复绝对化论证、实现可测试决策记录。公开规程供学习者自查；是否达成目标由学习者根据回答和证据判断。
