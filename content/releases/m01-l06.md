# M01-L06：综合自测——从空目录交付可测试程序

> **模块毕业任务：不依赖给定脚手架，从空目录交付一个能运行、能测试、能解释结果的 Rust 应用。** 先完成任务，再查看公开参考实现。

## 工程推进：独立交付工具

**从哪里来：** 上一节 M01-L05 已交付「通过测试的修复项目」。

**当前问题：** 离开脚手架后仍要能自行交付。

**本节决策：** 从空目录交付整数分格式化 CLI 与库函数。

**完成产物：** 可复现的最小 CLI 与验证报告。**验证证据：** 零值、边界格式和本地检查全部记录。

**为什么下一节需要它：** 在 M02-L01，将继续面对「CLI 的数值输入需要稳定类型和可变状态。」。

## 从空目录开始，才知道自己能否交付

现实中收到的小工具需求往往只有一句话：“做一个能从命令行使用的程序。”没有预先准备的函数签名或测试框架，最容易暴露的问题反而是需求没有写清：谁提供输入、如何处理失败、用户怎样运行？

开始前先把输入、输出、错误条件和验收命令写下来，再创建 Cargo 项目。`cargo run` 只能说明某条路径运行了，`cargo test` 则应覆盖不同输入与错误路径。最后从一个干净目录照自己的说明重新执行一遍，才能发现路径、清单或环境的遗漏。

独立交付的价值并不在于拒绝脚手架，而在于即使脚手架不存在，你也知道怎样把需求变成可复现的成果。

## 学习目标与先修

完成本节后，你能够独立创建 Cargo package、区分库代码与程序入口、编写真实行为测试，并对构建与运行留下可复查的验证记录。先完成 M01-L01–L05；使用 **Rust 1.95.0 / Edition 2024**，在本地终端操作。

## 场景：金额格式化小工具

团队收到一个明确的需求：把整数金额（单位：分）格式化成没有货币符号和千位分隔符的文本，始终保留两位小数。你需要交付一个叫 `amount-formatter` 的二进制 package，同时提供可复用的库函数。

**公开函数契约：**

```rust
pub fn format_cents(amount_cents: u32) -> String
```

**验收样例：**

| 输入（分） | 预期输出 |
| ---: | --- |
| `0` | `"0.00"` |
| `7` | `"0.07"` |
| `82` | `"0.82"` |
| `1000` | `"10.00"` |
| `1234` | `"12.34"` |
| `4007` | `"40.07"` |
| `1_000_000` | `"10000.00"` |

本节金额是无符号整数分值，不涉及浮点舍入、货币币种或国际化格式。

## 任务一：搭建项目骨架

在一个尚未存在的子目录旁运行：

```text
rustup toolchain install 1.95.0
cargo +1.95.0 new amount-formatter --edition 2024
```

进入项目根目录，至少组织出：

```text
amount-formatter/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   └── main.rs
└── （Cargo 首次解析依赖后生成的 Cargo.lock）
```

`src/lib.rs` 放公共函数，`src/main.rs` 调用它并打印 `12.34`。Rust package 名称中的连字符在 Rust 代码里引用 crate 时会对应下划线，例如 `use amount_formatter::format_cents;`。如果你已了解模块系统，可以直接尝试；不熟悉时以参考项目为准。

**验收：** 能指出 package 名称、Edition、函数签名和主程序入口，且没有增加与任务无关的依赖。

## 任务二：先写行为断言，再补实现

为 `format_cents` 至少写两项会调用函数的测试：

- 一项检查不到 1 元的输入（例如 7 → `"0.07"`）。
- 一项检查整数金额或零输入（例如 1000 → `"10.00"`）。

可以将单元测试写在 `src/lib.rs` 的 `#[cfg(test)]` 模块里。**只写 `assert!(true)` 或者测试没有被发现都不符合验收要求。**

**动手预测：** 为什么 `7 / 100` 是 0、而小数部分仍应显示 `07`？因为整数除法与取余得到两部分，格式化时还需要两位宽度补零。请先尝试独立实现，不要展开答案。

## 任务三：运行质量检查，记录结果

在项目根目录依次运行：

```text
cargo +1.95.0 fmt -- --check
cargo +1.95.0 check --all-targets
cargo +1.95.0 test
cargo +1.95.0 run
```

**检查结果时不要只看退出码：**

- 格式和编译命令应通过；
- 测试应该**发现至少两项有行为断言的测试**，并全部通过；
- 主程序标准输出应该只有一行 `12.34`（不计 Cargo 自身的构建信息）。

再用表中的其他输入手动或通过新测试验证。一个通过的测试集合只说明**已覆盖输入**符合契约，不能证明所有未知输入都满足要求。

## 任务四：做一次交付复盘

在 `verification.md` 中记录：

1. Rust 工具链版本与 Edition；
2. 运行的四项检查命令与结果；
3. 两项测试的输入、预期与实际；
4. 如果出过错，哪一条编译或测试诊断帮助你定位；
5. 哪些行为还未验证，以及下一步会补什么测试。

对于 Java / Go 后端开发者，这对应“把业务函数从启动入口分离、为可复用逻辑写单测、提交可审查构建证据”的习惯。Rust 的 Cargo 约定让最小库与二进制程序可以存在于同一个 package 中。

## 独立交付与边界验收

**从空目录创建另一个 package**，只根据公开签名实现 `format_cents`，不要复制 L05 的折扣函数。断言 `0→0.00`、`7→0.07`、`1000→10.00`、`1_000_000→10000.00` 和 `u32::MAX→42949672.95`；提交 `src/lib.rs`、`src/main.rs`、测试和命令记录。必须能在新目录独立复现。

**可复现命令：** 在仓库根目录运行 `cargo +1.95.0 test --offline --manifest-path content/samples/verified-lesson-drills/Cargo.toml m01_capstone::tests::l06_`。另可查看[配套 Rust 契约测试](https://github.com/liulewis67-ops/rust_training/blob/main/content/samples/verified-lesson-drills/src/m01_capstone.rs)，用于对照行为，**不代替原始实验起始工程或自己的独立实现**。

**提交证据：** 干净目录中的独立实现、输入/预期/实测边界表、可复现的 Cargo 检查命令与设计取舍说明。注明哪些内容由测试证明，哪些仍需人工评审。

## 分层提示

1. 整元部分是整数除法 `amount_cents / 100`。
2. 余下的分是 `amount_cents % 100`，展示时需要两位数。
3. 对不足两位的余数使用格式化宽度，例如 `{:02}`。
4. 在 `main` 里从本 package 的库 crate 导入并调用函数；确保测试实际执行，而不是仅通过编译。

## 参考实现

完成任务后可以下载[公开参考项目 ZIP](./m01-l06-reference.zip)。该项目提供完整清单、源码及 4 项行为测试，按课程基线曾通过格式、编译、测试和运行检查。

核心函数为：

```rust
pub fn format_cents(amount_cents: u32) -> String {
    format!("{}.{:02}", amount_cents / 100, amount_cents % 100)
}
```

注意：`format!` 只是创建字符串，**并不会**自动执行你的单元测试；你仍应核对项目结构、主程序输出及测试覆盖。

## 实践迁移：把金额格式化作为可交付接口

**先预测：** 金额为 5 分时，结果应是 `0.05` 还是 `0.5`？如果输入从几十变成数十亿分，字符串布局会变化吗？

**动手改造：** 从空目录创建包，先写整数分到两位小数的行为断言，再实现纯函数并通过 CLI 调用。

**反例与边界：** 覆盖零、个位分、恰好一元及足够大的整数；不要依赖浮点运算产生格式。

**验收证据：** 在干净目录依次运行 check、test、fmt，并提交可解释的输入/输出对照表。

## 本节小结

M01 不是要求背下四条 Cargo 命令，而是要求你能**从新建项目到故障排查、测试验证和可复查交付**独立走完一次小型开发循环。

## 原理推导与反例辨析：独立交付工具

**问题：** 离开脚手架后仍要能自行交付。

**原理与推导：** 独立交付必须从空目录建立包、公开函数与测试，不依赖上一节的预制故障工程。设计时先固定输入、输出和边界，随后验证。

**示例与证据：** 对照本节已有代码或起始工程，检验：零值、边界格式和本地检查全部记录。

**反例：** 反例是 CLI 显示了看似正确的整数分格式，却没有库级断言；用户看见一次输出不等于全部边界可靠。

**独立练习：** 从零创建 lib+bin，覆盖零值、单位转换与异常格式，执行 check/test/fmt 并记录独立复现步骤。

**复盘：** 判断是否掌握的标准是别人能按说明复现，而不是你自己的工作目录恰好能运行。
