# M07-L05 实验：可替换解析器接口

> **实验核心问题：** 两种解析器共享一份 trait 契约，某个实现却使用了错误分隔符。怎样用公开行为测试定位并修复，且不引入多余抽象？

## 实验目标

使用一个小型 trait 把调用方与分隔符解析规则解耦。学生将验证 `=` 与 `:` 两种格式经同一接口处理，保留首个分隔符之后的文本，报告输入错误，并从新解压目录完成可复现的库实验。

## 先修与环境

- 课程先修：完成 M07-L04，能用 newtype/错误类型表达有效值，并读懂 trait bound。
- 目标环境：Edition 2024、Rust 1.95.0；在本地使用 Cargo 运行公开项目与测试。
- 起始项目：[m07-l05-starter.zip](./public/m07-l05-starter.zip)，版本 0.1.0，无第三方依赖。

## 场景：配置文件同时支持两种键值分隔符

一组输入使用 `a=b`，另一组使用 `a:b`，都要转成统一标签格式 `key=value`。这并不要求把实现类型写死在调用方；统一 trait 可以让调用者依赖解析行为，而每个实现负责自己支持的分隔符。

**先预测：** 对输入 `"env:stable"`，让 `ColonParser` 错把 `=` 当分隔符会产生什么结果？为什么编译器不会自动识别它违反业务契约？

## 任务

项目已提供 `EntryParser` trait、共同错误类型、字段校验 helper、`EqualsParser` 与 `ColonParser` 两种解析器，以及泛型 `render_label<P: EntryParser>`。检查实现并修复题目中故意保留的错误：`ColonParser` 使用了错误的分隔符。若发现重复规则，可整理为一个共享 helper，但不增加没有调用方需求的额外 trait 或 wrapper 类型。

解析契约：

- 按该 parser 声明的分隔符第一次出现处分割；分隔符之后的其余字符属于 value，不再切开。
- key 与 value 用首尾空白判断有效性；有效字段保存 trim 后的文本。
- 无分隔符、空 key 和空 value 必须分别返回对应 `ParseError`，不要丢弃具体失败种类。
- `render_label` 对两种 parser 产生一致的规范形式 `key=value`，并原样保留 value 中额外出现的分隔符。
- 测试覆盖 ASCII、中文与 Unicode、首分隔符、空输入及错误传播。

## 分阶段验收

| 阶段 | 你要检查什么 |
| --- | --- |
| ① 初始行为 | `cargo test --offline` 能运行但有失败测试 |
| ② 定位 | 比较 `EqualsParser`、`ColonParser` 传给共同 helper 的分隔符 |
| ③ 修复 | 每种 parser 使用自身分隔符，并只在第一次匹配处分割 |
| ④ 错误契约 | 无分隔符、空 key、空 value 分别保留错误种类 |
| ⑤ 回归 | ASCII、中文/Unicode、多个分隔符及两种实现的测试通过 |

**与 Java/Go 对比：** 一个接口/trait 被实现，不代表实现自动符合行为契约。编译器验证方法签名和类型边界，业务测试则检验分隔符是否正确、错误信息是否保真。

## 起点与观察

打开起始 ZIP 后先运行 `cargo test --offline`。项目可以编译，但 `ColonParser` 错把 `:` 格式交给 `=` 分隔符，因此公开测试会失败。修复实现，让两种解析器满足同一契约。错误输入不应 panic，也不应全部伪装成缺分隔符。

## 检验理解

**先预测再执行：** 如果输入 `"key:part:rest"`，ColonParser 按第一个冒号切开后，value 是否还包含第二个冒号？为什么使用 `split_once` 比反复 `split` 更贴近本题？

## 分层提示

1. **定位提示**：对照 `ColonParser` 和 `EqualsParser` 的 `parse_delimited` 参数。
2. **行为提示**：separator 必须从当前 parser 获得，缺失错误也应记录同一个 separator。
3. **边界提示**：使用 `split_once`，然后分别检查 trim 后的 key/value；不要把整个 value 再切分。
4. **参考方案**：共享 helper 接收 `delimiter: char`，两个 trait 实现各自传入 `=` 或 `:`。

## 实践迁移：替换解析器时锁定首个分隔符

**先预测：** 一个输入支持 `env:stable`，另一个支持 `env=stable`。两个实现共享 trait 就保证它们按正确分隔符解析吗？

**动手改造：** 在实验 starter 中先预测错误的 ColonParser 行为，再修正分隔符，保持公共 trait 不变。

**反例与边界：** 验证没有分隔符、空 key、空 value、多个分隔符和 Unicode；第二个分隔符之后的内容不应被丢弃。

**验收证据：** 提供原始失败测试、修复后公开契约与一条说明为何类型检查不能捕获分隔符业务错误。

## 参考实现

```rust
impl EntryParser for ColonParser {
    fn parse(&self, input: &str) -> Result<Entry, ParseError> {
        parse_delimited(input, ':')
    }
}
```

共享 helper 负责首次分隔、字段 trim、空字段检查和错误区分；两种解析器保留各自的 delimiter。泛型 `render_label<P: EntryParser>` 仅依赖共同契约。
