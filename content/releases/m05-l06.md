## 拆分文本再修改源字符串，为何必须调整顺序

解析器先从一条字符串中借用两个子切片，接着想修改原字符串。即使切分位置本身合法，只要后续还要使用旧子切片，借用与修改就会重叠。这里同时考验 UTF-8 边界和借用有效范围。

先把子切片需要的信息处理完，再修改原字符串；或者当数据必须跨越修改长期存在时，明确生成拥有型副本。不要混淆“按分隔符找到正确的字节位置”与“修改后引用仍有效”：前者是文本合法性，后者是生命周期关系。

独立检查要分别证明两件事，再解释为何它们组合起来才构成安全接口。

## 输入检查点

- ASCII：split_label("head::tail", "::") 返回 ("head", "tail")。
- 多字节分隔符：split_label("部署：完成", "：") 返回 ("部署", "完成")。
- 多字节字符分隔符：split_label("东🧭西", "🧭") 返回 ("东", "西")。
- 首次匹配：split_label("a::b::c", "::") 返回 ("a", "b::c")。
- 分隔符为空、不存在，或输入为空时返回 None。
- 非空结果必须分别指向 text 中分隔符之前和之后的原始字节区间。

## 参考实现

```rust
pub fn split_label<'text>(
    text: &'text str,
    separator: &str,
) -> Option<(&'text str, &'text str)> {
    if separator.is_empty() {
        return None;
    }

    let start = text.find(separator)?;
    let end = start.checked_add(separator.len())?;
    Some((text.get(..start)?, text.get(end..)?))
}

fn main() {
    let mut label = String::from("部署：完成");
    let (kind, value) = split_label(&label, "：").unwrap();
    println!("parts: {kind} / {value}");
    label.push('!');
    println!("updated: {label}");
}
```

`find` 返回匹配位置的 UTF-8 字节偏移，`separator.len()` 也是字节数；匹配起止点因此对应分隔符两侧的边界。`get` 在边界无效时返回 `None`，避免直接索引可能触发的 panic。两片结果借用 `text`，所以先完成读取，再修改拥有文本的 `label`。
