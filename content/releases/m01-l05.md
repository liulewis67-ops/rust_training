# M01-L05：实验——让一个失败项目重新通过

> **实验任务：接手一个会“先编译失败、再测试失败”的折扣函数。** 你的任务不是直接抄正确实现，而是保存每个失败阶段的证据，逐步修好它。

## 工程推进：修复两层故障

**从哪里来：** 上一节 M01-L04 已交付「可审查的最小修复提交」。

**当前问题：** 一个编译通过的程序仍可能给出错误折扣结果。

**本节决策：** 先修类型错误，再以契约测试修业务逻辑。

**完成产物：** 通过测试的修复项目。**验证证据：** 编译和行为测试均独立通过。

**为什么下一节需要它：** 在 M01-L06，将继续面对「离开脚手架后仍要能自行交付。」。

## 折扣函数的两个失败阶段

接手一个折扣练习时，最初的错误可能来自类型或语法；修到能编译后，才暴露临界价格下的错误金额。如果只追求一次性把所有测试刷绿，很容易看不到故障是怎样一步步出现的。

保留一份原始起始工程，第一轮只修复阻止编译的问题，记录是哪条语言规则起了作用。第二轮准备正常金额、边界金额与错误输入，针对业务断言逐一修复。两轮测试报告应当清楚分开——不能把“终于编译成功”当成“折扣逻辑正确”。

一份好的实验复盘会写明：坏代码表现出什么结果、最小修复是什么、哪条断言能稳定识别原来的缺陷。

## 学习目标与先修

完成实验后，你能够：

- 用 `cargo check` 确认编译错误的类型和位置。
- 在修复编译后使用 `cargo test` 找出业务逻辑错误。
- 不修改公开函数签名和测试断言，交付能够解释、能够复验的最小差异。

先完成 M01-L03 与 M01-L04。项目使用 **Rust 1.95.0 / Edition 2024**；先运行 `rustup toolchain install 1.95.0`。本实验曾按该基线复现过初始失败和参考修复，但你仍应在自己的环境里验证。

## 场景与交付契约

下载[实验起始项目 ZIP](./m01-l05-starter.zip)，解压到新目录。项目是一个计算金额折扣的小库：

```rust
pub fn discounted_total_cents(
    subtotal_cents: i64,
    discount_percent: u8,
) -> i64
```

| 输入或规则 | 契约 |
| --- | --- |
| `subtotal_cents` | 0 到 1,000,000 分，包含边界 |
| `discount_percent` | 0 到 100，包含边界 |
| 折扣金额 | `subtotal_cents * discount_percent / 100`，整数除法向下取整（在给定非负范围内） |
| 返回值 | 原金额减去折扣金额 |

项目应包含 `Cargo.toml`、`src/lib.rs` 和 `tests/public_contract.rs`。公开测试覆盖 0%、10% 与 100% 折扣。**不允许删除测试、弱化断言或修改函数对外契约。**

## 实验步骤一：先捕获编译错误

在解压后的项目根目录运行：

```text
rustc +1.95.0 --version
cargo +1.95.0 check
```

**先预测：** 为什么此时还不能直接认定折扣业务逻辑错误？因为起始代码预计报类型不匹配 `E0308`，尚未通过编译检查。

记录错误码、文件位置和实际/期望类型，然后做**最小类型修复**。提示：`u8` 与 `i64` 不能隐式互换，但给定的百分比范围支持显式无损转换。

**阶段验收：** `cargo check` 通过；你能说明被修复的是哪一种编译约束，而不是“我多改几行后它绿了”。

## 实验步骤二：让测试暴露行为问题

不要立刻查看参考实现。类型问题修复后运行：

```text
cargo +1.95.0 test
```

起始样例的预期轨迹是 **1 项通过、2 项失败**。这说明测试已经能运行，但实现违反了折扣契约。

**动手预测：** 100 分打 10% 折扣，正确结果应该是多少？答案是 **90 分**。如果实现算出与之不符的金额，检查“百分比”是否真的按百分之一计算。

**阶段验收：** 你能指出失败测试、期望值、实际值与业务规则之间的关系，并且只调整必要逻辑。

## 实验步骤三：复验、查差异、解释原因

修复后执行：

```text
cargo +1.95.0 fmt -- --check
cargo +1.95.0 check
cargo +1.95.0 test
```

预期公开测试 **3 项通过**。如果使用 Git，可继续运行 `git diff`，确认没有改变项目契约。对 125 分、10% 的情况，按题意计算折扣 12 分，最终 113 分（整数向下取整）。

在 `notes.md` 里用三行写下：

1. 编译失败的证据 → 类型修复。
2. 测试失败的证据 → 业务逻辑修复。
3. 最终检查结果 → 仍存在的未覆盖边界。

## 与 Java / Go 开发习惯对比

Java、Go 和 Rust 都可能出现“代码能编译但计算不对”的情况。Rust 这里额外要求你显式处理不同整数类型，却**不会**替你推导正确的业务折扣公式。编译器负责检查类型约束，测试负责检查可观察行为；两者合起来才是反馈循环。

## 分层提示

1. 先看 `cargo check` 的主诊断，不要在编译失败时猜测试结果。
2. 如果百分比类型是 `u8`、金额是 `i64`，可以在确保范围符合契约时使用 `i64::from`。
3. 10% 意味着分母为 100；先用 100 分的输入手算，再运行测试。
4. 最后比较 0%、10%、100% 和“结果有余数”的情况。

## 参考实现

**请先完成三阶段实验再展开。** 保留原函数签名与所有公开测试，核心逻辑可以写为：

```rust
pub fn discounted_total_cents(subtotal_cents: i64, discount_percent: u8) -> i64 {
    let percent = i64::from(discount_percent);
    let discount_cents = subtotal_cents * percent / 100;
    subtotal_cents - discount_cents
}
```

这项实现依赖题面明确规定的非负金额、百分比和值域；不能不经审查就套用于任意 `i64` 或任意业务金额规则。完整失败样例和修复路径以 ZIP 内的公开材料为准。

## 实践迁移：把初次编译失败转成回归用例

**先预测：** 一个修复后的折扣计算在普通价格通过，却在折扣为零和上限附近出现错误。只保留快乐路径测试足够吗？

**动手改造：** 保留实验原始副本；先观察类型诊断，再让原有测试暴露业务错误，额外列出零折扣和临界输入。

**反例与边界：** 不准通过删除失败断言、改公开函数签名或修改期望值来让 CI 变绿。

**验收证据：** 分开保存“编译错误已修复”和“行为边界已修复”的证据，并能从干净副本重复执行。

## 本节小结

从错误现场入手，用“**编译诊断 → 测试结果 → 最小修复 → 重新验证**”交付可信的修改，而不是一次性修改到看似能运行。

## 原理推导与反例辨析：修复两层故障

**问题：** 一个编译通过的程序仍可能给出错误折扣结果。

**原理与推导：** 本实验把编译失败与业务断言失败分开解决，顺序很重要：只有能运行测试后，才可能观察业务契约是否成立。

**示例与证据：** 对照本节已有代码或起始工程，检验：编译和行为测试均独立通过。

**反例：** 反例是通过删除失败测试或修改期望值来“修绿”项目；这只是抹掉证据，没有恢复正确行为。

**独立练习：** 先保存初始失败诊断，按最小修改修复类型错误；再针对题目输入运行行为测试，增加一个越界或零值边界。

**复盘：** 完成报告应包含每个故障的根因、最小修复和独立验证，而不是只有最终 `ok`。
