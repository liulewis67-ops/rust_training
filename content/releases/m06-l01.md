# M06-L01：引用有效性与生命周期关系

> **本节核心问题：** 引用写了生命周期标注，就能保证局部 String 在函数返回后还活着吗？

## 工程推进：拒绝悬垂引用

**从哪里来：** 上一节 M05-L06 已交付「安全的 UTF-8 分割接口」。

**当前问题：** 零复制视图不能在 owner 销毁后仍被使用。

**本节决策：** 选择让调用方持有源数据或返回 owned 值。

**完成产物：** 不悬垂的返回契约。**验证证据：** 局部引用逃逸被编译器拒绝。

**为什么下一节需要它：** M06-L02 将面对「两个输入引用使输出来源不明确。」。

## 学习目标

- 区分拥有值的绑定与借用该值的引用，并判断引用在哪段代码中可以安全使用。
- 说明被引用值必须在引用的每次使用期间保持有效；缩短引用的使用范围不能让已经销毁的值复活。
- 通过作用域和数据使用顺序修复悬垂引用意图，而不是试图用类型标注延长对象寿命。
- 阅读编译器对悬垂引用的拒绝，指出 referent（被引用的值）离开作用域的位置。

## 先修与环境

完成 M05-L06，能追踪共享切片何时仍被使用，以及切片来自哪个 owner。本节先用局部作用域理解引用有效性；下一节再学习函数签名里的生命周期标注。生命周期描述引用可用的区域，不会管理或延长 owner 的实际寿命。

## 场景：处理请求时构造一个临时字符串

函数内部创建 `String`，请求处理结束后局部值将被销毁。如果向外返回指向它的 `&str`，调用方将引用无效内存。生命周期标注只描述引用**与被引用值的有效关系**，不会让值复活。

**先预测：** 先创建 `String`，再返回 `&local`，能靠把返回类型写为 `&'static str` 通过编译吗？为什么？

## 核心知识点一：引用只能在被引用值有效时使用

```rust
/// Borrows a String while its owner remains in scope.
fn main() {
    let notice = String::from("ready");
    let view = &notice;
    println!("notice: {view}");
    println!("owner: {notice}");
}
```

`notice` 拥有 `String` 值，`view` 是指向它内容的共享引用。`notice` 在两次读取时都有效，所以 `view` 可安全使用；创建引用没有移动 `String`。结束借用后，owner 仍可继续使用。

用两个区域想象这段关系：

```text
notice 的 String 有效：  ├──────────────────────────┤
view 的使用：              ├───────┤
```

安全条件是：每一次使用 `view` 时，`notice` 的值都还存在且可被借用。变量名可见的词法范围、值的有效时间、引用实际会被使用的区间相关但不是同一个概念。

## 核心知识点二：返回局部值的引用会悬垂

```rust
/// Attempts to return a borrow of a local String.
fn dangling_notice() -> &String {
    let notice = String::from("temporary");
    &notice
}

fn main() {
    let view = dangling_notice();
    println!("{view}");
}
```

函数返回时，局部绑定 `notice` 离开作用域，拥有的 `String` 随之销毁。当前签名缺少输出引用的来源标注，Rust 1.95 首先以 E0106 拒绝它。即使给返回类型写上 `'static`，也不会让局部 `String` 存活到函数外；那种写法会因返回局部值引用而被拒绝（通常诊断为 E0515）。生命周期标注只能描述有效期关系，不能延长对象的实际寿命。

可通过返回 owner 修复：

```rust
/// Transfers an owned notice to the caller.
fn make_notice() -> String {
    String::from("temporary")
}

fn main() {
    let notice = make_notice();
    let view = &notice;
    println!("{view}");
}
```

现在函数把 `String` 的所有权交给调用方；`notice` 在调用方作用域保持有效，`view` 只在借用期间读取它。另一个可行接口是借用调用方传入的文本并返回其中的切片，具体签名放到 M06-L02 学习。

## 核心知识点三：让引用不逃过 owner

如果只在创建 owner 的内层作用域里使用引用，代码安全：

```rust
/// Reads a borrowed view before its owner leaves the inner scope.
fn main() {
    {
        let notice = String::from("staged");
        let view = &notice;
        println!("view: {view}");
    }
    println!("inner owner has been dropped");
}
```

`view` 最后一次使用发生在 `notice` 离开作用域之前。离开内层作用域后，`notice` 和引用都不能再使用。这不是“把引用声明得短一点就能引用死值”：修复改变的是引用使用位置，使它仍落在 owner 有效的区域中。

分析引用代码时依次标记：谁拥有值、值在哪个作用域中存在、引用指向哪个值、引用的每次读取在哪里。如果引用使用延伸到 owner 被销毁之后，先重新设计数据流：把计算留在作用域内、返回拥有值，或借用调用者提供且仍有效的数据。

## 与 Java / Go 对比：Rust 的引用不拥有被借用值

Java 的对象引用通常参与垃圾回收可达性，Go 指针也可影响对象逃逸分析；Rust 的 `&T` 并不取得被借用值的所有权，编译器会约束它不能比来源值的有效范围更长。这不代表每个 Rust 数据都一定在栈上，也不能把生命周期写成变量“存活秒数”。

```text
owner 创建 ---- 引用可用 ---- owner 离开作用域
                             引用不能在此后继续使用
```

## 原理推导与反例辨析：拒绝悬垂引用

**问题：** 零复制视图不能在 owner 销毁后仍被使用。

**原理与推导：** 引用有效性的基础是被引用的 owner 在每次使用时都活着；生命周期标注不能替局部变量延长其真实存在时间。

**示例与证据：** 对照本节示例或起始工程核验：局部引用逃逸被编译器拒绝。

**反例：** 从函数返回指向局部 String 的 `&str` 会悬垂；把返回类型标为 `&'static str` 也不能让局部 String 获得静态寿命。

**独立练习：** 分别写从调用方 String 借用切片和返回新建 String 的函数；尝试在结果仍被使用时销毁源值，预测拒绝位置。

**复盘：** 复盘时解释借用返回与拥有型返回分别把哪些责任交给调用方。

**预测 → 验证：** 先在局部作用域内创建 `String`，把引用留到作用域外尝试打印，观察编译诊断；再分别用“在作用域内完成读取”和“直接返回拥有型 `String`”修复。

## 分层提示

1. **定位提示**：圈出 `String` 被创建的语句，以及它的右花括号。
2. **关系提示**：给 owner 画有效区间；把通过引用的每次读取画在同一时间线上。

## 实践迁移：临时配置字符串的悬垂引用

**先预测：** 函数构造临时 `String` 并返回它的 `&str`，给返回引用补上 `'static` 就能让局部数据活得更久吗？

**动手改造：** 先复现编译器拒绝，再按调用方需求改为返回 owned `String` 或引用调用方仍持有的数据。

**反例与边界：** 把借用传到另一个函数时确认输入 owner 仍活着；不要用 `Box::leak` 伪装成正常设计。

**验收证据：** 保存编译失败原因和修改后的所有权流向说明，并覆盖至少一个空输入。

## 本节小结

- 生命周期与引用约束描述数据关系，不负责让 owner 存活更久。
- 返回类型要与调用方的持有需求一致，不能只为避免复制就返回悬垂引用。
- 先用编译器和明确的边界测试验证来源，再考虑 API 的分配与维护成本。
