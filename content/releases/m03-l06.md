## 同时处理缺失和状态，不能只写一排 if

提醒系统需要告诉用户下一步行动。但提醒可能根本不存在，也可能已过期、已完成或仍在等待。如果先把“不存在”转换成一个默认状态，之后的分支就再也看不出究竟发生了什么。

先用 `Option` 表达查询结果，再用枚举表达存在的提醒所处的互斥状态。两层判断代表两件事：有没有这条记录，以及记录当前意味着什么。把它们分开，才能在增加新状态时判断哪些分支需要改、哪些不用改。

独立提交时不妨故意构造一组容易混淆的输入：没有提醒、名称为空但确实存在、刚过期和恰好到边界时间。解释每一条为何返回该动作，会比只给出 match 代码更有说服力。

## 契约

- `None` 返回 `"not found"`。
- `Queued` 返回 `"claim"`；`Claimed` 返回 `"deliver"`。
- `Delivered { attempts }` 在 `attempts < 2` 时返回 `"retry"`，否则返回 `"archive"`。
- `Cancelled { by_user: true }` 返回 `"close"`；`Cancelled { by_user: false }` 返回 `"review"`。
- 显式匹配 `Option` 和枚举的所有形态，不用 `_` 代替状态分支。新增枚举变体时应由编译器要求重新检查。

## 原理推导与反例辨析：交付提醒状态

**问题：** 查询缺失和业务状态需要组合决策。

**原理与推导：** 提醒动作是对状态和查询结果的组合决策，`None` 表示没有任务，不应与某个正常任务状态混为一谈。

**示例与证据：** 使用本节原有代码或实验验证：None 与每个状态均有独立断言。

**反例：** 只 match 状态却对缺失查询默认返回“已完成”，会误导调用方；把未知状态并入 `_` 也可能掩盖业务分支。

## 参考实现

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum AlertStatus {
    Queued,
    Claimed,
    Delivered { attempts: u8 },
    Cancelled { by_user: bool },
}

pub fn next_action(status: Option<AlertStatus>) -> &'static str {
    match status {
        None => "not found",
        Some(AlertStatus::Queued) => "claim",
        Some(AlertStatus::Claimed) => "deliver",
        Some(AlertStatus::Delivered { attempts }) => {
            if attempts < 2 { "retry" } else { "archive" }
        }
        Some(AlertStatus::Cancelled { by_user: true }) => "close",
        Some(AlertStatus::Cancelled { by_user: false }) => "review",
    }
}
```

没有通配分支，因此新增 `AlertStatus` 变体会触发穷尽性诊断。
