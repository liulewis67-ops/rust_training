# M01-L01：Rust 解决的问题与路线选择

> **本节核心问题：什么时候值得为一个现有的 Java / Go / TypeScript 团队引入 Rust？** 学会按约束做技术选择，而不是按语言热度投票。

## 学习目标

完成本节后，你应该能够：

- 给定一个项目场景，说明 Rust 是否**值得进入候选名单**，而非未经测量就宣称胜出。
- 分清已知约束、待验证假设与采用新语言的维护成本。
- 写出一份有验证办法和停止条件的简短技术决策记录。

## 先修

面向已经学过至少一门编程语言的人：能够描述程序的输入、输出，以及运行环境即可。若尚不熟悉函数、终端和文件，请先完成编程基础预备学习。

## 场景：两个项目，同一个语言选择

| 判断维度 | A：离线日志解析工具 | B：两周上线的报名页面 |
| --- | --- | --- |
| 交付目标 | 持续解析大文件 | 快速交付内部表单 |
| 主要约束 | 设备内存、输入规模、长期维护 | 上线时间、团队交接 |
| 现有团队 | 有 Rust 经验 | 已有成熟 TypeScript 模板 |
| 初步判断 | Rust 值得试点，**尚未证明胜出** | 优先复用现有技术栈 |

为什么不能直接说“A 用 Rust、B 不用 Rust”？因为这些结论仍取决于具体数据：日志大小、峰值内存、依赖能否部署、维护人员是否足够。决策要能够被实验推翻。

## 核心知识点一：语言特性不是交付结果

**先说结论：** Rust 的所有权与类型检查可以在编译期阻止一类无效内存访问和数据竞争，但不保证程序没有业务错误、逻辑竞态或安全漏洞，也不保证某段程序一定快于 Java 或 Go。

以日志解析为例，同一个业务需求至少要验证两件事：

1. **结果正确性**：输入相同日志时，字段解析、错误处理与输出一致。
2. **资源表现**：在目标设备上测量峰值内存、吞吐、启动时间及构建/发布成本。

只有正确性契约一致，才有资格比较性能。把“Rust 可能减少运行时开销”写成**假设**；把测出来的结果写成**证据**。

## 核心知识点二：Java / Go / Rust 如何比较

| 维度 | Java | Go | Rust |
| --- | --- | --- | --- |
| 常见内存管理方式 | GC | GC | 所有权、借用及确定性的资源管理机制 |
| 开发反馈 | 编译/测试、运行期分析 | 编译/测试、运行期分析 | 编译期所有权/类型检查、测试 |
| 工程选择重点 | 现有生态与团队、JVM 运行环境 | 部署简单性、并发模型与团队效率 | 资源控制、目标平台、类型设计与团队成本 |

**不要用这张表决定胜者。** JVM/Go 的 GC、Rust 的所有权都是工具；真正的依据是你的服务需要解决什么问题。对于熟悉 Java/Go 的后端开发者，学习 Rust 的价值还包括理解资源所有权、类型边界和并发约束，而不只是在项目中替换一种语言。

## 核心知识点三：用最小实验减少不确定性

对日志解析工具，可以先做一个“能运行但尚未证明性能”的探针：

```rust
fn main() {
    let input = "INFO|started";
    let (level, message) = input.split_once('|').expect("示例输入包含分隔符");
    println!("{level}: {message}");
}
```

**预测：** 输出是 `INFO: started`。这个例子只证明了最基本的字符串分割行为，**不能**证明 64 MB 内存约束、日志正确性或生产可用性。真正的试点还需要真实样本、错误输入和目标设备上的基准。

做技术决策记录时，建议填写：

| 必填项 | 应回答的问题 |
| --- | --- |
| 目标与硬约束 | 要交付什么，哪些数值必须达标？ |
| 当前证据 | 已测得什么？哪些只是推测？ |
| 备选方案 | 是否能先改进现有 Java/Go/TS 实现？ |
| 最小实验 | 使用什么输入、设备和正确性契约？ |
| 决策门槛 | 什么结果会继续、缩小或停止 Rust 试点？ |

## 检验理解

**先预测，再查看理由：** 一个服务偶尔有并发 bug，改用 Rust 后是不是就可以取消回归测试？

不能。Rust 的类型与借用检查不替你定义业务不变量，逻辑竞态、错误授权、错误重试策略仍可能出现。需要先复现原故障，再比较修复现有实现和试点 Rust 的代价。

## 本地练习

新建 `decision.md`，选择一个你熟悉的后端服务，填完上表。请继续完成本节下方的三道递进练习：**预测候选语言 → 修复不严谨的论证 → 写可验证的决策记录**。

**验收标准：** 能指出一项硬约束、两项可测量指标以及至少一个会推翻初步结论的结果；没有把未经验证的速度或安全性写成事实。

## 实践迁移：从语言偏好转向约束决策

**先预测：** 一个已有 Java API 的尾延迟超标，团队提议把整个服务迁移到 Rust。未定位热点时，技术决策能否直接写“改成 Rust 就会更快”？

**动手改造：** 选一个最小可替换模块，分别列出 CPU、内存、延迟、FFI/部署与团队学习成本，制定一份只测该模块的对照计划。

**反例与边界：** 增加“性能没有改善或维护成本明显提高”的情况，写出停止迁移的条件。

**验收证据：** 一页包含基线、可重复的测量方法、停止条件及回退方案的技术决策记录。

## 本节小结

- 语言选型服务于约束与交付，不是特性排行榜。
- “进入候选名单”与“已经证明最佳选择”是两回事。
- 一个好的选型结论必须带着可复现的验证办法和停止条件。
