# M02-L06：综合自测——带溢出处理的合计函数

> **模块综合任务：** 对所有 `u32` 输入计算两数合计；数学和可表示就返回精确值，否则返回错误。这次不允许靠 debug/release 的差异碰运气。

本节综合变量与类型、函数返回、分支和数值边界。先独立实现并运行公开测试，再展开参考实现。题目与所有检查点均公开，本站不记录独立能力证明。

## 工程推进：锁定合计契约

**从哪里来：** 上一节 M02-L05 已交付「可恢复的分钟转秒函数」。

**当前问题：** 多次合计需要可重复的溢出策略。

**本节决策：** 用 checked_add 交付带错误结果的合计函数。

**完成产物：** 经过边界验证的累计接口。**验证证据：** MAX+0 与 MAX+1 被区分。

**为什么下一节需要它：** M03-L01 将面对「累计数据需要带含义的字段与约束。」。

## 溢出策略应该由业务决定，而不是由构建模式决定

你正在交付一个结算合计函数，开发机的测试偶尔因为整数溢出 panic，发布版本却可能表现不同。如果这个函数处理的是资金或配额，静默回绕显然不是可以接受的业务决策。

从数学定义开始：两个 `u32` 相加的真实结果可能超过 `u32::MAX`。此时要么返回明确错误，要么在需求允许时采用更宽的类型；不要先写普通加法，再依靠测试碰巧没有覆盖极值。`checked_add` 能把“无法表示”变成稳定的返回分支，使调用方知道下一步怎么处理。

作为独立检查，这道题真正考察的不是能否记住 API 名称，而是你能否用临界输入证明结果在 debug 和 release 下都遵守同一契约。

## 学习目标与先修

完成 M02-L01–L05。实现一个对所有 `u32` 输入都不会 panic 的求和函数：可表示时返回精确和，溢出时返回错误。

## 场景：订单数量汇总不能静默溢出

两个计数都来自合法的 `u32` 字段；但这不代表两数的和仍能被 `u32` 表示。普通 `+` 在不同构建配置下可能表现不同，因此业务契约要求显式处理不可表示的结果。

**先预测：** `u32::MAX + 1` 是不是应该返回 0？根据题意不允许回绕，必须返回 `Err`。


- 若数学上的和可以由 `u32` 表示，返回 `Ok(精确和)`。
- 若和大于 `u32::MAX`，返回 `Err`；不能 panic、回绕或饱和到最大值。

```rust
mod tests {

    #[test]
    fn handles_zero_and_regular_values() {
        assert_eq!(checked_total(0, 0), Ok(0));
        assert_eq!(checked_total(17, 25), Ok(42));
        assert_eq!(checked_total(123, 456), Ok(579));
        assert_eq!(checked_total(456, 123), Ok(579));
    }

    #[test]
    fn handles_the_largest_valid_sum() {
        assert_eq!(checked_total(u32::MAX, 0), Ok(u32::MAX));

    }

    #[test]

    }
```

## 参考实现

```rust
pub fn checked_total(base: u32, adjustment: u32) -> Result<u32, &'static str> {
    base.checked_add(adjustment)
        .ok_or("total exceeds the u32 range")
}
```

`checked_add` 在结果可表示时给出 `Some(total)`，溢出时给出 `None`。`ok_or` 把两种情况映射到函数契约所需的 `Result`；实现不需要自行计算上界，也不会 panic。

## 原理推导与反例辨析：锁定合计契约

**问题：** 多次合计需要可重复的溢出策略。

**原理与推导：** 累计求和比单次乘法多一个不变量：每次更新后的总和都必须可表示，`checked_add` 将失败定位到具体一步。

**示例与证据：** 对照本节现有代码或实验，核验：MAX+0 与 MAX+1 被区分。

**反例：** 只测试总和很小的正数序列，会漏掉中间步骤的溢出；把溢出截断或环绕也会改变业务契约。

**独立练习：** 设计空输入、单项、恰好达到上限、超限的四组测试，记录首次失败的累加步骤并说明返回值。

**复盘：** 能解释为什么选用 checked_add 而不是依赖默认 `+`，才算完成独立测试。

## 检验理解

**先预测再验证：** 为什么两个合法的 `u32` 数相加，不一定产生合法的 `u32`？尝试 `(u32::MAX, 0)` 与 `(u32::MAX, 1)`，对比 `checked_add` 返回的 `Some`/`None`，再解释如何映射成 `Ok`/`Err`。

## 自查清单

- 函数签名保留 `Result<u32, &'static str>`。
- 测试调用函数并检查实际结果，测试数量大于零。
- 两个参数交换后结果仍符合数学加法。
- 最大合法值成功，超过最大值时返回 `Err`。
- 解释 `checked_add` 的两条路径，并能说明普通 `+` 不满足此处的全输入契约。

## 实践迁移：合计函数的边界反例

**先预测：** 两个独立合法的 `u32` 计数值相加，是否保证结果仍然合法？

**动手改造：** 先写出 `u32::MAX + 0` 与 `u32::MAX + 1` 的预期，再按本题接口实现可恢复的溢出路径。

**反例与边界：** 检查交换两个输入后结果是否一致；不能用 wrapping_add 或静默饱和替换题目规定的错误返回。

**验收证据：** 对普通、零、边界和溢出输入保留实际断言，说明它们与编译通过是两类证据。

## 本节小结

- 输入类型合法，不代表算术结果不会超出类型范围。
- `Result` 需要为成功与失败分别建模，不能靠 panic、回绕或饱和值伪造结果。
- 让测试覆盖普通值、零、最大合法值与越界值，才能验证边界契约。
