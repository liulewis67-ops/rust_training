## 场景：从服务处理器的临时资源开始

一个处理器创建了两个拥有资源的临时值，离开内层代码块时要释放它们。你需要区分**变量绑定**、**拥有的值**和**值管理的资源**，而不能把“变量名”画成内存地址。

**先预测：** 在同一作用域按顺序创建两个局部 owner 后，作用域结束的销毁顺序是什么？用教材中的 `Drop` 事件输出来验证，而不是凭直觉。

## 核心知识点一：绑定、值和资源

Rust 中每个值有一个 owner；当 owner 离开作用域时，该值会被销毁。变量名是绑定，不等同于它所绑定的值；值还可能拥有其他资源。例如 `String` 值拥有用于存储文本的缓冲区。作用域图是理解关系的模型，不承诺值在机器上的固定地址或具体布局。

下例用 `ResourceLease` 的自定义 `Drop` 回调打印销毁事件。每个实例也持有一个 `String` 字段；`Drop` 只负责记录“lease 正在销毁”，其字段仍由 Rust 自动清理。

```rust
/// Owns a label that makes scope cleanup visible in the output.
struct ResourceLease {
    name: String,
}

impl ResourceLease {
    /// Creates a lease with an owned label.
    fn new(name: &str) -> Self {
        Self {
            name: String::from(name),
        }
    }
}

impl Drop for ResourceLease {
    fn drop(&mut self) {
        println!("drop {}", self.name);
    }
}

/// Shows when owners leave nested scopes.
fn main() {
    let room = ResourceLease::new("room");
    {
        let first = ResourceLease::new("first");
        let second = ResourceLease::new("second");
        println!("inner scope ends");
    }
    println!("outer scope continues");
    println!("main scope ends");
}
```

事件顺序为：

```text
inner scope ends
drop second
drop first
outer scope continues
main scope ends
drop room
```

`second` 在内层作用域创建得比 `first` 晚，因此离开该作用域时先销毁；`room` 的 owner 仍在 `main` 作用域中，所以要等到最后才销毁。每个 `drop ...` 行来自对应值的 `Drop::drop` 回调。

可用下面的关系图核对对象；箭头表示拥有关系，而不是借用：

```text
main scope
└── binding `room`
    └── value `ResourceLease`
        └── owned resource: `String` buffer "room"
    inner scope
    ├── binding `first`  ──> value `ResourceLease` ──> String buffer "first"
    └── binding `second` ──> value `ResourceLease` ──> String buffer "second"
```

离开内层作用域先调用 `second` 的自定义 Drop 回调，再调用 `first` 的回调；这些值随后拥有的字段也会由 Rust 自动清理。`Drop` 回调适合封装确实需要的资源清理或可观察事件。普通 `String` 等字段通常已经知道怎样清理，不必仅为释放内存再写自定义 `Drop`。

## 核心知识点二：`Drop` 何时运行

实现 `Drop` 后，Rust 会在值被销毁时调用 `drop(&mut self)`。常见时机是 owner 离开作用域，或值通过 `std::mem::drop(value)` 被提前丢弃。不能直接调用 `Drop::drop`；这样会破坏“每个值只按生命周期销毁一次”的约束。提前释放时使用标准库的 `drop` 函数，它会消费该值。

阅读事件输出时按次序标记：先找创建绑定的语句和它所属的花括号，再找离开作用域前的普通输出，最后依反向创建次序列出将销毁的 owner。若某值在内层作用域结束后仍被使用，先检查它究竟在哪个作用域创建；不要把绑定名、拥有的值和字段资源混成同一个实体。

## 与 Java / Go 对比：资源离开作用域的时机

Java/Go 的垃圾回收负责某些内存回收，并不等于所有资源都有确定的作用域结束释放时间；资源仍常通过 try-with-resources、defer、close 等机制进行管理。Rust 的所有权与 `Drop` 使拥有值离开作用域时发生析构，但不要据此承诺具体物理地址或操作系统即时回收所有相关内存。

**心智模型：**

```text
绑定名 -> 拥有的值 -> 值管理的资源
        作用域结束 -> Drop / 字段清理
```

## 检查顺序

1. 为每个资源值标出唯一 owner 和创建位置。
2. 找到 owner 的作用域边界，以及是否通过标准库 `drop` 提前销毁。
3. 对同一作用域内的值按创建顺序反向列出 Drop 事件。
4. 把自定义 Drop 回调和自动字段清理分开说明；检查图示关系是否能解释所有输出。

## 原理推导与反例辨析：追踪资源生命周期

**问题：** 任务结构进入处理流程后，必须知道何时释放。

**原理与推导：** 值的所有权和变量名并不等价：局部绑定拥有值，值拥有资源，离开作用域时 `Drop` 与字段清理按规则执行。

**示例与证据：** 对照原有代码或实验验证：移动后的资源仅被释放一次。

**反例：** 把 `Drop::drop` 当作能手动反复调用的资源释放函数，会产生错误直觉；正确提前销毁应通过 `std::mem::drop(value)` 消费值。

**独立练习：** 先画三个嵌套 owner 的作用域与销毁顺序，再加入一次显式 `drop`，比对事件 trace 是否与预测一致。

**复盘：** 检查自己能否分别指出绑定、资源和自定义 Drop 回调，而不是把它们混成一个指针。

## 本节小结

- 先标出 owner、发生变化的操作和受影响的旧绑定，再判断代码是否合法。
- 编译期所有权检查与运行期资源清理是不同层面，不能相互替代。
- 需要同时保留多份数据时，先明确业务契约及可能的复制成本。
