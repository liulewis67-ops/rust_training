> **实验核心问题：** 同一份配置可以零复制地查看，也可以转换为独立拥有的结果；什么时候必须选择后者？

## 一次解析，为什么需要借用视图和拥有结果

配置解析器既支持前端页面的即时预览，又要将最终配置发送给长期运行的任务。强行让两边共用拥有型 `String` 会产生不必要的拷贝；强行让队列保存输入切片，则可能让队列依赖已经释放的请求缓冲区。

一种清晰的组织方式是先构造借用视图供读取和校验，再在真正需要独立保存时显式转为拥有型结构。整个过程要检查字段是否真正借用了原输入，以及转换后即使原缓冲区销毁，结果是否仍然完整。

实验的重点是把“所有权转换发生在哪里”变成 API 的清晰节点，而不是在每个函数中随意调用 `to_owned`。

## 学习目标与先修

已完成 M06-L01–L04，能说明输出引用与输入 owner 的关系。本实验使用两种配置解析 API，在源输入离开作用域后检验拥有型结果是否仍有效。

## 实验目标

- 实现对同一配置输入提供一致业务字段的借用视图和拥有型返回值。
- 证明 `ConfigView` 的字段来自原始输入，调用方在视图最后一次使用前保留输入 owner。
- 让 `queued_config` 返回独立拥有的 `Config`，使调用方能在源输入销毁后继续读取。
- 比较借用版不复制字段文本与拥有版复制/分配字段的使用边界。

## 行为契约

- `parse_view(line)` 和 `parse_owned(line)` 都按第一个 `=` 分隔为 key/value；没有分隔符时均返回 `None`。
- 空 key、空 value 和后续额外 `=` 均保留原输入字段语义；不得硬编码样例。
- `ConfigView<'source>` 的 key 和 value 都借用输入 `line` 的原始 UTF-8 切片。
- `Config` 的两个字段均为 `String`，可独立于输入保存；`queued_config` 必须输出 `MODE` / `cache`。
- `queued_config` 的源字符串离开函数作用域后，返回结果仍可读；不得泄漏源字符串或把局部视图标为 `'static`。
- 不联网、不读写文件、不使用第三方 crate；不得修改公开函数名、返回值语义或公开契约测试。

## 先预测：同一输入，两种结果

输入 `"MODE=cache"`，借用版与拥有版都应该得到 key `"MODE"`、value `"cache"`。但如果 `line` 在函数返回前销毁，借用视图便不能再被调用方使用；需要排队保存时必须返回拥有型 `String` 字段。

**先预测：** 仅把 `ConfigView` 标为 `'static` 能让它合法引用局部 `String` 吗？为什么？

## 原理推导与反例辨析：修复配置视图

解析结果需要同时支持借用读取和独立入队。 解析配置后给 UI 展示可以返回借用视图，交给队列则必须把需要长期存活的内容变为拥有型数据；两条路径应共享一致的解析规则。

当配置需要支持即时预览与异步保存时，先用借用视图检查输入，再在独立保存的边界做一次明确的拥有型转换，比在每个字段处重复 `to_owned` 更容易维护。

让视图借用临时解析缓冲区会悬垂；为所有短期读取都复制整个配置则可能带来无必要开销。 让预览引用依赖源文本，然后销毁源文本并确认拥有型配置仍可独立使用。测试还应包含空字段和非法输入，不能只凭生命周期检查推断解析结果正确。

关键的对照实验应当能亲自复现：在 starter 中分别验证立即读取与 owned 入队结果，覆盖空字段和无效字段，明确每条路径的存活边界。 复盘时解释为何两种返回类型都满足需求，而不是只看是否通过借用检查。

## 同一份配置，可以有即时视图，也可以有独立副本

配置预览与任务入队看起来都需要两个字段：`key` 与 `value`。但预览发生在源字符串仍存在的当下，可以借用原始切片；后台任务在函数结束后继续运行，则不能把局部 `String` 的引用当成长期存储。这里最重要的 API 决策是结果必须活多久，而不是字段名字如何拼写。

以 `"MODE=cache"` 为例，借用视图和拥有型配置都应得到 `MODE`、`cache`。如果使用第一次 `=` 进行分割，额外的 `=` 仍属于 value；空 key 与空 value 也必须按题目语义保留，而不是因为看起来奇怪就删除。两条 API 应共享解析规则，区别只在最终内容由谁持有。

起始工程的 `queued_config` 故意在源字符串离开作用域后还试图留下借用视图。给返回类型随手加 `'static` 并不会延长原输入的寿命。正确的设计方向是确定一个明确的拥有型转换边界：在数据从同步预览流向异步或长期存储时，创建真正独立的 `String` 字段。

测试可以先比较两条解析路径的文本一致性，再检查借用切片的来源与拥有型结果脱离源输入后的可用性。前者验证解析，后者验证生命周期；不能因为两个字符串内容相同就推断它们的存储关系也相同。

## 分阶段验收

| 阶段 | 期望证据 |
| --- | --- |
| ① 类型诊断 | `queued_config` 初始把 `&str` 放进 `String` 字段的类型错误 |
| ② 借用解析 | `ConfigView` 指针范围与输入一致，未分配字段副本 |
| ③ 拥有解析 | `Config` 字段是独立 `String`，源字符串销毁后仍能读取 |
| ④ 契约边界 | 缺失分隔符返回 `None`，空字段和额外 `=` 保留原有语义 |
| ⑤ 交付 | 离线格式、check、test 全部通过，原始 ZIP 可重置 |

与 Java/Go 对比：返回结果的**使用期限**决定是否需要拥有型字段。Rust 的借用视图降低了不必要的文本拷贝，但也限制了调用方可以持有结果多久；队列需要跨过输入作用域，因此必须显式拥有数据。

## API 选择依据

借用视图以 `&str` 字段指向输入，不复制字段内容；它要求输入 owner 覆盖视图的读取区间。拥有型 `Config` 把两个字段复制进 `String`，需要额外分配，但可脱离输入作用域继续留在队列。队列契约明确要求跨过源输入作用域，因此这里选择拥有型返回值。

## 分层提示

1. 先通过 `split_once('=')` 找到两个原始子切片，不要处理超出业务约定的分隔符。
2. `ConfigView` 的字段可以直接借用源文本；不能让它逃离源 owner 的有效范围。
3. `Config` 的字段需要 `String`，可以对各字段执行 `to_owned()` 或使用已有拥有型解析 API。
4. 对比相同输入的两种结果与实际持有范围，不能靠添加 `'static` 绕开源数据销毁。

## 参考实现

**阅读代码前先预测：** 这份参考实现同时展示借用视图和拥有型结果。阅读前先问：哪个字段仍指向原始配置文本，哪个结果可以在原输入销毁后继续使用？

```rust
pub fn parse_view(line: &str) -> Option<ConfigView<'_>> {
    let (key, value) = line.split_once('=')?;
    Some(ConfigView { key, value })
}

pub fn parse_owned(line: &str) -> Option<Config> {
    let (key, value) = line.split_once('=')?;
    Some(Config { key: key.to_owned(), value: value.to_owned() })
}

pub fn queued_config() -> Config {
    let line = String::from("MODE=cache");
    parse_owned(&line).expect("the sample line contains '='")
}
```


**运行或编译后观察：** 对照两条解析路径输出相同的字段内容，但保留时间不同。把借用视图试图放进长期队列，应该让生命周期约束指出问题；将拥有型转换安排在入队边界更符合需求。
借用解析返回 `line` 中的原始切片；拥有型解析复制字段到独立 `String`。`queued_config` 选择拥有型结果，所以局部输入销毁后返回值仍有效。
