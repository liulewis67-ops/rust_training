# M01-L03: build, check, run, test and diagnostic reading

> **Guiding question:** If Cargo says a command failed, which stage actually failed?


## A deeper principle and falsifiable exercise

Cargo check, test and run answer distinct questions about types, assertions and runtime behavior. One success does not prove all three.

**Practice:** Construct a minimal passing example, one deliberate counterexample, and a fixed version. Predict the result before compiling, then record the diagnostic and explain why the fix preserves the intended API rather than merely hiding the error.

## Engineering thread: Separate failure stages

**Carry forward:** The previous lesson, M01-L02, produced "Pinned setup notes and Cargo package."

**Current obstacle:** Build, test, and runtime failures are easy to conflate.

**Decision to make:** Distinguish check, test, and run failures.

**Deliverable:** Reproducible diagnostic log. **Evidence:** Each failure has its own command and evidence.

**Why it leads forward:** In M01-L04, the next constraint is: Unrelated edits obscure whether a fix works.

## Compilation failures and behavioral failures tell different stories

A developer runs `cargo check`, `build`, `run`, and `test` and reports only that “Cargo failed.” These commands answer different questions. A type error stops before assertions execute; a failing assertion means compilation succeeded far enough to reach a behavioral disagreement.

Instead of adding `clone` or weakening assertions on sight, read the first meaningful diagnostic and record the command, phase, minimal input, and observed result. This distinction between toolchain, compiler, and domain behavior is the basis of useful bug reports.

## Learning objectives

- Choose check, build, run and test for different questions

- Read file, line, error code and types in compiler output

- Distinguish compilation, test assertions and runtime behavior

## Scenario: build, check, run, test and diagnostic reading

A teammate sends a screenshot of an old unit test failure, but your current checkout cannot even compile. Separate failures rather than patching the wrong layer.

## Core concept 1: A command answers a specific question

cargo check type-checks quickly without producing a normal executable; build produces artifacts; run executes a binary; test builds and runs tests.

## Core concept 2: Diagnose in order

Record the exact command, toolchain, first relevant error, expected behavior and observed result before changing implementation.

## Core concept 3: Verify a fix at the same boundary

Fix compilation before interpreting unit-test failures. A successful check does not assert correct discount calculations or runtime output.

## Reason through a counterexample: Separate failure stages

**Problem:** Build, test, and runtime failures are easy to conflate.

**Principle and deduction:** Classify failures by compile checks, assertions, and runtime execution; these verify different properties and require different evidence.

**Example and evidence:** Use the example or starter above to check: Each failure has its own command and evidence.

**Counterexample:** A successful cargo run does not prove that tests passed or that malformed input is handled.

**Independent exercise:** Introduce one type error, one incorrect assertion, and one runtime boundary failure. Predict the earliest revealing command and capture the before/after evidence.

**Review:** A useful diagnostic report identifies the minimal reproduction command for each defect.

## Practice transfer: Three reproducible failure stages

**Predict:** Can a unit test be meaningfully evaluated if its crate fails compilation?

**Implement:** Run cargo check, cargo test and cargo run separately, capturing the first relevant diagnostic and exit status.

**Counterexample and boundaries:** Produce a case that compiles but fails a business assertion; contrast it with a real compile error.

**Acceptance evidence:** A short reproduction log with each stage, before/after evidence and the exact fix applied.
