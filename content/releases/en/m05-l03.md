## Why UTF-8 text cannot be sliced by a character guess

A log line contains `你好|ready`. If you treat the second character as the second byte, a slice may land inside a multibyte character. Rust string slices must remain valid UTF-8.

Find a valid boundary using an operation such as `split_once('|')`, and return borrowed `&str` views into the original input. That preserves data without allocating new strings. When designing text APIs, distinguish bytes, Unicode scalar values, and user-perceived grapheme clusters.

### Example 1

~~~rust
/// Keeps ownership of a String after passing a borrowed view.
fn main() {
    /// Reads a borrowed string slice without taking ownership.
    fn describe(text: &str) {
        println!("text: {text}; bytes: {}", text.len());
    }

    let title = String::from("你好");
    describe(&title);
    println!("owner: {title}");
}
~~~

### Example 2

~~~rust
/// Exercises first_token on ASCII, Chinese, Unicode whitespace, and empty text.
fn main() {
    /// Returns the first Unicode-whitespace-delimited token from the input slice.
    fn first_token(text: &str) -> &str {
        text.split_whitespace().next().unwrap_or("")
    }

    println!("ascii: {}", first_token("  build tools  "));
    println!("chinese: {}", first_token("你好 世界"));
    println!("unicode space: {}", first_token("  rust\u{3000}课程"));
    println!("empty: {:?}", first_token(""));
}
~~~

### Example 3

~~~rust
/// Tries to return a slice into a local String.
fn invalid_token(text: &str) -> &str {
    let owned = String::from(text);
    owned.split_whitespace().next().unwrap_or("")
}
~~~

## Java / Go comparison

Java String.length counts UTF-16 code units; Go len(string) and Rust str::len count UTF-8 bytes. User-perceived graphemes are different again.
