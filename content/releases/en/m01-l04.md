# M01-L04: Git, formatting, Clippy and minimal tests

> **Guiding question:** What makes a small Rust change safe enough to merge?

## Engineering thread: Make reviewable changes

**Carry forward:** The previous lesson, M01-L03, produced "Reproducible diagnostic log."

**Current obstacle:** Unrelated edits obscure whether a fix works.

**Decision to make:** Separate format, lint, behavior tests, and staging.

**Deliverable:** Minimal reviewable fix. **Evidence:** A failing assertion turns green and the staged diff is focused.

**Why it leads forward:** In M01-L05, the next constraint is: A compiling program may still calculate an incorrect discount.

## Learning objectives

- Separate formatting, lint, compilation and behavior checks

- Write a test that calls real production logic

- Review exactly what is staged in Git

## Prerequisites

Finish the preceding lesson and be able to run Cargo commands locally. Examples follow the Rust 1.95.0 / Edition 2024 course baseline.

## Scenario: Git, formatting, Clippy and minimal tests

You fix a discount function while the working tree contains unrelated draft documentation. Reviewers should not have to sift through an accidental all-files commit.

## Core concept 1: Four tools cover different risks

cargo fmt addresses style; cargo clippy highlights likely issues; cargo check verifies type and borrow constraints; cargo test checks declared behavior.

## Core concept 2: A useful test can fail

Use specific input and expected output. A test that only checks whether a function exists cannot catch an incorrect discount calculation.

## Core concept 3: Stage the smallest coherent change

Use git diff, git add <specific paths> and git diff --cached; leave unrelated files outside the PR.

## Java / Go comparison

Java and Go teams use formatters, linters, compiler checks and tests too. Keep these signals separate instead of treating one green command as a universal correctness certificate.

## Reason through a counterexample: Make reviewable changes

**Problem:** Unrelated edits obscure whether a fix works.

**Principle and deduction:** Formatting, Clippy, type checking, tests, and staged diffs address style, suspicious code, legality, behavior, and change scope respectively.

**Example and evidence:** Use the example or starter above to check: A failing assertion turns green and the staged diff is focused.

**Counterexample:** A green cargo test run with zero tests, or a commit that stages unrelated files, does not establish a safe change.

**Independent exercise:** Write an assertion that fails against a wrong implementation, show red/green evidence, and inspect exactly what Git has staged.

**Review:** Review what each tool actually proves, including what it cannot prove.

## Practice transfer: A minimal reviewable pull request

**Predict:** Will git add . include unrelated work already in the tree?

**Implement:** Add a discount boundary assertion, run all four checks and stage only the relevant source and test files.

**Counterexample and boundaries:** Intentionally return a constant discount once to prove your test catches an incorrect result.

**Acceptance evidence:** Show the red/green assertion result, staged diff and a one-sentence scope explanation.

## Summary

- Four tools cover different risks: cargo fmt addresses style; cargo clippy highlights likely issues; cargo check verifies type and borrow constraints; cargo test checks declared behavior..

- A useful test can fail: Use specific input and expected output.

- Stage the smallest coherent change: Use git diff, git add <specific paths> and git diff --cached; leave unrelated files outside the PR..
