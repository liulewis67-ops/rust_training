# M02-L01: Variables, mutability, primitive types and inference

> **Guiding question:** Why is mut required for reassignment, and why does Rust sometimes need an explicit integer type?


## How the knowledge fits together

**Module goal: Turn input constraints into reliable calculations.** Work through the concepts as a sequence of problems and decisions rather than a list of API names:

1. **Define numeric contracts** — The CLI needs explicit numeric types and mutable counters. The decision is to choose integer types, binding mutability, and conversions.
2. **Extract pure functions** — Typed data still needs a testable function result. The decision is to use tail expressions for return and conditional branches.
3. **Make control flow explicit** — Calculations need iterations with precise bounds. The decision is to choose if, for, and while with verified bounds.
4. **Model data shapes** — A sample set and a heterogeneous record need different types. The decision is to distinguish arrays, tuples, indexing, and match.

L05 integrates these ideas into **Recoverable minutes-to-seconds converter**. L06 changes the scenario and checks whether you can produce **Boundary-tested aggregation interface** independently. Examples within the module need not share one business setting: the continuity is conceptual.

## Scenario: Variables, mutability, primitive types and inference

A retry counter receives an 8-bit request value while the running total uses u32. Explicitly model the two distinct concerns: binding mutation and numeric representation.

## Core concept 1: Rule

Bindings are immutable by default; mut permits reassignment but does not alter the type.

## Core concept 2: Reasoning

Type inference follows expressions and constraints; annotate types when a value or operation is ambiguous.

## Core concept 3: Verification

Different integer types do not implicitly widen into one another. Convert deliberately after checking the intended range.

## Code walkthrough

The examples below are retained from the validated source lesson. Some deliberately show compiler or business failures: test them in separate files, predict the failure first, and do not remove the failing behavior to make an assertion pass.

### Example 1

```rust
/// Prints a value from an immutable binding.
fn main() {
    let attempts = 3;
    println!("attempts = {attempts}");
}
```

### Example 2

```rust
/// Shows a binding that is intentionally updated.
fn main() {
    let mut attempts = 3;
    attempts += 1;
    println!("attempts = {attempts}");
}
```

### Example 3

```rust
/// Demonstrates type inference for scalar values.
fn main() {
    let retries = 3; // 整数默认类型是 i32。
    let ratio = 0.75; // 浮点数默认类型是 f64。
    let enabled = true;
    let marker = 'R';
    println!("{retries}, {ratio}, {enabled}, {marker}");
}
```

### Example 4

```rust
/// Demonstrates explicit annotations for scalar values.
fn main() {
    let port: u16 = 8080;
    let temperature_c: i16 = -5;
    let sample_rate: f32 = 0.5;
    println!("{port}, {temperature_c}, {sample_rate}");
}
```

### Example 5

```rust
/// Demonstrates an explicit, lossless integer conversion.
fn main() {
    let parsed: u32 = "42".parse().expect("示例输入是有效的 u32");
    println!("{parsed}");
}
```

### Example 6

```rust
/// Demonstrates a parse operation with a known-valid teaching literal.
fn main() {
    let discount_percent: u8 = 10;
    let displayed_percent: i64 = i64::from(discount_percent);
    println!("{displayed_percent}");
}
```

## Java / Go comparison

Java and Go have different rules for inferred numeric types and mutability. Rust makes the variable binding and numeric conversion constraints visible at compile time.
