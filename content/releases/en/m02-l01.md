## A retry counter is also a data contract

A developer adds a retry counter to an occasionally failing API call and instinctively reaches for a mutable variable. Rust's default immutability asks a useful question: which values are configuration, and which actually change during execution?

`let mut` marks intended mutation; type inference determines types from context, not the business range you had in mind. Choose integer widths based on valid inputs and overflow requirements, especially when parsing external text. Variable declarations are more useful when they encode a real decision than when they merely silence compiler diagnostics.

## Core concept 1: Rule

Bindings are immutable by default; mut permits reassignment but does not alter the type.

## Core concept 2: Reasoning

## Reason through a counterexample: Define numeric contracts

**Problem:** The CLI needs explicit numeric types and mutable counters.

**Principle and deduction:** Rust bindings are immutable by default; shadowing creates a new binding, while type inference uses context and does not implicitly widen numeric types.

**Example and evidence:** Compare with the existing code or lab and verify: Zero, u8 bounds, and invalid mixed arithmetic are checked.

**Counterexample:** Treating mut as a universal variable modifier or assigning a u16 to a u32 without conversion confuses mutability with type conversion.

**Independent exercise:** Predict the type and output of immutable, mutable, and shadowed counters; add explicit numeric conversions and explain possible overflow.

**Review:** Separate the question of whether a binding can change from the question of which type its value has.
