# M07-L01: Generics and trait bounds

> **Guiding question:** Why does a generic T not automatically support every operator or comparison?

## Learning objectives

- A generic parameter separates reusable algorithm structure from concrete input types.

- Trait bounds declare the minimum operations a generic function is allowed to call.

- Prefer constraints derived from actual function requirements; a bound such as Clone should not be added without a cloning operation.

## Prerequisites

Review earlier ownership, borrowing and trait basics; use the Rust 1.95.0 / Edition 2024 course baseline.

## Scenario: Generics and trait bounds

The same selection algorithm must work for numeric priorities and text labels, yet the function body requires a specific ordering operation.

## Core concept 1: Abstraction contract

A generic parameter separates reusable algorithm structure from concrete input types.

## Core concept 2: Type and dispatch boundary

Trait bounds declare the minimum operations a generic function is allowed to call.

## Core concept 3: Verifiable behavior

Prefer constraints derived from actual function requirements; a bound such as Clone should not be added without a cloning operation.

## Code walkthrough

The original Rust examples are preserved. A snippet designed to fail compilation must be checked separately; behavior still requires tests.

### Example 1

```rust
/// Returns the greater value while accepting any ordered type.
fn greater<T: PartialOrd>(left: T, right: T) -> T {
    if left >= right { left } else { right }
}

/// Uses one generic function with two concrete types.
fn main() {
    assert_eq!(greater(7_i32, 4_i32), 7);
    assert_eq!(
        greater(String::from("cedar"), String::from("birch")),
        "cedar"
    );
}
```

### Example 2

```rust
/// Intentionally invalid: arbitrary T does not promise comparison.
fn invalid_greater<T>(left: T, right: T) -> T {
    if left >= right { left } else { right }
}
```

### Example 3

```rust
/// Clones and formats a value only when both capabilities are available.
fn cloned_label<T>(value: &T) -> String
where
    T: Clone + std::fmt::Display,
{
    format!("value={}", T::clone(value))
}

/// Checks the formatting result for two concrete types.
fn main() {
    assert_eq!(cloned_label(&12), "value=12");
    assert_eq!(cloned_label(&String::from("ready")), "value=ready");
}
```

## Java / Go comparison

Java generic bounds and Go type constraints express related capabilities but have different syntax and dispatch rules. Rust's generic operators are checked against trait bounds.

## Practice transfer: Add only the necessary bound

**Predict:** Does a function declared with <T> automatically support the > operator on T?

**Implement:** Extract a shared selection function, add its real comparison bound and test two concrete types.

**Counterexample and boundaries:** Pass a type lacking the required comparison trait and save the compiler error; avoid unrelated Clone bounds.

**Acceptance evidence:** Demonstrate valid results for two types and explain the compile-time contract.
