## Code walkthrough

The original Rust examples are preserved. A snippet designed to fail compilation must be checked separately; behavior still requires tests.

### Example 1

```rust
/// Returns the greater value while accepting any ordered type.
fn greater<T: PartialOrd>(left: T, right: T) -> T {
    if left >= right { left } else { right }
}

/// Uses one generic function with two concrete types.
fn main() {
    assert_eq!(greater(7_i32, 4_i32), 7);
    assert_eq!(
        greater(String::from("cedar"), String::from("birch")),
        "cedar"
    );
}
```

### Example 2

```rust
/// Intentionally invalid: arbitrary T does not promise comparison.
fn invalid_greater<T>(left: T, right: T) -> T {
    if left >= right { left } else { right }
}
```

### Example 3

```rust
/// Clones and formats a value only when both capabilities are available.
fn cloned_label<T>(value: &T) -> String
where
    T: Clone + std::fmt::Display,
{
    format!("value={}", T::clone(value))
}

/// Checks the formatting result for two concrete types.
fn main() {
    assert_eq!(cloned_label(&12), "value=12");
    assert_eq!(cloned_label(&String::from("ready")), "value=ready");
}
```

## Reason through a counterexample: Extract shared bounds

**Problem:** Different domain types need shared algorithms.

**Principle and deduction:** Generics reuse one algorithm across types, but an unconstrained T promises no operations. Trait bounds express the minimum required capabilities.

**Example and evidence:** Verify with the existing example or lab: Types without required traits fail compilation.

**Counterexample:** Using >= on an unconstrained T fails; demanding Clone when unused unnecessarily restricts callers.

**Independent exercise:** Remove the necessary PartialOrd bound, observe the compiler, then restore only needed bounds and test two distinct types.

**Review:** Derive the bounds from operations inside the function rather than copying a long trait list.
