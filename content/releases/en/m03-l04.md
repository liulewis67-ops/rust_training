# M03-L04: Modules, visibility and public APIs

> **Guiding question:** Should every field of a task object be pub just because another module needs one operation?

## Learning objectives

- Modules organize namespaces and paths; declarations are private unless visibility is explicitly granted.

- pub on an item does not automatically open every enclosing module or every private field.

- Expose a narrow stable operation instead of making internal representation part of the public contract.

## Scenario: Modules, visibility and public APIs

A consumer needs to mark a reminder as read. Publishing its internal status and attempts counters would permit invalid external combinations.

## Code walkthrough

### Example 1

```rust
/// Exposes task operations while keeping the state representation internal.
pub mod task_api {
    enum State {
        Open,
        Closed,
    }

    pub struct Task {
        pub id: u32,
        state: State,
    }

    impl Task {
        /// Creates an open task with the supplied identifier.
        pub fn new(id: u32) -> Self {
            Self {
                id,
                state: State::Open,
            }
        }

        /// Closes the task through the public interface.
        pub fn close(&mut self) {
            self.state = State::Closed;
        }

        /// Reports whether the task is closed.
        pub fn is_closed(&self) -> bool {
            matches!(self.state, State::Closed)
        }

        /// Reopens a task for an internal workflow.
        fn reopen(&mut self) {
            self.state = State::Open;
        }
    }
}

/// Uses only the task API exposed to sibling modules.
mod client {
    fn print_task() {
        let mut task = crate::task_api::Task::new(17);
        println!("{} {}", task.id, task.is_closed());
        task.close();
        println!("{} {}", task.id, task.is_closed());
    }

    /// Runs the client-side example.
    pub fn run() {
        print_task();
    }
}

/// Runs the module API example.
fn main() {
    client::run();
}
```

### Example 2

```rust
/// Exposes a small counter API without exposing its stored value.
pub mod counter {
    pub struct Counter {
        value: u16,
    }

    impl Counter {
        /// Creates a counter at the requested starting value.
        pub fn new(value: u16) -> Self {
            Self { value }
        }

        /// Reads the current value.
        pub fn value(&self) -> u16 {
            self.value
        }

        /// Advances the counter by one without exceeding u16::MAX.
        pub fn advance(&mut self) {
            if self.value < u16::MAX {
                self.value += 1;
            }
        }
    }
}

/// Uses the counter without reaching into its representation.
fn main() {
    let mut counter = counter::Counter::new(4);
    counter.advance();
    println!("{}", counter.value());
}
```

### Example 3

```rust
/// Exposes a task with one public state transition.
pub mod task_api {
    enum State {
        Open,
        Closed,
    }

    pub struct Task {
        state: State,
    }

    impl Task {
        /// Creates a closed task.
        pub fn new_closed() -> Self {
            Self {
                state: State::Closed,
            }
        }

        /// Reopens a task for an internal workflow only.
        fn reopen(&mut self) {
            self.state = State::Open;
        }
    }
}

/// Attempts an operation unavailable to outside callers.
mod client {
    pub fn reopen_task() {
        let mut task = crate::task_api::Task::new_closed();
        task.reopen();
    }
}

fn main() {
    client::reopen_task();
}
```

## Java / Go comparison

Java access modifiers and Go exported-name rules have distinct boundaries. Rust module visibility should be designed from the consumer's required behavior.

## Practice transfer: Keep internal representation private

**Predict:** If a caller needs mark_as_read, must it also mutate status and attempts directly?

**Implement:** Keep state fields private and export a minimal read/update API with its invariants.

**Counterexample and boundaries:** Reproduce a denied direct field access from another module instead of making everything pub.

**Acceptance evidence:** Show valid external behavior and the intentional visibility diagnostic.
