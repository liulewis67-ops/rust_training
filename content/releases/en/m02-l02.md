# M02-L02: Expressions, statements, functions and return values

> **Guiding question:** Why can one semicolon change a function's result type?


## Mechanism, boundary and independent exercise

A block evaluates to its final expression when no trailing semicolon discards that value. Function bodies follow the same rule; adding a semicolon can turn an i32 result into unit (). This is a type-contract issue, not a formatting preference.

**Deeper exercise:** Write an inner block returning i32, then add a trailing semicolon and predict the diagnostic. Create an if expression with one i32 arm and one () arm. Repair the mismatch and test both paths. Explain why deleting the declared return type is not an acceptable fix.

## The semicolon that changes a function result

An amount calculation looks right, yet Rust says an integer was expected and the unit type was found. The algorithm is not the culprit: a semicolon turned the final value-producing expression into a statement whose result is `()`.

Blocks and `if` branches can themselves yield values. Trace every branch of a function against its declared return type, and notice where an accidental semicolon changes the contract. Tail expressions are concise, but they still require deliberate reasoning about control flow.

## Code walkthrough

The examples below are retained from the validated source lesson. Some deliberately show compiler or business failures: test them in separate files, predict the failure first, and do not remove the failing behavior to make an assertion pass.

### Example 1

```rust
/// Multiplies a unit price by a quantity under the caller's bounds.
fn line_total(unit_price_cents: u32, quantity: u32) -> u32 {
    unit_price_cents * quantity
}

/// Prints the result of calling the calculation function.
fn main() {
    let amount = line_total(250, 3);
    println!("{amount}");
}
```

### Example 2

```rust
/// Returns a calculation produced by a block expression.
fn adjusted_count() -> i32 {

    imported - rejected
}
```

### Example 3

```rust

```

### Example 4

```rust
/// Returns the unchanged input through the function's tail expression.
fn identity(value: i32) -> i32 {
    value
}

/// Returns the input through an explicit return statement.
fn identity_explicit(value: i32) -> i32 {
    return value;
}
```

### Example 5

```rust
/// This intentionally fails because the semicolon discards the i32 value.
fn plus_one(value: i32) -> i32 {
    value + 1;
}
```

## Java / Go comparison

Java and Go commonly write explicit return statements. Rust also allows the final expression to determine a block's value, so punctuation has type consequences.

## Reason through a counterexample: Extract pure functions

**Problem:** Typed data still needs a testable function result.

**Principle and deduction:** A function signature sets an input/output contract, and a block's final expression supplies its value; a semicolon can change that value to unit ().

**Example and evidence:** Compare with the existing code or lab and verify: Semicolon and branch type errors are detected.

**Counterexample:** Removing the return annotation to hide E0308, or returning an integer on only one if arm, abandons the original calculation contract.

**Independent exercise:** Predict what happens when the tail expression receives a semicolon or one branch yields unit; test both paths of an order-total function.

**Review:** Check the type produced by every branch, not just whether the word return appears.
