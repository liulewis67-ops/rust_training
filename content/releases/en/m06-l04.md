## Static bounds do not make every value immortal

A background task accepts a `String`, and someone calls it “static data” because the API requires `T: 'static`. But `&'static str` describes a reference lifetime, while a `'static` type bound means the value does not rely on shorter-lived borrowed data.

An owned `String` may satisfy the bound and still be dropped normally when its owner ends. A reference into a request buffer cannot simply be promoted by writing a bound. Inspect what data is owned before choosing an async boundary.

## Learning objectives

- &'static str is a reference whose referent is valid for the required static lifetime.

- T: 'static means the type contains no shorter non-static references, not that its values cannot be dropped.

- An owned String can satisfy T: 'static while an arbitrary &String cannot be treated as &'static str.

## Java / Go comparison

Static fields in Java and package globals in Go do not correspond directly to Rust's lifetime trait bounds. Always distinguish referent validity from owned-value duration.

## Reason through a counterexample: Clarify static bounds

**Problem:** Long-term ownership does not imply a static reference.

**Principle and deduction:** &'static str is a reference valid for the entire program, while T: 'static means T holds no non-static borrowed dependencies; it does not imply T is immortal.

**Example and evidence:** Verify against the lesson's example or lab: Owned String can still be dropped normally.

**Counterexample:** Treating owned String as a &'static str, or leaking memory to silence a bound error, confuses type constraints with resource management.

**Independent exercise:** Compare a literal, a local String borrow, and owned String under a 'static bound; identify which may be moved into retained work.

**Review:** Distinguish borrow validity, type bounds and eventual Drop of an owned value.
