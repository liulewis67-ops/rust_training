    use super::checked_total;

    #[test]
    fn handles_zero_and_regular_values() {
        assert_eq!(checked_total(0, 0), Ok(0));
        assert_eq!(checked_total(17, 25), Ok(42));
        assert_eq!(checked_total(123, 456), Ok(579));
        assert_eq!(checked_total(456, 123), Ok(579));
    }

    #[test]
    fn handles_the_largest_valid_sum() {
        assert_eq!(checked_total(u32::MAX, 0), Ok(u32::MAX));
        assert_eq!(checked_total(u32::MAX - 1, 1), Ok(u32::MAX));
    }

    #[test]
    fn reports_overflow() {
        assert!(checked_total(u32::MAX, 1).is_err());
        assert!(checked_total(u32::MAX, 2).is_err());
    }
}

## Reason through a counterexample: Lock aggregate behavior

**Problem:** Repeated totals require explicit overflow semantics.

**Principle and deduction:** Accumulation adds an invariant: every intermediate sum must fit. checked_add identifies the step where representability fails.

**Example and evidence:** Compare with the existing code or lab and verify: MAX+0 and MAX+1 produce distinct outcomes.

**Counterexample:** Testing only small positive inputs misses overflow; silent truncation or wrapping would change the business contract.

**Independent exercise:** Cover empty, singleton, exactly-at-limit, and overflowing sequences; identify the first failing addition and expected return.

**Review:** Explain why checked_add satisfies the contract better than unchecked arithmetic.

## Reference implementation

Check the source solution only after working through the task.

```rust
pub fn checked_total(base: u32, adjustment: u32) -> Result<u32, &'static str> {
    base.checked_add(adjustment)
        .ok_or("total exceeds the u32 range")
}
```
