## When a newly created task cannot be found

A task can be successfully inserted according to its function signature yet disappear from later lookups. The compiler checks ownership and type relationships, not whether a domain item was stored under the right key.

Trace one observable path: creation input, ID assignment, storage location, lookup key, and state transition. Add assertions at each boundary rather than editing every CRUD method at once. The complete create–read–update–read story is stronger evidence than a single happy-path test.

## Reason through a counterexample: Integrate a task list

Correct types do not guarantee correct task-list behavior. An in-memory task list integrates structs, state enums, and missing-item queries; creation, update and lookup each preserve different invariants.

If an inserted task cannot be found, trace ID creation, storage keys, and lookup keys before rewriting every collection operation. A type-correct insertion can still violate the storage contract.

Checking only Vec length can miss corrupted IDs, incorrect states or unknown IDs treated as valid. Keep a create–read–update–read test sequence and an absent-ID case. If a single insertion works, probe multiple records and repeated identifiers before declaring the CRUD behavior correct.

Test the contract rather than a single happy path:Test creation, state changes, missing lookup and repeated operations in order; assert ID, state and Option results separately. Tie every assertion to a concrete API guarantee rather than program startup.

## Why a compiling task list can still lose its newly created task

The starter first exposes a type mismatch in state parsing. It prevents execution, but cannot explain a later lookup bug. Repair only the parser's declared return type in the first phase; then run the tests to reveal the behavioral defect that remained hidden behind compilation.

Follow one task through its lifecycle: what ID is allocated on creation, which `Vec<Task>` receives it, which key lookup uses, and whether an update targets the same record. Checking only collection length is insufficient. Even with the expected count, a lookup may return the wrong task or the wrong status. Two tasks with different titles help discriminate those cases.

Error precedence adds another contract. An unknown state string must yield `InvalidStatus` even when the requested task ID does not exist. A lookup-first implementation that immediately returns `TaskNotFound` is perfectly type-correct and still wrong. Pair an absent ID with `"blocked"` to expose that ordering defect.

The useful regression is a complete create–lookup–update–lookup story, plus a check that invalid updates leave existing tasks unchanged. The deliverable is not just CRUD methods: it is a defended set of identity, state, and error-precedence invariants.

## Reference implementation

Review after completing the task.

```rust
/// The supported lifecycle states for a task.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum TaskStatus {
    Todo,
    Doing,
    Done,
}

/// The outcome of requesting a task status change.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum UpdateOutcome {
    Updated,
    TaskNotFound,
    InvalidStatus,
}

/// A task whose fields are read through methods.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Task {
    id: u32,
    title: String,
    status: TaskStatus,
}

impl Task {
    /// Returns the stable identifier assigned by the list.
    pub fn id(&self) -> u32 { self.id }
    /// Returns the task title.
    pub fn title(&self) -> &str { &self.title }
    /// Returns the current lifecycle state.
    pub fn status(&self) -> TaskStatus { self.status }
}

/// An in-memory collection of tasks.
#[derive(Debug)]
pub struct TaskList {
    tasks: Vec<Task>,
    next_id: u32,
}

impl TaskList {
    /// Creates an empty list whose first task receives identifier 1.
    pub fn new() -> Self { Self { tasks: Vec::new(), next_id: 1 } }

    /// Adds a task and returns its assigned identifier.
    pub fn add_task(&mut self, title: &str) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        self.tasks.push(Task { id, title: String::from(title), status: TaskStatus::Todo });
        id
    }

    /// Looks up a task by identifier.
    pub fn get(&self, id: u32) -> Option<&Task> {
        self.tasks.iter().find(|task| task.id == id)
    }

    /// Parses and applies a status update, reporting invalid input or a missing task.
    pub fn set_status(&mut self, id: u32, status_text: &str) -> UpdateOutcome {
        let status = match parse_status(status_text) {
            Some(status) => status,
            None => return UpdateOutcome::InvalidStatus,
        };
        for task in &mut self.tasks {
            if task.id == id {
                task.status = status;
                return UpdateOutcome::Updated;
            }
        }
        UpdateOutcome::TaskNotFound
    }
}

fn parse_status(status_text: &str) -> Option<TaskStatus> {
    match status_text {
        "todo" => Some(TaskStatus::Todo),
        "doing" => Some(TaskStatus::Doing),
        "done" => Some(TaskStatus::Done),
        _ => None,
    }
}
```
