# M09-L02: Custom errors and source chains

> **Guiding question:** Why keep error category, input location, and underlying cause as structured data instead of one String?

## Why one error string makes diagnosis harder

An operations log says “invalid port on line 12.” If all failures are reduced to `String`, higher layers must parse changing text to distinguish overflow, missing configuration, or file I/O failures.

Structured error types preserve stable categories and useful context, while a source chain can retain underlying causes for controlled diagnostics. An absent file and an invalid file often require different remedies. A good error API lets callers make those decisions without scraping a human-readable message.

## Learning objectives

- Give callers stable, matchable error categories.
- Keep line numbers and field context without losing underlying parser errors.
- Implement `Debug`, `Display`, and `std::error::Error`.
- Return the original wrapped cause from `Error::source()` when a cause exists.

## Scenario: an invalid port on line 12

A service cannot start because one configuration port is malformed. An operator needs a field and line number; a developer needs the underlying `ParseIntError`. These are complementary responsibilities. A single formatted string cannot reliably preserve typed diagnosis.

**Predict:** Should a `MissingValue` error have a parser source? Can a formatted `ParseIntError` string still be downcast using `Error::source()`?

## Preserve categories and context in the error value

The example models `PortProblem::MissingValue` separately from `PortProblem::InvalidNumber(ParseIntError)`, then wraps it in `ConfigError { line, problem }`.

`Display` produces a stable, concise description such as `line 7: invalid port value`. `Error::source()` returns `Some(source)` for malformed digits but `None` for missing fields: the latter has no underlying parser failure.

Do not stringify the wrapped cause prematurely or duplicate it inside `Display` while also exposing it as a source: error reporters may otherwise repeat information.

~~~rust
use std::error::Error;
use std::fmt;
use std::num::ParseIntError;

/// Identifies the kind of problem found in a port field.
#[derive(Debug)]
enum PortProblem {
    /// The configuration line did not provide a port value.
    MissingValue,
    /// The provided value could not be parsed as a port number.
    InvalidNumber(ParseIntError),
}

/// Adds source location to a configuration parsing problem.
#[derive(Debug)]
struct ConfigError {
    /// Stores the one-based line number from the input.
    line: usize,
    /// Preserves the structured reason for the failure.
    problem: PortProblem,
}

/// Displays concise context without duplicating the wrapped parser message.
impl fmt::Display for ConfigError {
    /// Formats the location and stable category for a user-facing message.
    fn fmt(&self, formatter: &mut fmt::Formatter<'_>) -> fmt::Result {
        match &self.problem {
            PortProblem::MissingValue => {
                write!(formatter, "line {}: port value is missing", self.line)
            }
            PortProblem::InvalidNumber(_) => {
                write!(formatter, "line {}: invalid port value", self.line)
            }
        }
    }
}

/// Exposes a lower-level parse error for diagnostics and troubleshooting.
impl Error for ConfigError {
    /// Returns the parse error when one caused this configuration failure.
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        match &self.problem {
            PortProblem::MissingValue => None,
            PortProblem::InvalidNumber(source) => Some(source),
        }
    }
}

/// Parses an optional port field while retaining its input line.
fn parse_port_field(line: usize, raw: Option<&str>) -> Result<u16, ConfigError> {
    let Some(raw) = raw else {
        return Err(ConfigError {
            line,
            problem: PortProblem::MissingValue,
        });
    };
    let raw = raw.trim();
    if raw.is_empty() {
        return Err(ConfigError {
            line,
            problem: PortProblem::MissingValue,
        });
    }

    match raw.parse::<u16>() {
        Ok(port) => Ok(port),
        Err(source) => Err(ConfigError {
            line,
            problem: PortProblem::InvalidNumber(source),
        }),
    }
}

/// Checks success, a context-only error, and a nested parse failure.
fn main() {
    assert_eq!(parse_port_field(2, Some(" 8080 ")).unwrap(), 8080);

    let missing = parse_port_field(4, None).unwrap_err();
    assert_eq!(missing.line, 4);
    assert_eq!(missing.to_string(), "line 4: port value is missing");
    assert!(Error::source(&missing).is_none());

    let invalid = parse_port_field(7, Some("wide")).unwrap_err();
    assert_eq!(invalid.line, 7);
    assert_eq!(invalid.to_string(), "line 7: invalid port value");
    let source = Error::source(&invalid).expect("parser error should be preserved");
    assert!(source.downcast_ref::<ParseIntError>().is_some());
}
~~~

## Attach the input position at the correct layer

A numeric parser does not automatically know the original file line. Pass the location into the function that constructs the outer error, then preserve the original error object inside it.

In a multi-layer pipeline, each layer adds only context it actually knows. The illustrated chain describes the structure, not an exact stable `ParseIntError` display string; such diagnostic wording can vary between error cases or Rust versions.

~~~text
ConfigError: line 7: invalid port value
└── ParseIntError: invalid digit
~~~

## Types and presentation have different jobs

- The enum or error type supports reliable branching.
- `Display` summarizes what the current audience needs to know.
- `Debug` is a developer-oriented representation and is not a public protocol.
- `Error::source` links to a wrapped error object; use `None` if no underlying cause exists.
- Location belongs to the outer parsing context, while the lower-level parser supplies the actual cause.

This standard-library implementation deliberately avoids derive-macro dependencies.

## Java / Go comparison

Java's `Throwable.getCause()` and Go's `fmt.Errorf("%w", err)` / `errors.Unwrap` preserve a causal chain. Rust's `Error::source()` plays a similar role. Unlike parsing human messages, typed variants plus explicit location fields are suitable for dependable branching and testing.

## Reason through a counterexample: Preserve original causes

**Problem:** Callers need field/line context while diagnostics need the cause.

**Principle and deduction:** Custom errors encode categories; Display renders text and Error::source exposes the underlying cause. Attach line context where that location is known.

**Example and evidence:** Verify with this lesson's code or lab: Missing fields and parse errors have distinct causes.

**Counterexample:** A single concatenated string loses machine-readable categories, while discarding source hides the original failure.

**Independent exercise:** Parse an invalid port on line 12 and assert category, line, display text and source separately.

**Review:** Preserve both programmatic matching and human-readable diagnostics.

## Progressive hints

1. Model failure categories first, rather than matching the wording of `Display`.
2. Attach the line number where it becomes known.
3. Return a reference to the original cause from `source()`; never return the wrapper itself as its own cause.
4. Test the outer variant, location, stable message, source presence, and source type separately.
5. A missing field yields `None`; a failed integer parse yields the original parser error.

## Lesson summary

- Structured errors keep category, location, and cause distinct.
- `Display` is a human-facing summary; `source()` preserves diagnostic type information.
- A passing compilation is not a substitute for testing redaction or source-chain behavior.
