## The hidden boundary problem in a summation loop

A report must sum numbers from one through N. The first implementation looks plausible but fails for N=0 or N=1. Usually the issue is not loop syntax: the developer never specified whether the upper bound was inclusive or what zero iterations should produce.

A `for` loop suits a known range, `while` models state-driven repetition, and `loop` requires an explicit exit. Think about state ownership and termination first. Trace a few iterations by hand, then test an empty range, a single element, and exactly the upper boundary.

### Example 3

```rust
/// Counts down from the starting value to zero.
fn count_down(mut remaining: u32) -> u32 {
    let mut ticks = 0;
    while remaining > 0 {
        remaining -= 1;
        ticks += 1;
    }
    ticks
}
```

### Example 4

```rust
/// Sums the integers from one through four and returns the sum via break.
fn sum_until_four() -> u32 {
    let mut next = 1;
    let mut total = 0;
    loop {
        if next > 4 {
            break total;
        }
        total += next;
        next += 1;
    }
}
```

### Example 5

```rust
/// Sums a bounded inclusive integer range.
fn sum_one_to(limit: u32) -> u32 {
    let mut total = 0;
    for value in 1..=limit {
        total += value;
    }
    total
}

/// Prints a short inclusive sequence.
fn main() {
    for value in 1..=3 {
        println!("{value}");
    }
}
```

## Reason through a counterexample: Make control flow explicit

Calculations need iterations with precise bounds. if branches and loops model different control needs: for traverses ranges, while checks a condition, and loop requires an explicit exit.

The difference between `1..=n` and `1..n` becomes obvious with small values such as `n=1`. List the exact visited numbers before debating which loop syntax is more idiomatic.

Mistaking 0..n for an inclusive range causes off-by-one errors; a loop without a reachable break may never terminate. Test `n=0`, `n=1`, `n=2`, and a value near the chosen integer limit. For very large N, consider computational cost and sum overflow separately from whether the loop terminates.

To test the decision rather than memorizing a rule,Compare sums over 0..3 and 0..=3, then implement bounded retries with while and test a zero-retry edge case. State loop bounds and the maintained invariant instead of memorizing syntax alone.
