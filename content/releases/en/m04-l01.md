## Who closes a file when processing exits early

An upload handler opens a temporary file and allocates a buffer, then exits early on failure. Who is responsible for cleanup? Ownership and `Drop` connect ordinary resource release to the owner's scope, although fallible operations such as flushing or committing still need explicit handling.

Trace the lifetime of the file, buffer, and result across both normal and error paths. The important idea is not a slogan about scope, but a precise resource-flow story.

### Example 1

```rust
/// Owns a label that makes scope cleanup visible in the output.
struct ResourceLease {
    name: String,
}

impl ResourceLease {
    /// Creates a lease with an owned label.
    fn new(name: &str) -> Self {
        Self {
            name: String::from(name),
        }
    }
}

impl Drop for ResourceLease {
    fn drop(&mut self) {
        println!("drop {}", self.name);
    }
}

/// Shows when owners leave nested scopes.
fn main() {
    let room = ResourceLease::new("room");
    {
        let first = ResourceLease::new("first");
        let second = ResourceLease::new("second");
        println!("inner scope ends");
    }
    println!("outer scope continues");
    println!("main scope ends");
}
```

## Java / Go comparison

Java garbage collection and Go GC/finalizers are different from Rust's deterministic ownership-based cleanup. Do not treat Drop like an arbitrary GC callback.

## Reason through a counterexample: Trace resource lifetime

**Problem:** A task pipeline needs clear resource cleanup.

**Principle and deduction:** A binding, an owned value, and the resource it manages are different concepts. Scope exit triggers destruction according to Rust rules.

**Example and evidence:** Verify with the existing Rust example or lab: Moved resources are dropped exactly once.

**Counterexample:** Treating Drop::drop as an ordinary cleanup method is wrong; std::mem::drop consumes a value when early destruction is needed.

**Independent exercise:** Draw the drop order for three nested owners, add an explicit drop call, and verify the printed event trace.

**Review:** Distinguish a binding, its resource and a custom Drop callback without inventing fixed memory addresses.
