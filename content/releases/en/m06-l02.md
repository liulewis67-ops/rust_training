## Returning one of two inputs needs a source relationship

A configuration helper receives two `&str` inputs and returns whichever has priority. Humans see the result must borrow from an input, but the function signature needs to describe that relationship clearly enough for the compiler.

Lifetimes bound how the returned reference can be used relative to its sources. Elision rules handle common unambiguous cases; multiple candidate inputs often deserve explicit relationships. Shorten one input's scope in a thought experiment to see why the returned view cannot be treated as independently owned.

## Code walkthrough

### Example 1

```rust
/// Returns the borrowed text unchanged.
fn echo(text: &str) -> &str {
    text
}

/// Prints a slice borrowed from the caller's String.
fn main() {
    let message = String::from("queue ready");
    let result = echo(&message);
    println!("{result}");
}
```

### Example 2

```rust
fn echo_explicit<'text>(text: &'text str) -> &'text str {
    text
}
```

### Example 3

```rust
/// A borrowed message view owned by its caller.
struct MessageView<'text> {
    text: &'text str,
}

impl MessageView<'_> {
    /// Returns a slice borrowed through this receiver.
    fn text(&self) -> &str {
        self.text
    }
}
```

### Example 4

```rust
/// Ambiguous: the output might borrow from either input.
fn longer(left: &str, right: &str) -> &str {
    if left.len() >= right.len() {
        left
    } else {
        right
    }
}
```

### Example 5

```rust
/// Chooses a slice when both inputs share the required valid region.
fn longer<'text>(left: &'text str, right: &'text str) -> &'text str {
    if left.len() >= right.len() {
        left
    } else {
        right
    }
}
```

### Example 6

```rust
/// Still invalid: a named lifetime cannot keep this local String alive.

    let local = String::from("short-lived");
```

## Reason through a counterexample: Express borrow relationships

Two borrowed inputs make return provenance ambiguous. Elision works only when a returned borrow has a determined input source. When either of two inputs may be returned, the signature needs an explicit common validity relationship.

When a helper chooses between two configuration strings, the result may refer to either one. Without a relationship connecting the returned borrow to its possible sources, the caller cannot safely infer how long the result remains valid.

Inventing a 'longer' named lifetime cannot resurrect an already destroyed input; the constraint is about validity, not spelling. Give the inputs different enclosing scopes and attempt to use the result after the shorter-lived source ends. This demonstrates the constraint better than mechanically assigning matching lifetime letters. Then contrast a single-input function where elision suffices.

The distinguishing experiment is concrete:Start with fn longer(a: &str, b: &str) -> &str, predict the diagnostic, add the required relationship, and test a shorter-lived input scope. Separate naming a relation from creating or extending actual data.
