# M08-L01: Vec, HashMap and access strategies

> **Guiding question:** When should a task store preserve order, and when should it use unique-key lookup?


## Learning sequence for this module

**Goal: Build deterministic reports from events.** Work through four related design problems in order:

1. **Choose storage representation** — Events need both keyed lookup and ordered display. **Decision:** Choose Vec or HashMap from access requirements.
2. **Control callback captures** — Event callbacks may read, mutate, or consume state. **Decision:** Match Fn, FnMut, FnOnce to capture semantics.
3. **Choose iteration ownership** — Events may be read, edited in place, or consumed downstream. **Decision:** Distinguish iter, iter_mut, and into_iter.
4. **Compose lazy transforms** — map/filter adaptors do not execute on their own. **Decision:** Use collect/fold to drive real transformation and aggregation.

L05 integrates the tools into **Deterministic service summary**. L06 tests independent transfer through **Sensor report preserving all rows**. The examples are chosen per concept and do not have to form a single running project.

## Learning objectives

- Vec stores an ordered sequence and supports positional access; get returns Option instead of panicking on an invalid index.

- HashMap maps unique keys to values, and a repeated insert replaces the previous value; entry supports aggregation without silently overwriting.

- Choose data structures from access requirements and explicitly sort or maintain a sequence when deterministic output matters.

## Code walkthrough

The source Rust snippets below are unchanged; some intentionally fail compilation or behavioral assertions to demonstrate a rule.

### Example 1

~~~rust
/// Reads an optional item without consuming the vector.
fn read_item(items: &[String], index: usize) -> Option<&str> {
    items.get(index).map(String::as_str)
}

/// Checks empty and non-empty vector access.
fn main() {
    let empty: Vec<String> = Vec::new();
    assert_eq!(read_item(&empty, 0), None);

    let items = vec![String::from("oak"), String::from("pine")];
    assert_eq!(read_item(&items, 1), Some("pine"));
    assert_eq!(read_item(&items, 2), None);
    assert_eq!(items.len(), 2);
}
~~~

### Example 2

~~~rust
use std::collections::HashMap;

/// Looks up an account label by borrowed key.
fn label_for<'a>(labels: &'a HashMap<String, String>, key: &str) -> Option<&'a str> {
    labels.get(key).map(String::as_str)
}

/// Checks missing, present, and repeated-key behavior.
fn main() {
    let mut labels = HashMap::new();
    assert_eq!(labels.get("A-17"), None);

    assert_eq!(
        labels.insert(String::from("A-17"), String::from("queued")),
        None
    );
    assert_eq!(label_for(&labels, "A-17"), Some("queued"));
    assert_eq!(
        labels.insert(String::from("A-17"), String::from("running")),
        Some(String::from("queued"))
    );
    assert_eq!(label_for(&labels, "A-17"), Some("running"));
    assert_eq!(labels.len(), 1);
}
~~~

### Example 3

~~~rust
use std::collections::HashMap;

/// Counts each borrowed event label without copying the label strings.
fn count_events<'a>(events: &[&'a str]) -> HashMap<&'a str, usize> {
    let mut counts = HashMap::new();
    for event in events {
        *counts.entry(*event).or_insert(0) += 1;
    }
    counts
}

/// Verifies empty input, duplicate keys, and a Unicode key.
fn main() {
    assert!(count_events(&[]).is_empty());
    let counts = count_events(&["warn", "成功", "warn"]);
    assert_eq!(counts.get("warn"), Some(&2));
    assert_eq!(counts.get("成功"), Some(&1));
}
~~~

## Java / Go comparison

Java lists and maps, Go slices and maps, and Rust Vec/HashMap have distinct access and iteration semantics. Rust also makes borrowed lookup returns explicit.
