## A correct UTF-8 split does not make later mutation safe

A parser borrows two slices from a string and then wants to modify the original. The delimiter may define a valid UTF-8 boundary, yet a later use of either borrowed slice still conflicts with mutation.

Finish the work that needs those views before modifying the source, or create an explicitly owned copy if data must survive the change. Text-boundary correctness and borrow validity are separate contracts; a robust interface must satisfy both.

## Reason through a counterexample: Split Unicode safely

Delimiter positions and mutation test both UTF-8 and borrows. Safe text splitting must respect UTF-8 boundaries and exclusive mutation rules; valid slices remain borrowed from the source.

After splitting a string at a valid UTF-8 delimiter, later `push_str` mutation must not overlap with continued use of the borrowed slices. A legal text boundary does not imply a legal borrow schedule.

Cutting inside a multibyte character is invalid, and mutating the source while a borrowed slice is still live is also rejected. Compare printing the slices before modification with using them afterward. If the old text truly must survive mutation, return an owned result and account for its allocation rather than weakening the borrow contract.

## A string split must satisfy both UTF-8 boundaries and borrow timing

This independent check combines two constraints that are easy to conflate. `split_label` must return borrowed slices on either side of the first nonempty separator, and the caller later mutates the owning `String`. Finding valid byte boundaries solves the text problem; ensuring the old borrows are no longer used solves the ownership problem. Neither proof substitutes for the other.

For input `"部署：完成"`, the separator `"："` spans multiple UTF-8 bytes. Obtain its actual byte location from a search operation and advance past its byte length, rather than treating characters as one-byte positions. An absent or empty separator should return `None`, not two fabricated default slices.

The caller deliberately takes `kind` and `value`, runs `label.push('!')`, and only afterward tries to print the old borrowed slices. Finish using the slices before mutating their owner. If the old text genuinely must survive a later mutation, that is a separate reason to produce owned data. Annotating a longer lifetime or bypassing checks with `unsafe` does not repair the required sequence.

Test splitting separately with ASCII and Unicode separators, first versus later occurrences, and empty separators. Then test the call order. Record compiler and runtime evidence separately: an invalid UTF-8 boundary may cause a runtime panic, while overlapping borrows should be rejected at compile time.

## Reference implementation

```rust
pub fn split_label<'text>(
    text: &'text str,
    separator: &str,
) -> Option<(&'text str, &'text str)> {
    if separator.is_empty() {
        return None;
    }

    let start = text.find(separator)?;
    let end = start.checked_add(separator.len())?;
    Some((text.get(..start)?, text.get(end..)?))
}

fn main() {
    let mut label = String::from("部署：完成");
    let (kind, value) = split_label(&label, "：").unwrap();
    println!("parts: {kind} / {value}");
    label.push('!');
    println!("updated: {label}");
}
```
