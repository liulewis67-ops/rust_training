## Scenario

The same core serves a `history-report` command and `GET /profiles/{id}/history?retention_days=...`. Its `HistoryError` classifies three cases: invalid retention days, missing profile, and temporarily unavailable history storage.

The storage cause may include SQL text, database hostnames, internal paths, or credentials. Keep those details for appropriately controlled diagnostics, never in CLI `stderr` or remote API messages.

## Fixed presentation contract

The strings below are **exact contract values**; preserve punctuation and trailing newline exactly.

| Domain error | CLI `stderr` | Exit code | HTTP | API `code` | API `message` | `retryable` |
| --- | --- | ---: | ---: | --- | --- | --- |
| Invalid retention days | `error: retention-days must be an integer from 1 to 365\n` | 2 | 400 | `invalid_retention_days` | `retention_days must be an integer from 1 to 365.` | false |
| Profile not found | `error: profile was not found\n` | 3 | 404 | `profile_not_found` | `profile was not found.` | false |
| History storage unavailable | `error: history service is temporarily unavailable; try again later\n` | 1 | 503 | `history_unavailable` | `history service is temporarily unavailable; retry later.` | true |

The API mapping must preserve the supplied `request_id`. Every CLI failure has a nonzero exit code. Neither adapter may return success, echo raw invalid input, or disclose a storage source. The domain error must still retain the original cause for authorized diagnosis.

## Predict before implementing

**Predict:** For `retention_days=0`, which CLI exit code and HTTP status apply? For a transient storage outage, should the client retry? Should a database connection address ever appear in the public `message`?

## Staged acceptance

1. Test all three CLI error cases for exact `stderr` and nonzero exit code.
2. Test the HTTP status, stable `code`, `message`, and `retryable` together.
3. Verify `request_id` is unchanged after presentation.
4. Inject a fake internal error with SQL, hostnames, or secrets; assert that none appear in public output.
5. Verify the original storage cause is still accessible to controlled diagnostics.

**Java / Go comparison:** Think of Java domain failures mapped through `ControllerAdvice` or Go errors mapped by an HTTP handler. The Rust core should likewise remain independent of HTTP framework types and presentation details.

## Design notes to submit

1. Explain why CLI exit codes and HTTP statuses or error codes are not interchangeable.
2. State what is public, what belongs only in controlled logs, and how `request_id` correlates the two.
3. Explain why transient storage failure is retryable while invalid input and an absent profile are not automatically retryable.
4. Explain why runner/platform failure must never be mislabeled a learner's Rust implementation failure.

## Reference implementation

The full [M09 reference `src/lib.rs`](https://github.com/liulewis67-ops/rust_training/blob/main/content/samples/m09-reference/src/lib.rs) matches each `HistoryError` separately. For `StorageUnavailable`, the HTTP response uses status `503`, code `history_unavailable`, and `retryable=true`.

The shown match arm is only the HTTP portion. You must also keep the original `request_id`, the separate CLI exit-code mapping, and public redaction of any data reachable through `source()`.

```rust
HistoryError::StorageUnavailable(_) => (
    503,
    "history_unavailable",
    "history service is temporarily unavailable; retry later.",
    true,
),
```
