## Why a configurable strategy list needs a different kind of dispatch

A deployment service begins with one validation strategy, so a generic function works well. Then product requirements allow users to configure different strategies and their execution order. The new need is runtime heterogeneity, not merely reusing code for one compile-time type.

Static dispatch specializes concrete types; trait objects allow different implementations to share a runtime interface. Consider object compatibility, ownership of the collection, and whether configuration should change without recompilation. That architectural question matters more than an abstract argument about dispatch speed.

### Example 1

**Before reading this snippet:** Watch where the implementation type is known and where a trait object could erase that type. Predict which call site can be specialized for a concrete implementation.

```rust
/// Exposes one operation that can be called through a trait object.
trait Label {
    /// Returns a display label owned by the caller.
    fn label(&self) -> String;
}

/// Represents a queued item.
struct QueueItem {
    code: String,
}

/// Implements the label behavior for a queued item.
impl Label for QueueItem {
    fn label(&self) -> String {
        format!("queue:{}", self.code)
    }
}

/// Represents a completed import batch.
struct ImportBatch {
    accepted: u32,
}

/// Implements the same behavior for an import batch.
impl Label for ImportBatch {
    fn label(&self) -> String {
        format!("imported:{}", self.accepted)
    }
}
```


**After running or inspecting it:** Compare the heterogeneous collection and deliberately incompatible trait. Similar method-call syntax does not imply identical dispatch. A deliberate compilation failure is evidence, not something to delete.
### Example 2

```rust
/// Calls Label using a concrete type selected for this instantiation.
fn render_static<T: Label>(value: &T) -> String {
    value.label()
}

/// Renders two separate concrete types through generic instantiations.
fn main() {
    let item = QueueItem {
        code: String::from("Q17"),
    };
    let batch = ImportBatch { accepted: 4 };
    assert_eq!(render_static(&item), "queue:Q17");
    assert_eq!(render_static(&batch), "imported:4");
}
```

### Example 3

```rust
/// Calls Label through a trait object.
fn render_dynamic(value: &dyn Label) -> String {
    value.label()
}

/// Stores and calls values with different concrete types.
fn main() {
    let values: Vec<Box<dyn Label>> = vec![
        Box::new(QueueItem {
            code: String::from("Q17"),
        }),
        Box::new(ImportBatch { accepted: 4 }),
    ];
    let labels: Vec<String> = values
        .iter()
        .map(|value| render_dynamic(&**value))
        .collect();
    assert_eq!(labels, ["queue:Q17", "imported:4"]);
}
```

### Example 4

```rust
/// The native async method makes this trait dyn-incompatible.
trait AsyncLabel {
    /// Returns a future whose concrete type is hidden by async fn.
    async fn label(&self) -> String;
}

/// This trait-object use is intentionally rejected.
fn require_dynamic_async(_: &dyn AsyncLabel) {}
```

### Example 5

```rust
/// Keeps one method dynamically callable and one statically constrained.
trait Renderer {
    /// This method can be dispatched through dyn Renderer.
    fn render(&self) -> String;

    /// This generic helper is explicitly unavailable through the trait object.
    fn render_typed<T: std::fmt::Display>(&self, value: T) -> String
    where
        Self: Sized;
}
```

## Reason through a counterexample: Choose dispatch strategy

Runtime strategy lists may contain heterogeneous types. Generic code commonly uses static dispatch for concrete types; dyn Trait allows runtime dispatch through trait objects where the trait is dyn-compatible.

A generic `fn render<T: Formatter>` normally operates with a concrete type per call, while `Vec<Box<dyn Formatter>>` can hold heterogeneous strategies at runtime. Start with configuration and collection requirements before choosing a dispatch mechanism.

Not every trait can be made into dyn, and runtime dispatch alone is not proof of a meaningful performance problem. Attempt to turn a trait with an incompatible generic method into `dyn` and inspect E0038. Then place two implementations of a compatible trait into one vector. Runtime dispatch by itself does not establish a meaningful performance regression.
