# M09-L03: Library errors and application boundaries

> **Guiding question:** Why should domain code not decide both CLI exit codes and HTTP status codes?

## Engineering thread: Separate presentation boundaries

**Carry forward:** The previous lesson, M09-L02, produced "Located error type with source."

**Current obstacle:** The same domain failure maps differently for CLI and HTTP.

**Decision to make:** Keep CoreError in the library; map at CLI/HTTP edges.

**Deliverable:** Separate CLI/API error adapters. **Evidence:** 400/404/500 and controlled diagnostics meet the contract.

**Why it leads forward:** In M09-L04, the next constraint is: Expected input failure must not panic or expose secrets.

## Learning objectives

- Keep domain failure categories independent of CLI text and HTTP transport.
- Translate the same error into a command-line exit code and `stderr`.
- Independently translate domain errors into HTTP statuses and safe response bodies.
- Preserve internal diagnostic causes without exposing SQL, addresses, paths, or credentials to remote callers.

## Prerequisites and environment

Complete M09-L02 and understand error wrapping, matching, and borrowing. Use Rust 1.95.0 with Edition 2024 locally; no hosted grader is involved.

## Scenario: one business core serving CLI and HTTP

The profile core may report an invalid port, a missing profile, or unavailable storage. A terminal user needs an actionable diagnostic and exit status; a remote API client needs a suitable HTTP status and sanitized error object. Embedding both protocols inside the core couples otherwise reusable logic to two unrelated transports.

**Predict:** Should a missing profile return HTTP 404 or 500? Should raw SQL or a database address appear in the API error body?

## The library reports domain facts only

The core returns a structured `CoreError` enum. `InvalidPort` is bad input, `ProfileNotFound` is absence, and `Storage(io::Error)` retains a lower-level I/O cause. It does not import HTTP or process-exit machinery.

The code below shows how separate mapping functions can match those same variants without inspecting unstable `Display` strings. Keeping `source()` intact does not mean exposing its contents to an untrusted audience.

~~~rust
use std::error::Error;
use std::fmt;
use std::io;

/// Describes failures in the profile and port domain.
#[derive(Debug)]
enum CoreError {
    /// The supplied port value did not satisfy the domain rules.
    InvalidPort { line: usize },
    /// The requested profile does not exist.
    ProfileNotFound { name: String },
    /// Storage failed while the library was performing an operation.
    Storage(io::Error),
}

/// Adds storage errors to the library error vocabulary.
impl From<io::Error> for CoreError {
    /// Preserves the concrete I/O error for diagnostics.
    fn from(source: io::Error) -> Self {
        Self::Storage(source)
    }
}

/// Provides a concise library-level description.
impl fmt::Display for CoreError {
    /// Formats the domain context without choosing a CLI or HTTP presentation.
    fn fmt(&self, formatter: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Self::InvalidPort { line } => write!(formatter, "invalid port at line {line}"),
            Self::ProfileNotFound { name } => write!(formatter, "profile {name:?} not found"),
            Self::Storage(_) => write!(formatter, "storage operation failed"),
        }
    }
}

/// Exposes an underlying storage failure to trusted diagnostics.
impl Error for CoreError {
    /// Returns a source only when a lower-level storage error exists.
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        match self {
            Self::Storage(source) => Some(source),
            Self::InvalidPort { .. } | Self::ProfileNotFound { .. } => None,
        }
    }
}

/// Stores a local process exit code and stderr message.
#[derive(Debug, PartialEq, Eq)]
struct CliFailure {
    /// Uses the application-defined command-line exit contract.
    exit_code: i32,
    /// Contains the message intended for the local terminal.
    stderr: String,
}

/// Maps a library error to the CLI contract.
fn map_cli(error: &CoreError) -> CliFailure {
    match error {
        CoreError::InvalidPort { line } => CliFailure {
            exit_code: 2,
            stderr: format!("line {line}: invalid port; expected an unsigned 16-bit integer"),
        },
        CoreError::ProfileNotFound { name } => CliFailure {
            exit_code: 3,
            stderr: format!("profile {name:?} was not found"),
        },
        CoreError::Storage(source) => CliFailure {
            exit_code: 1,
            stderr: format!("storage failure: {source}"),
        },
    }
}

/// Stores a transport-neutral HTTP response projection.
#[derive(Debug, PartialEq, Eq)]
struct ApiFailure {
    /// Uses an HTTP status appropriate to the failure category.
    status: u16,
    /// Provides a stable machine-readable error code.
    code: &'static str,
    /// Provides a safe message for the remote client.
    message: &'static str,
}

/// Maps a library error to the API contract without leaking internals.
fn map_api(error: &CoreError) -> ApiFailure {
    match error {
        CoreError::InvalidPort { .. } => ApiFailure {
            status: 400,
            code: "invalid_port",
            message: "port must be an unsigned 16-bit integer",
        },
        CoreError::ProfileNotFound { .. } => ApiFailure {
            status: 404,
            code: "profile_not_found",
            message: "profile not found",
        },
        CoreError::Storage(_) => ApiFailure {
            status: 500,
            code: "internal_error",
            message: "internal server error",
        },
    }
}

/// Checks that the same domain errors map differently at each boundary.
fn main() {
    let invalid = CoreError::InvalidPort { line: 8 };
    assert_eq!(map_cli(&invalid).exit_code, 2);
    assert_eq!(map_api(&invalid).status, 400);

    let missing = CoreError::ProfileNotFound {
        name: String::from("daily"),
    };
    assert_eq!(map_cli(&missing).exit_code, 3);
    assert_eq!(map_api(&missing).status, 404);

    let storage = CoreError::from(io::Error::new(
        io::ErrorKind::PermissionDenied,
        "private filesystem detail",
    ));
    assert!(Error::source(&storage).is_some());
    assert_eq!(map_cli(&storage).exit_code, 1);
    assert!(map_cli(&storage).stderr.contains("private filesystem detail"));
    let api = map_api(&storage);
    assert_eq!(api.status, 500);
    assert_eq!(api.code, "internal_error");
    assert_eq!(api.message, "internal server error");
    assert!(!api.message.contains("private filesystem detail"));
}
~~~

## Translate the error separately at CLI and HTTP edges

In **this example's CLI contract**, invalid input maps to exit code `2`, missing profile to `3`, and storage failure to `1`. These codes are application-specific, not universal Rust command conventions. A local terminal may provide more diagnostic detail to an authorized operator, but secret-bearing information still requires a disclosure review.

The HTTP mapping uses `400` for invalid port, `404` for missing profile, and `500` for unexpected storage failure. Its stable public codes are `invalid_port`, `profile_not_found`, and `internal_error`. Do not include the storage source in a remote response.

RFC 9110 describes the HTTP status semantics; the chosen CLI exit codes belong only to this learning scenario.

## Mapping rules for a safe boundary

- **Domain:** Keep a precise failure category and optionally its original source.
- **CLI:** Produce the agreed nonzero exit code and appropriate `stderr` text.
- **HTTP:** Produce the right 4xx/5xx status plus a stable, safe public error code.
- **Diagnostics:** Preserve useful cause-chain and correlation metadata only in appropriately access-controlled logs.
- **Meaning:** Do not turn caller mistakes or missing resources into a generic 500 error.

## Java / Go comparison

In Spring, domain exceptions are commonly translated by a controller advice or handler boundary. Go HTTP handlers similarly translate domain errors into responses. Rust's `Result` and enum variants work well with the same separation. Database causes may be recorded under controlled access but should not be serialized straight to the network.

## Progressive hints

1. Ask whether the failing value describes a domain fact or a presentation protocol.
2. Distinguish a client-correctable parameter from a missing resource and an internal dependency failure.
3. Remember that terminal and remote audiences need different levels of disclosure.
4. Check that `Storage` still exposes `io::Error` through `source()` where authorized.
5. Match the `CoreError` variants, not their displayed text.

## Lesson summary

- Libraries expose stable domain errors, not HTTP or CLI transport details.
- Separate adapters implement their own exit and response contracts.
- Sensitive lower-level causes remain available to controlled diagnostics, not public error bodies.
