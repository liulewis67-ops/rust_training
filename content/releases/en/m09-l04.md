# M09-L04: Panic, recovery decisions, and safe error messages

> **Guiding question:** When is an ordinary failure a Result rather than a panic, and what can recovery guarantee?

## Learning objectives

- Separate expected input or dependency failures from broken program invariants.
- Return `Result` for normal errors instead of using `panic!` as a control-flow mechanism.
- Produce safe public messages while retaining controlled internal diagnostic categories.
- Understand `catch_unwind`, unwind versus abort, panic hooks, and the limits of recovery.

## Prerequisites and environment

Complete M09-L03. Work locally using Rust 1.95.0 / Edition 2024; panic and diagnostic experiments should not be treated as a hosted grader.

## Scenario: bad input versus a broken invariant

A caller enters malformed timeout text: it can reasonably fix the input and retry. An impossible internal state may mean an invariant has already been violated, and continuing could be unsafe.

**Predict:** Can `catch_unwind` intercept a `panic = "abort"` panic? If it catches an unwinding panic, have external side effects and shared-state invariants automatically been restored?

## Use Result for recoverable input errors

Invalid numeric input is an expected failure and should be returned as `Err`, not forced through `expect` or `unwrap`. The application can then provide a stable correction message.

In the example, `parse_limit` returns `Result<u16, RequestError>` and keeps the underlying parser source for diagnostics. The public message is selected from the error category and deliberately omits raw request text and private paths.

~~~rust
use std::error::Error;
use std::fmt;
use std::io;
use std::num::ParseIntError;

/// Preserves expected input errors and unexpected storage failures.
#[derive(Debug)]
enum RequestError {
    /// The request supplied a limit that cannot be parsed as u16.
    InvalidLimit(ParseIntError),
    /// The request could not be completed because storage failed.
    Storage(io::Error),
}

/// Formats an internal description without selecting a user channel.
impl fmt::Display for RequestError {
    /// Writes a concise category description.
    fn fmt(&self, formatter: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Self::InvalidLimit(_) => write!(formatter, "invalid limit"),
            Self::Storage(_) => write!(formatter, "storage operation failed"),
        }
    }
}

/// Exposes the lower-level failure to trusted diagnostic code.
impl Error for RequestError {
    /// Returns the original parser or storage cause.
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        match self {
            Self::InvalidLimit(source) => Some(source),
            Self::Storage(source) => Some(source),
        }
    }
}

/// Parses a user-provided limit and returns ordinary input errors.
fn parse_limit(raw: &str) -> Result<u16, RequestError> {
    let limit = raw.trim().parse::<u16>().map_err(RequestError::InvalidLimit)?;
    Ok(limit)
}

/// Chooses a stable message that is safe to show to a request user.
fn public_message(error: &RequestError) -> &'static str {
    match error {
        RequestError::InvalidLimit(_) => "limit must be an unsigned 16-bit integer",
        RequestError::Storage(_) => "request could not be completed",
    }
}

/// Gives each failure class a stable internal diagnostic category.
fn diagnostic_code(error: &RequestError) -> &'static str {
    match error {
        RequestError::InvalidLimit(_) => "invalid_limit",
        RequestError::Storage(_) => "storage_failure",
    }
}

/// Checks normal input failure, message separation, and an isolated panic boundary.
fn main() {
    let private_input = "not-a-number-secret";
    let invalid = parse_limit(private_input).unwrap_err();
    assert_eq!(public_message(&invalid), "limit must be an unsigned 16-bit integer");
    assert_eq!(diagnostic_code(&invalid), "invalid_limit");
    assert!(Error::source(&invalid).is_some());
    assert!(!public_message(&invalid).contains(private_input));

    let storage = RequestError::Storage(io::Error::new(
        io::ErrorKind::PermissionDenied,
        "private filesystem path",
    ));
    assert_eq!(public_message(&storage), "request could not be completed");
    assert_eq!(diagnostic_code(&storage), "storage_failure");
    assert!(Error::source(&storage).is_some());
    assert!(!public_message(&storage).contains("private filesystem path"));

    let isolated = std::panic::catch_unwind(|| {
        panic!("synthetic internal invariant failure");
    });
    assert!(isolated.is_err());
}
~~~

## Panic exposes a defect; it does not replace an error channel

A panic can stop execution when an internal assumption is violated. It is not a general-purpose replacement for `Result` on missing resources, invalid requests, or routine I/O errors.

`catch_unwind` can observe some unwinding panics if the closure meets its safety requirements. It **cannot** catch aborting panics. The panic hook runs before unwinding is caught. Catching a panic does not roll back I/O, revert transactions, or certify shared state as safe to reuse.

When unwinding, Rust drops values in unwound stack frames. With the abort strategy, the process terminates instead of unwinding. An isolation boundary must decide whether to discard compromised state or terminate, rather than promising automatic recovery.

## Keep public responses separate from diagnostics

- **Public message:** Brief, stable, actionable, and free of raw secrets.
- **Controlled diagnostics:** Error category, source chain, request ID, and essential location information with access limits.
- **Sensitive content:** Do not echo tokens, credentials, internal file paths, or whole unfiltered request bodies.
- **Panic hooks/backtraces:** Internal debugging aids, not a client-facing response format.
- **Recovery:** Ask whether the caller can correct an input, whether a dependency retry is bounded, or whether a violated invariant requires isolation.

## Java / Go comparison

Java exception handling and Go's `panic/recover` use their own stack and recovery rules. Rust's `Result` is designed for ordinary recoverable failures. `catch_unwind` is a constrained boundary, not transaction rollback, a generic try/catch, or guaranteed thread-state repair.

Replace an `expect`-based user-input parser with `Result<_, ParseIntError>`. Test valid, malformed, empty, and out-of-range text. Explain why `catch_unwind` is not the default request recovery mechanism.

**Acceptance:** Bad input never needs panic to express failure; public messages contain no secrets, and the distinction between unwind/abort and state consistency is explained.

## Progressive hints

1. Is the failure something a normal caller can correct, or a violated internal invariant?
2. Which layer can choose to retry, prompt the user, or stop the task?
3. Identify raw values, secrets, or paths in any proposed public error.
4. Check whether the panic strategy is unwind or abort, and what shared state remains valid.
5. Preserve classification and the lower-level source in controlled diagnostics while returning safe public output.

## Lesson summary

- Expected failures travel through `Result`.
- Catching an unwinding panic is not guaranteed state or transaction recovery.
- Separate public messaging from confidential diagnostic context.
