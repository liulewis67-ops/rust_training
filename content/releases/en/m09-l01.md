# M09-L01: Result, the ? operator, and error propagation

> **Guiding question:** At which function boundary should a failed numeric parse be handled?


## From a working data pipeline to diagnosable failures

This module uses a separate configuration-parsing example. Earlier lessons emphasized correct behavior for valid inputs; a value such as `timeout=abc` raises a new question: how should a function represent failure, and which layer should handle it?

This lesson uses `Result` and `?` to establish error flow. M09-L02 adds error context, L03 separates library and application responsibilities, and L04 distinguishes recoverable failures from panic. L05–L06 verify location-aware diagnostics and independent transfer. Together the modules close the loop on reproducible builds, data, ownership, interfaces, and errors.

## Learning objectives

- Read `Result<T, E>` as either `Ok(T)` or `Err(E)`.
- Decide whether to handle failure locally with `match` or propagate it.
- Explain how `?` unwraps success and returns early on failure.
- Describe the required conversion when the source and target error types differ.

## Scenario: parsing a timeout setting

An API or configuration file supplies a timeout as text. The low-level parser knows whether the string can be parsed; it usually does not know whether a failure should become a CLI diagnostic, HTTP response, or application retry.

**Predict:** If `"abc".parse::<u32>()?` returns an error, will statements following `?` execute? What if the enclosing function's error type differs from `ParseIntError`?

## Result explicitly represents both outcomes

A parsing function returns `Result<u32, ParseIntError>`, which forces the caller to choose a success or failure path. The example uses `panic!` only to expose a broken *test fixture*; normal invalid input should not become a panic.

**Try it:** Compare the `Ok(18)` and `Err(_)` branches. Neither result disappears unless the caller intentionally ignores it.

~~~rust
use std::num::ParseIntError;

/// Parses a count and preserves the standard integer parsing error.
fn parse_count(input: &str) -> Result<u32, ParseIntError> {
    input.trim().parse::<u32>()
}

/// Handles both successful and failed parsing results.
fn main() {
    match parse_count("18") {
        Ok(count) => assert_eq!(count, 18),
        Err(error) => panic!("valid fixture failed to parse: {error}"),
    }

    match parse_count("many") {
        Ok(count) => panic!("invalid fixture unexpectedly parsed as {count}"),
        Err(error) => assert!(!error.to_string().is_empty()),
    }
}
~~~

## Propagate with ? rather than hiding a failure

Within a function returning a compatible `Result`, `?` extracts the `Ok` value. On `Err`, it immediately returns from **that function**, not from the entire application.

`scale_count("seven")` leaves its remaining arithmetic unexecuted. The caller still receives `Err`; `?` does not log, retry, substitute zero, or transform failure into success.

~~~rust
use std::num::ParseIntError;

/// Parses a count and scales it, forwarding parse failures to the caller.
fn scale_count(input: &str) -> Result<u32, ParseIntError> {
    let count = input.trim().parse::<u32>()?;
    Ok(count * 3)
}

/// Checks the success value and confirms invalid text remains an error.
fn main() {
    assert_eq!(scale_count("7"), Ok(21));
    assert!(matches!(scale_count("seven"), Err(_)));
}
~~~

## The destination error type controls conversion

A function returning `Result<U, E_target>` can propagate `Result<T, E_source>` with `?` when `E_source` can be converted to `E_target`, commonly via `From<E_source> for E_target`. The example distinguishes an empty value from a malformed integer.

If conversion is unavailable, make an explicit `map_err` mapping or redesign the error type. Do not apply `.ok()`, `unwrap_or`, or fabricated defaults to conceal failures.

**Check:** `InputError::InvalidNumber` retains the underlying `ParseIntError`; `InputError::Empty` remains a distinct branch.

~~~rust
use std::num::ParseIntError;

/// Distinguishes blank input from malformed integer text.
#[derive(Debug)]
enum InputError {
    /// The caller supplied no count text.
    Empty,
    /// Standard integer parsing rejected the supplied text.
    InvalidNumber(ParseIntError),
}

/// Converts the standard parser error into this function's error type.
impl From<ParseIntError> for InputError {
    /// Preserves the original parse error inside the domain variant.
    fn from(error: ParseIntError) -> Self {
        Self::InvalidNumber(error)
    }
}

/// Parses a non-empty count and propagates conversion failures.
fn parse_nonempty_count(input: &str) -> Result<u32, InputError> {
    let input = input.trim();
    if input.is_empty() {
        return Err(InputError::Empty);
    }

    let count = input.parse::<u32>()?;
    Ok(count)
}

/// Checks success, blank input, and converted parse failure separately.
fn main() {
    assert!(matches!(parse_nonempty_count("9"), Ok(9)));
    assert!(matches!(parse_nonempty_count("  "), Err(InputError::Empty)));
    match parse_nonempty_count("nine") {
        Err(InputError::InvalidNumber(error)) => {
            assert!(!error.to_string().is_empty());
        }
        other => panic!("expected converted parse error, got {other:?}"),
    }
}
~~~

## When to choose match or ?

- Use `match` or `if let` when this layer has enough context to recover, choose a fallback, or present a particular message.
- Use `?` when the layer cannot reasonably recover and its caller can handle the error.
- The outermost CLI or HTTP boundary still needs an observable failure response.
- Propagation is a transfer of responsibility, not an implicit recovery strategy.

## Java / Go comparison

Java exceptions and Go's `(value, err)` convention also carry failures across calls. Rust makes the possible error part of `Result<T, E>`; `?` returns from the containing function, performing only the required conversion. Application boundaries should decide how errors become messages and statuses.

## Check your understanding and local practice

**Predict → compile → test:** Try `"4"`, `"bad"`, and a decimal string too large for `u32`. Identify the `Ok`/`Err` result and the exact function exited by `?`. Deliberately use an incompatible result error type to inspect the compiler message, then fix it with `From` or `map_err`.

**Acceptance:** Invalid user input remains an error rather than a panic; you can identify which layer finally interprets and reports it.

## Progressive hints

1. Determine the value and error types inside both `Ok` and `Err`.
2. Find the function in which `?` appears, and inspect that function's declared return type.
3. If the error types differ, identify the necessary `From` conversion or explicit `map_err`.
4. Keep empty input and malformed input distinguishable.
5. Assert both successful computation and the still-visible `Err` at the caller.

## Lesson summary

- `Result` preserves success and error as typed outcomes.
- `?` returns early from the function where it is used, subject to type conversion.
- Handle predictable user failures with `Result`, and decide how to display them only at an informed boundary.
