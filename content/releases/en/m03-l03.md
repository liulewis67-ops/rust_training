# M03-L03: Option and missing values

> **Guiding question:** Why is an empty string a poor substitute for a missing task?

## Engineering thread: Handle missing lookups

**Carry forward:** The previous lesson, M03-L02, produced "Type-safe task state."

**Current obstacle:** A task may be absent even when an empty name is valid.

**Decision to make:** Use Option to distinguish present and missing data.

**Deliverable:** Lookup API with explicit absence. **Evidence:** None differs from Some(empty data).

**Why it leads forward:** In M03-L04, the next constraint is: Callers must not mutate arbitrary internal fields.

## Not found and empty are not the same result

A ticket lookup returns an empty `String` when nothing exists. Then a valid ticket with an empty title appears, and the API can no longer distinguish absence from successful retrieval.

`Option<T>` models presence and absence directly. It asks the caller to decide what to do with `Some(value)` or `None` rather than using `unwrap()` to turn an ordinary missing record into a panic. This distinction matters in caches, databases, and search APIs, where “nothing matched” is often a valid outcome.

## Learning objectives

- Option<T> has Some(value) and None and makes absence part of the return type.

- match or if let requires the caller to choose how to handle a missing value.

- unwrap is inappropriate when a normal input can produce None; prefer explicit handling or propagation.

## Code walkthrough

The following are the original authored Rust examples. Some intentionally fail compilation; keep those failures distinct from runnable snippets.

### Example 1

```rust
/// Looks up a display name for a small set of ticket codes.
fn ticket_title(code: u16) -> Option<&'static str> {
    match code {
        10 => Some("standard"),
        20 => Some("priority"),
        _ => None,
    }
}

/// Produces a message for either a found or missing ticket.
fn ticket_message(code: u16) -> &'static str {
    match ticket_title(code) {
        Some(title) => title,
        None => "not found",
    }
}

/// Prints one found result and one missing result.
fn main() {
    println!("{}", ticket_message(10));
    println!("{}", ticket_message(99));
}
```

### Example 2

```rust
/// Returns a short note only when the code has a note.
fn optional_note(code: u16) -> Option<&'static str> {
    match code {
        10 => Some("renewal available"),
        20 => Some("priority handling"),
        _ => None,
    }
}

/// Converts an optional note into an explicit display label.
fn note_label(code: u16) -> &'static str {
    match optional_note(code) {
        Some(note) => note,
        None => "no note",
    }
}
```

### Example 3

```rust
/// Searches titles before the demonstration panic path.
fn lookup_title(code: u16) -> Option<&'static str> {
    match code {
        10 => Some("standard"),
        20 => Some("priority"),
        _ => None,
    }
}

/// Panics when the ticket code has no matching title.
fn title_or_panic(code: u16) -> &'static str {
    lookup_title(code).unwrap()
}

/// Demonstrates the missing-query panic path.
fn main() {
    println!("{}", title_or_panic(99));
}
```

## Reason through a counterexample: Handle missing lookups

A task may be absent even when an empty name is valid. Option<T> represents absence in the type; an empty string, zero, and a missing value are not equivalent.

A valid ticket can have an empty title, so returning an empty string for missing records collapses two facts. `Option` separates presence from actual content and forces the caller to acknowledge the distinction.

Using "" as a missing-value sentinel misclassifies valid empty names; blindly unwrapping None turns ordinary absence into a panic. Test `Some(String::new())` against `None` instead of immediately using `unwrap_or_default()` to erase the difference again. A storage failure may justify `Result`, while an ordinary not-found lookup may not be an error.

Test the contract rather than a single happy path:Test a valid item with an empty name and an unknown ID, then handle Some and None explicitly. Verify that the return type distinguishes every business state that matters.
