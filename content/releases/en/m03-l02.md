# M03-L02: Enums and match

> **Guiding question:** How can the compiler help you handle every state of a task?


## Mechanism, boundary and independent exercise

Independent Boolean flags can express invalid combinations (running and finished at once). An enum restricts representable states to named variants, while exhaustive match makes additions visible at compile time.

**Deeper exercise:** Add Cancelled to the task state, observe the missing-match-arm diagnostic, then define its retry policy. Test an allowed and rejected state. Finally introduce a wildcard arm and explain how it can silently conceal future state-handling decisions.

## Move illegal states out of runtime conditionals

A background job can be queued, running, or finished. Encoding those states as strings invites typos; separate booleans can permit impossible combinations such as queued and completed at once.

An enum models the exclusive alternatives, while exhaustive `match` expressions force newly introduced states to be considered. The benefit is not shorter branching syntax. It is moving part of the domain contract into a place where changes become visible to the compiler and code reviewer.

## Code walkthrough

The following are the original authored Rust examples. Some intentionally fail compilation; keep those failures distinct from runnable snippets.

### Example 1

```rust
/// Represents the mutually exclusive states of a scheduled task.
enum TaskState {
    Queued,
    Running,
    Finished,
    Failed { attempts: u8 },
}

/// Returns a short action label for a task state.
fn action_for(state: TaskState) -> &'static str {
    match state {
        TaskState::Queued => "start",
        TaskState::Running => "wait",
        TaskState::Finished => "none",
        TaskState::Failed { attempts } => {
            if attempts < 3 {
                "retry"
            } else {
                "inspect"
            }
        }
    }
}

/// Prints one action for each kind of task state.
fn main() {
    println!("{}", action_for(TaskState::Queued));
    println!("{}", action_for(TaskState::Failed { attempts: 2 }));
}
```

### Example 2

```rust
/// Represents the possible delivery states.
enum DeliveryState {
    Waiting,
    Sent,
    Failed,
}

/// Reports whether a delivery has reached a terminal state.
fn is_terminal(state: DeliveryState) -> bool {
    match state {
        DeliveryState::Waiting => false,
        DeliveryState::Sent => true,
        DeliveryState::Failed => true,
    }
}

/// Prints whether the delivery is terminal.
fn main() {
    println!("{}", is_terminal(DeliveryState::Sent));
}
```

## Reason through a counterexample: Enumerate lifecycle

Independent booleans cannot express mutually exclusive task states. Enum variants define mutually exclusive states; exhaustive match makes a newly added state a visible review obligation.

Separate `queued`, `running`, and `finished` booleans can all become true together. An enum rules out that representation; exhaustive `match` statements make each modeled alternative visible to consumers.

Independent Boolean flags admit contradictions, while an unconditional wildcard arm can swallow newly added states. Add a `Cancelled` variant and recompile code that matches the enum. The compiler can point out missing arms, but only domain tests can decide whether a transition from finished to queued should be allowed.

Test the contract rather than a single happy path:Add Cancelled, predict the compiler response, assign actions to every state, and test all branches explicitly. Explain how the type model excludes invalid combinations, beyond merely compiling match.
