# M06-L01: Reference validity and lifetime relationships

> **Guiding question:** Can a lifetime annotation keep a local String alive after its owner has been dropped?

## A lifetime annotation cannot revive a temporary value

A request handler builds a local `String` and attempts to return a borrowed `&str` into it. Adding a lifetime parameter cannot make that local allocation survive the function.

A lifetime annotation describes relationships among references; it does not create ownership or extend an object's real existence. Return an owned `String` when the caller must keep newly produced text, or borrow when the result points into input the caller already owns.

## Learning objectives

- Borrowed references are valid only while the referenced storage remains alive.

- Returning a view into a local owned value would create a dangling reference and is rejected.

- Choose an owned return or borrow data the caller already owns if that is the actual contract.

## Reason through a counterexample: Reject dangling references

**Problem:** A zero-copy view cannot outlive its owner.

**Principle and deduction:** A reference is valid only while its referent remains alive for every use; lifetime annotations do not keep a local owner alive.

**Example and evidence:** Verify against the lesson's example or lab: Escaping a local reference is rejected.

**Counterexample:** Returning &str into a local String dangles; spelling the return type &'static str cannot give a local allocation static lifetime.

**Independent exercise:** Compare borrowing from caller-owned String with returning newly allocated String; attempt to destroy a source before the borrowed result's final use.

**Review:** Explain who must retain the source and when an owned return is preferable.
