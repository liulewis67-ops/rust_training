# M06-L01: Reference validity and lifetime relationships

> **Guiding question:** Can a lifetime annotation keep a local String alive after its owner has been dropped?


## Module concept map

The goal is **Match result lifetime to retention needs**. The concepts form an ordered explanation, not an unrelated collection:

1. **Reject dangling references** — A zero-copy view cannot outlive its owner. **Design decision:** Keep caller-owned data alive or return an owned value.
2. **Express borrow relationships** — Two borrowed inputs make return provenance ambiguous. **Design decision:** Specify necessary named lifetime relationships.
3. **Choose borrowed or owned results** — Immediate preview and queued work need different lifetimes. **Design decision:** Design view-style and owned-style results separately.
4. **Clarify static bounds** — Long-term ownership does not imply a static reference. **Design decision:** Distinguish T: 'static from &'static str.

L05 asks you to apply these concepts to **Two config result shapes**. L06 checks whether you can produce **Conditional-allocation normalizer** in a different scenario. Different examples are intentional; concept dependency is what connects the lessons.

## Learning objectives

- Borrowed references are valid only while the referenced storage remains alive.

- Returning a view into a local owned value would create a dangling reference and is rejected.

- Choose an owned return or borrow data the caller already owns if that is the actual contract.

## Scenario: Reference validity and lifetime relationships

A handler constructs a temporary String and tries to return a slice pointing into it. A longer annotation cannot make the data continue to exist.

## Core concept 1: Reference relationship

Borrowed references are valid only while the referenced storage remains alive.

## Core concept 2: Owner and return shape

Returning a view into a local owned value would create a dangling reference and is rejected.

## Core concept 3: Validation boundary

Choose an owned return or borrow data the caller already owns if that is the actual contract.

## Code walkthrough

Preserved Rust source examples include deliberate compile-time failures. Test each separately, identify the true owner and do not try to fix dangling data with an arbitrary lifetime name.

### Example 1

```rust
/// Borrows a String while its owner remains in scope.
fn main() {
    let notice = String::from("ready");
    let view = &notice;
    println!("notice: {view}");
    println!("owner: {notice}");
}
```

### Example 3

```rust
/// Attempts to return a borrow of a local String.
fn dangling_notice() -> &String {
    let notice = String::from("temporary");
    &notice
}

fn main() {
    let view = dangling_notice();
    println!("{view}");
}
```

### Example 4

```rust
/// Transfers an owned notice to the caller.
fn make_notice() -> String {
    String::from("temporary")
}

fn main() {
    let notice = make_notice();
    let view = &notice;
    println!("{view}");
}
```

### Example 5

```rust
/// Reads a borrowed view before its owner leaves the inner scope.
fn main() {
    {
        let notice = String::from("staged");
        let view = &notice;
        println!("view: {view}");
    }
    println!("inner owner has been dropped");
}
```

## Java / Go comparison

Java and Go manage object lifetime differently. Rust's references cannot outlive their owners; a named lifetime expresses constraints rather than extending runtime storage.
