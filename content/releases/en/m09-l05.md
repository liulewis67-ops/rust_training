## Lab objectives

Build a strict service configuration parser that reports **kind, field, line, and column** without preserving untrusted raw values in public error messages.

You will validate duplicate fields, missing values, invalid numbers, unexpected keys, and EOF; reason about Unicode scalar-value columns; and distinguish compilation failures from deliberately failing business assertions.

## Input and output contract

Input consists of UTF-8 lines in the form `key=value`. Fields may appear in either order, and blank lines are ignored. The **only two required keys** must appear **exactly once**:

| Field | Required type | Valid example |
| --- | --- | --- |
| `timeout_ms` | decimal `u64` | `timeout_ms=250` |
| `retry_limit` | decimal `u8` | `retry_limit=3` |

Do not permit whitespace around keys or values, comments, unknown fields, or repeated fields. Numeric text must consist only of ASCII digits `0`–`9`; empty text, non-digits, and numeric overflow produce `InvalidValue`. Support LF and CRLF line endings.

On success return `Config { timeout_ms, retry_limit }`. On failure return a structured `ConfigError` without copying raw input values or unknown secret keys into its display:

- Line and column numbers are **1-based**; columns count Unicode scalar values (Rust `char`), not UTF-8 bytes.
- If `=` is absent, report the expected delimiter position just after the end of the line.
- Unknown and duplicate keys point to the first column of the key; the duplicate error identifies the known field.
- Invalid or empty values point immediately after `=`.
- A missing required field points to column 1 of the line after the end of the input. Empty input means line 1, column 1.

## Predict Unicode error columns

For the invalid line `"变更timeout_ms"`, the UTF-8 byte length differs from `chars().count()`. The expected delimiter column is **Unicode scalar count + 1**, not byte length + 1.

**Predict:** Is `retry_limit=256` accepted? What happens on `timeout_ms=20\ntimeout_ms=30`? Where should the missing-field error be located for empty input?

## Advanced public-test acceptance

**Java / Go comparison:** Rust `str::len()` and Go `len(string)` count UTF-8 bytes, while Java `String.length()` counts UTF-16 code units. This exercise explicitly defines user-facing columns in Rust `char` units instead of relying on a language's default length.

## Progressive hints

1. Iterate lines with `str::lines()` and use `split_once('=')` for each nonempty line.
2. Let integer parsers validate range while your explicit ASCII-digit check enforces lexical format.
3. Use `chars().count()` for user-facing columns; `len()` counts bytes.
4. Check whether an `Option` already contains a field value *before* storing the next one.
5. After parsing, verify both mandatory fields and report the defined EOF position.

The critical fix is to detect an already-seen field **before** writing its replacement. Do not bypass the check, return a fabricated default `Config`, or delete Unicode and error-location assertions.

```rust
if duplicate {
    return Err(config_error(ConfigErrorKind::DuplicateField, field, line_no, 1));
}
```

## Reason through a counterexample: Deliver strict config parser

**Problem:** Duplicate keys and UTF-8 column counting break diagnostics.

**Principle and deduction:** A strict config parser needs a stated line/column convention; byte offsets and Unicode character columns are different. Duplicate keys require a deterministic policy.

**Example and evidence:** Verify with this lesson's code or lab: L05 failing test turns green without leaking input.

**Counterexample:** Mixing byte and character columns reports misleading locations; silently overwriting duplicate fields can hide invalid configuration.

**Independent exercise:** Test duplicate keys, bad numbers, Unicode prefixes and empty input, asserting ConfigError category, location and cause.

**Review:** Treat error location and category as part of the API contract, not incidental text.
