# M06-L05: Lab: borrowed configuration view and owned configuration

> **Guiding question:** Can one parsed configuration support both zero-copy preview and independent queue storage?

## Engineering thread: Repair config views

**Carry forward:** The previous lesson, M06-L04, produced "Retention strategy without leaks."

**Current obstacle:** Parsed configuration must serve both views and queues.

**Decision to make:** Share parsing rules but separate borrowed/owned outputs.

**Deliverable:** Two config result shapes. **Evidence:** Both interfaces pass lifetime-specific tests.

**Why it leads forward:** In M06-L06, the next constraint is: Cloning every string wastes allocation on borrowed paths.

## One parse, two different ownership products

A parser supports both immediate configuration preview and long-term background processing. Forcing owned strings everywhere may add needless allocation; forcing a queued task to retain request-buffer slices creates an invalid lifetime dependency.

Build a borrowed view for local reading and validation, then convert to an owned representation only when the result needs an independent lifetime. Test that the owned result survives the original buffer's end. Make the ownership conversion an explicit API step.

## Learning objectives

- Borrowed views depend on the input lifetime and can be efficient for immediate checks.

- Queue-ready owned results need owned String fields, not borrowed slices from temporary input.

- Both APIs should share parsing rules but differ in storage ownership, tested across boundary inputs.

## Reference implementation

Review after your own attempt.

**Before reading this snippet:** This reference deliberately offers both a borrowed view and an owned result. Identify which fields still point into the input buffer and which result survives after that buffer is gone.

```rust
pub fn parse_view(line: &str) -> Option<ConfigView<'_>> {
    let (key, value) = line.split_once('=')?;
    Some(ConfigView { key, value })
}

pub fn parse_owned(line: &str) -> Option<Config> {
    let (key, value) = line.split_once('=')?;
    Some(Config { key: key.to_owned(), value: value.to_owned() })
}

pub fn queued_config() -> Config {
    let line = String::from("MODE=cache");
    parse_owned(&line).expect("the sample line contains '='")
}
```


**After running or inspecting it:** The two paths can produce equivalent text while having different retention contracts. Attempting to queue the borrowed view exposes the lifetime limitation; converting to owned data at the enqueue boundary expresses the real requirement.
