## The first rejection in a deployment pipeline matters

A deployment flow runs environment, approval, and release-window gates. Users care about execution order and the first rejection reason, not about how many strategy objects are constructed.

A heterogeneous runtime collection points toward trait objects, but the pipeline also needs deterministic ordering and short-circuiting. Continuing to invoke side-effectful gates after an early rejection can cause real damage. Verify calls, order, returned reason, and the absence of further execution. Explain dispatch choice and control-flow contract separately.

## Reason through a counterexample: Execute gate chain

Multiple strategies must execute in order and short-circuit. A runtime gate chain composes ordered trait objects; short-circuiting stops after the first rejection.

A deployment gate list must hold heterogeneous strategies at runtime and also stop at the first rejection in configuration order. A trait object addresses the storage problem, not the control-flow rule.

An unordered collection or continuing side-effecting gates after rejection violates the chain's public contract. Instrument three gates, make the second reject, and assert that the third is never called and the returned reason came from the second. Checking only the final Boolean result could miss an incorrect execution order.

Make the abstraction pay for itself with a discriminating test:Create three gates that record calls and assert execution order for all-pass, first-reject and middle-reject cases. Explain separately the need for dynamic dispatch, deterministic ordering and early exit.

## Reference implementation

Review only after attempting the contract.

```rust
impl Gate for MinimumNumber {
    fn evaluate(&self, build: &Build) -> Result<(), String> {
        if build.number >= self.0 {
            Ok(())
        } else {
            Err(format!("build {} is below minimum {}", build.number, self.0))
        }
    }
}

impl Gate for ChannelIs {
    fn evaluate(&self, build: &Build) -> Result<(), String> {
        if build.channel == self.0 {
            Ok(())
        } else {
            Err(format!("channel {} does not match {}", build.channel, self.0))
        }
    }
}

fn evaluate_pipeline(gates: &[Box<dyn Gate>], build: &Build) -> Result<(), String> {
    for gate in gates {
        gate.evaluate(build)?;
    }
    Ok(())
}
```
