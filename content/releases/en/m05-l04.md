## Why a Vec cannot always be read and extended simultaneously

A task panel holds a reference into a `Vec` and then calls `push`. Appending may relocate the backing storage; continuing to use an old element reference would be unsafe.

The design alternatives depend on the real requirement: copy a small field before mutation, rearrange read/write order, or keep a stable item ID rather than a long-lived internal address. Cloning the entire vector is not the universal answer. Ask what information truly must survive the mutation.

### Example 2

~~~rust
/// Reads an existing title before appending a new one.
fn main() {
    let mut titles = vec![String::from("draft")];
    {
        let first = &titles[0];
        println!("original: {first}");
    }
    titles.push(String::from("published"));
    println!("count: {}", titles.len());
}
~~~

### Example 3

~~~rust
/// Appends a title and reports a copied summary of the previous first title.
fn append_and_measure(titles: &mut Vec<String>, next: String) -> (usize, usize) {
    let previous_bytes = {
        let first = &titles[0];
        first.len()
    };
    titles.push(next);
    (previous_bytes, titles.len())
}

/// Uses the summary and the updated vector after the call.
fn main() {
    let mut titles = vec![String::from("draft")];
    let (previous_bytes, count) = append_and_measure(&mut titles, String::from("published"));
    println!("previous bytes: {previous_bytes}; count: {count}");
    println!("new item: {}", titles[1]);
}
~~~

## Reason through a counterexample: Design narrow APIs

**Problem:** Borrowing an element and its container mutably blocks the caller.

**Principle and deduction:** Borrow conflicts often reveal APIs that keep an element view alive while the caller also needs mutable container access.

**Example and evidence:** Check the original code or lab: Both the E0502 failure and valid alternatives are tested.

**Counterexample:** Retaining a Vec/HashMap element reference while mutating the whole container cannot be justified by the borrow rules.

**Independent exercise:** Design a read-summary-then-mutate API and compare it with one that retains an element reference across mutation.

**Review:** Review whether the API naturally separates reading from mutation, rather than adding arbitrary scopes.
