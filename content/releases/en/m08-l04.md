## A map pipeline is not always executing yet

A developer adds logging inside an iterator's `map` closure but sees no output. The transformation has been described, not necessarily consumed. Iterator adapters are generally lazy until something drives them.

Use `filter` to select, `map` to transform, `fold` to accumulate, and `collect` to materialize a result. Trace both types and consumption points. If the goal is a side effect rather than a value transformation, a simple loop may express the intent more clearly.

## Learning objectives

## Code walkthrough

The source Rust snippets below are unchanged; some intentionally fail compilation or behavioral assertions to demonstrate a rule.

### Example 1

~~~rust
/// Keeps non-negative values and scales each selected value.
fn select_scaled(values: &[i32]) -> Vec<i32> {
    values
        .iter()
        .filter(|&&value| value >= 0)
        .map(|&value| value * 10)
        .collect()
}

/// Checks filtering, mapping, empty input, and source reuse.
fn main() {
    let values = vec![-2, 0, 3];
    assert_eq!(select_scaled(&values), vec![0, 30]);
    assert_eq!(select_scaled(&[]), Vec::<i32>::new());
    assert_eq!(values, vec![-2, 0, 3]);
}
~~~

### Example 2

~~~rust
/// Adds every value to an explicit running total.
fn total(values: &[i32]) -> i32 {
    values.iter().fold(0, |sum, value| sum + *value)
}

/// Checks non-empty and empty folds.
fn main() {
    assert_eq!(total(&[3, -1, 5]), 7);
    assert_eq!(total(&[]), 0);
}
~~~

### Example 3

~~~rust
/// Demonstrates that adapter work starts only when an iterator is consumed.
fn main() {
    let values = [2, 4, 6];
    let mut calls = 0;

    {
        let pending = values.iter().map(|value| {
            calls += 1;
            *value * 2
        });
        drop(pending);
    }
    assert_eq!(calls, 0);

    let doubled: Vec<i32> = values
        .iter()
        .map(|value| {
            calls += 1;
            *value * 2
        })
        .collect();
    assert_eq!(doubled, vec![4, 8, 12]);
    assert_eq!(calls, 3);
}
~~~

### Example 4

~~~rust
/// Intentionally wrong: map is created and discarded without being consumed.
fn main() {
    let values = [1, 2];
    let mut output = Vec::new();

    values.iter().map(|value| output.push(value * 2));
    assert_eq!(output, vec![2, 4]);
}
~~~

## Practice transfer: Prove an iterator is lazy

**Predict:** Will an unconsumed map closure increment a counter once for each input?

**Implement:** Combine filter, map and collect, then write a fold whose empty input result is explicit.

**Counterexample and boundaries:** Drop an unused map and show zero side effects; use for/for_each when the operation exists only for side effects.

**Acceptance evidence:** Test empty, all-negative and mixed collections and compare closure call counts before/after consumption.

## Reason through a counterexample: Compose lazy transforms

map/filter adaptors do not execute on their own. map and filter are lazy adapters; collect, fold and loops drive iteration. The fold seed also determines the empty-input result.

A `map` closure may not run until the iterator is consumed. Constructing a transformation without driving it does not mean the compiler ignored the code; it means the work is lazy.

Creating map solely for printing and never consuming it runs no print callbacks; the wrong fold seed changes empty-input semantics. Observe state before and after `collect`, then use `fold` for accumulation and `map` for value transformation. Test the consumption point and output instead of treating `map` as a convenient way to hide printing side effects.

The most useful tests separate these obligations:Count closure calls before and after collect, then compare folds over empty input with different initial accumulators. Distinguish transformation, filtering, consumption and side effects.
