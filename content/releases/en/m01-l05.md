# M01-L05: Lab: repair a failing project

> **Guiding question:** How should you fix a crate that first fails compilation, then tests?

## Engineering thread: Repair two failure layers

**Carry forward:** The previous lesson, M01-L04, produced "Minimal reviewable fix."

**Current obstacle:** A compiling program may still calculate an incorrect discount.

**Decision to make:** Repair the type error, then the business behavior.

**Deliverable:** Repaired project with passing tests. **Evidence:** Compilation and behavior tests pass independently.

**Why it leads forward:** In M01-L06, the next constraint is: The workflow must work without a prepared scaffold.

## A discount exercise has two different failure phases

A discount function may first fail to compile. Once that is repaired, a boundary-price example may reveal the wrong amount. Solving everything in one jump hides the crucial debugging distinction.

Keep a pristine starter. First explain and fix only the compiler failure. Then prepare normal, boundary, and invalid order values, and repair the behavioral assertions. A convincing handoff links the old implementation, its observed symptom, the smallest correction, and a regression test that rejects the original mistake.

## Learning objectives

- Capture the compiler error before editing

- Fix types without weakening the function contract

- Use failing public tests to locate business mistakes

## Reason through a counterexample: Repair two failure layers

A compiling program may still calculate an incorrect discount. The discount starter intentionally contains two phases of failure. First the program cannot compile; once that is repaired, its arithmetic result still violates the contract. Treating both as one bug loses the diagnostic trail.

This lab fixes a compilation defect and a behavior defect in sequence: until tests can run, business assertions cannot provide evidence. Repair the type or syntax constraint first, and only then run behavioral tests. A compiler rejection does not execute the discount calculation, so no runtime assertion can explain that initial failure.

Deleting a failing test or weakening its expected result makes the output green without repairing the contract. Submit the original diagnostic, the first runtime test results, and the final regression evidence. Copying the answer or removing a failing assertion may produce green output without demonstrating fault isolation.

Now make the hypothesis observable:Capture the initial compiler diagnostic, fix the type issue minimally, then test required behavior including a boundary input. The delivery note needs root causes, focused changes, and separate evidence for each defect.

## From the first red diagnostic to a real discount fix

The starter is not merely an algorithm exercise: it is a Cargo project with deliberate defects. First verify the extracted working directory and manifest, then run the unmodified `cargo check`. While compilation fails, the discount assertions have not had a chance to execute. Record the diagnostic's location and type constraint so the first repair has a precise explanation.

Once `cargo check` succeeds, `cargo test` may still be red. This is progress, not a contradiction: the investigation has moved from compiler constraints to the business calculation. For a boundary amount, derive the expected payable total from the specification before editing code. Trace the comparison, the arithmetic order, and the returned value rather than adjusting a constant until one test passes.

Two tempting shortcuts are to delete the failing assertion or hard-code the published examples. Either can produce misleading local success. Normal amounts, the exact threshold, and values on either side of it distinguish a general implementation from a lookup table or an off-by-one comparison.

The handoff should contain two separate pieces of evidence: the original compile error disappearing, and the originally failing business test passing under the same contract. Keep the original ZIP pristine so another developer can reproduce the whole causal sequence.

## Reference implementation

Read this only after attempting the lab and recording the initial failure.

```rust
pub fn discounted_total_cents(subtotal_cents: i64, discount_percent: u8) -> i64 {
    let percent = i64::from(discount_percent);
    let discount_cents = subtotal_cents * percent / 100;
    subtotal_cents - discount_cents
}
```
