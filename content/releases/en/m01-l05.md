# M01-L05: Lab: repair a failing project

> **Guiding question:** How should you fix a crate that first fails compilation, then tests?

## Engineering thread: Repair two failure layers

**Carry forward:** The previous lesson, M01-L04, produced "Minimal reviewable fix."

**Current obstacle:** A compiling program may still calculate an incorrect discount.

**Decision to make:** Repair the type error, then the business behavior.

**Deliverable:** Repaired project with passing tests. **Evidence:** Compilation and behavior tests pass independently.

**Why it leads forward:** In M01-L06, the next constraint is: The workflow must work without a prepared scaffold.

## A discount exercise has two different failure phases

A discount function may first fail to compile. Once that is repaired, a boundary-price example may reveal the wrong amount. Solving everything in one jump hides the crucial debugging distinction.

Keep a pristine starter. First explain and fix only the compiler failure. Then prepare normal, boundary, and invalid order values, and repair the behavioral assertions. A convincing handoff links the old implementation, its observed symptom, the smallest correction, and a regression test that rejects the original mistake.

## Learning objectives

- Capture the compiler error before editing

- Fix types without weakening the function contract

- Use failing public tests to locate business mistakes

## Prerequisites

Finish the preceding lesson and be able to run Cargo commands locally. Examples follow the Rust 1.95.0 / Edition 2024 course baseline.

## Scenario: Lab: repair a failing project

The downloadable starter implements discounted_total_cents using a u8 percentage and i64 amount. The initial type issue hides a subsequent business defect.

## First repair the type layer

Reproduce E0308 using the specified toolchain. Convert the percentage intentionally rather than assuming different integer types mix implicitly.

## Then repair the arithmetic

Percentages must be divided by 100. Keep the function signature and every public assertion unchanged.

## Reproduce the full repair

After cargo check succeeds, run cargo test, compare expected/actual values and finish with fmt, check and test.

## Reason through a counterexample: Repair two failure layers

**Problem:** A compiling program may still calculate an incorrect discount.

**Principle and deduction:** This lab fixes a compilation defect and a behavior defect in sequence: until tests can run, business assertions cannot provide evidence.

**Example and evidence:** Use the example or starter above to check: Compilation and behavior tests pass independently.

**Counterexample:** Deleting a failing test or weakening its expected result makes the output green without repairing the contract.

**Independent exercise:** Capture the initial compiler diagnostic, fix the type issue minimally, then test required behavior including a boundary input.

**Review:** The delivery note needs root causes, focused changes, and separate evidence for each defect.

## Practice transfer: Turn the initial failure into regression coverage

**Predict:** If ordinary discounts pass, could zero percent or the maximum contract amount still expose a bug?

**Implement:** Keep an untouched starter copy; repair compilation first, then test ordinary and boundary discount values.

**Counterexample and boundaries:** Never delete assertions, alter the public signature or replace expected outputs to force green results.

**Acceptance evidence:** Separate compiler-fix evidence from business-fix evidence; rerun from a fresh checkout.

## Reference implementation

Read this only after attempting the lab and recording the initial failure.

```rust
pub fn discounted_total_cents(subtotal_cents: i64, discount_percent: u8) -> i64 {
    let percent = i64::from(discount_percent);
    let discount_cents = subtotal_cents * percent / 100;
    subtotal_cents - discount_cents
}
```
