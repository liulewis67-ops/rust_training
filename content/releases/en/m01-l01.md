# M01-L01: Why Rust? Choosing with evidence

> **Guiding question:** When is Rust a sensible candidate for an existing Java, Go, or TypeScript team?

## Engineering thread: Define constraints

**Carry forward:** Start by testing whether Rust is justified for the engineering constraints.

**Current obstacle:** Choose a language based on constraints rather than fashion.

**Decision to make:** Document a falsifiable Rust prototype hypothesis.

**Deliverable:** Decision record with stop criteria. **Evidence:** Baseline and pilot measurements can be compared.

**Why it leads forward:** In M01-L02, the next constraint is: A pilot cannot be reviewed if its toolchain is unknown.

## Learning objectives

- Identify hard constraints before choosing a language

- Separate an engineering hypothesis from measured evidence

- Record a stop condition for a language migration

## Prerequisites

Comfort with basic programming, functions and a terminal.

## Scenario: Why Rust? Choosing with evidence

A long-lived log parser on memory-constrained hardware has different delivery pressures from a two-week internal registration form. Choose by constraints rather than language popularity.

## Core concept 1: Start with observable requirements

Peak memory, latency, compatibility, delivery deadline and staff skills are measurable constraints. A language feature is not itself a performance result.

## Core concept 2: Compare candidates fairly

Rust can rule out many memory-safety and data-race patterns in safe code; Java and Go offer mature runtimes and ecosystems. None guarantees correct business logic or good latency without measurement.

## Core concept 3: Use a bounded proof of concept

Evaluate a small replaceable component on representative hardware and data. Record correctness, resource use, build/deploy costs, maintenance and when to stop.

## Java / Go comparison

Java and Go may already meet a project's requirements with lower migration risk. Rust is compelling when ownership, predictable resources or systems integration materially matter—but benchmark the actual workload.

## Reason through a counterexample: Define constraints

**Problem:** Choose a language based on constraints rather than fashion.

**Principle and deduction:** A language decision is an experiment: turn input sizes, memory limits, and deployment constraints into measurable requirements before comparing implementations.

**Example and evidence:** Use the example or starter above to check: Baseline and pilot measurements can be compared.

**Counterexample:** A benchmark screenshot is not evidence if the algorithms or output contracts differ; the measured difference may have nothing to do with the language.

**Independent exercise:** Define shared correctness fixtures, peak memory and throughput measurements, and a stop condition for a Rust pilot. Explain what result would overturn the initial choice.

**Review:** Review the conditions under which Rust is justified rather than ranking languages in the abstract.

## Check your understanding

Before running anything, answer: When is Rust a sensible candidate for an existing Java, Go, or TypeScript team? Then explain which of the three concepts above determines your answer.

## Practice transfer: Evidence-based language proposal

**Predict:** A Java service has occasional latency spikes. Is replacing the entire service with Rust guaranteed to remove them?

**Implement:** Locate the bottleneck, propose a small Rust prototype, and compare the same inputs, functionality, deployment and maintenance constraints.

**Counterexample and boundaries:** Include a stop condition when the new version fails compatibility or cost targets.

**Acceptance evidence:** A one-page decision record with baseline, measurement method, rollback plan and explicit non-goals.

## Summary

- Start with observable requirements: Peak memory, latency, compatibility, delivery deadline and staff skills are measurable constraints.

- Compare candidates fairly: Rust can rule out many memory-safety and data-race patterns in safe code; Java and Go offer mature runtimes and ecosystems.

- Use a bounded proof of concept: Evaluate a small replaceable component on representative hardware and data.
