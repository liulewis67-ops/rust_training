## Code walkthrough

The source Rust snippets below are unchanged; some intentionally fail compilation or behavioral assertions to demonstrate a rule.

### Example 1

~~~rust
/// Calls a read-only label formatter twice.
fn preview_twice<F>(format_label: F) -> (String, String)
where
    F: Fn(&str) -> String,
{
    (format_label("prepare"), format_label("publish"))
}

/// Formats two labels by immutably capturing the site name.
fn main() {
    let site = String::from("north");
    let formatter = |action: &str| format!("{site}:{action}");
    assert_eq!(
        preview_twice(formatter),
        (String::from("north:prepare"), String::from("north:publish"))
    );
    assert_eq!(site, "north");
}
~~~

### Example 2

~~~rust
/// Calls a stateful callback twice and returns both results.
fn call_twice<F>(mut callback: F) -> (usize, usize)
where
    F: FnMut() -> usize,
{
    (callback(), callback())
}

/// Increments captured state through a mutable closure borrow.
fn main() {
    let mut attempts = 0;
    let mut next_attempt = || {
        attempts += 1;
        attempts
    };

    assert_eq!(call_twice(&mut next_attempt), (1, 2));
    assert_eq!(attempts, 2);
}
~~~

### Example 3

~~~rust
/// Runs one operation that may consume its captured state.
fn run_once<F, T>(operation: F) -> T
where
    F: FnOnce() -> T,
{
    operation()
}

/// Moves an owned message out of a closure exactly once.
fn main() {
    let message = String::from("release accepted");
    let take_message = move || message;
    let result = run_once(take_message);
    assert_eq!(result, "release accepted");
}
~~~

### Example 4

~~~rust
/// Reuses a move closure whose body only reads its owned capture.
fn call_twice<F>(callback: F) -> (usize, usize)
where
    F: Fn() -> usize,
{
    (callback(), callback())
}

/// Owns a label in a move closure while calling it repeatedly.
fn main() {
    let label = String::from("artifact");
    let length = move || label.len();
    assert_eq!(call_twice(length), (8, 8));
}
~~~

## Verified code and boundaries: How closure capture behavior determines Fn traits

`src/m08_closures.rs` shows that a `move` closure which only reads a captured String can still satisfy `Fn` and run twice, a counter-updating closure requires `FnMut`, and consuming a captured String fits `FnOnce`. `compile_fail/m08_fnmut_not_fn.rs` requires `Fn` for a mutating closure and should yield **E0525**. `move` alone does not imply a closure is callable only once.

## Reason through a counterexample: Control callback captures

**Problem:** Event callbacks may read, mutate, or consume state.

**Principle and deduction:** Closures capture by shared borrow, mutable borrow or ownership. Fn, FnMut and FnOnce describe callable capabilities, not a simple count of calls.

**Example and evidence:** Verify using the lesson's code or lab: Consuming and reusable closures are distinguished.

**Counterexample:** A closure that consumes a captured String cannot be promised as repeatedly callable Fn; a read-only closure need not be restricted to FnOnce.

**Independent exercise:** Write one read-only, one counter-updating, and one consuming closure; predict supported Fn-family bounds and repeatability.

**Review:** Derive the bound from what the closure does to captures, not merely the presence of move.
