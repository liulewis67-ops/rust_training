> **Guiding question:** When can a normalizer return the original input without allocating new text?

## Cow delays an ownership decision; it does not make copies disappear

A text normalizer often returns its input unchanged but occasionally needs to replace characters. Always building a `String` allocates unnecessarily; always returning `&str` cannot represent a newly produced string.

`Cow<'a, str>` can express both paths, but your rules still decide when to borrow and when to own. Test each branch, including ownership behavior, and explain why a changed result can survive independently of its source.

## Learning objectives

## Reason through a counterexample: Allocate only when necessary

Cloning every string wastes allocation on borrowed paths. Cow<'a, str> can borrow unchanged text and own transformed text; it does not promise allocation never occurs.

A normalizer returning `Cow::Borrowed` leaves unchanged text borrowed, while `Cow::Owned` carries an independent modified string. This is not magic that eliminates copying; it makes the ownership choice representable.

Calling into_owned() unconditionally forfeits conditional allocation, while returning the original slice after normalization gives the wrong content. Test already-normalized, changed, and empty input, checking both the text and the borrowed/owned variant where that distinction is part of the contract. Show that a newly owned result survives without its source buffer.

The distinguishing experiment is concrete:Test already-normalized, modified and empty inputs for Cow Borrowed/Owned variants and exact output. Reason about both the result contract and when allocation becomes necessary.

## Cow saves a copy only when the unchanged path actually borrows

Topic normalization has a small textual rule but a revealing ownership contract. If the input already begins with `#`, remove only the first marker and return a slice of the original text. Otherwise prepend `#`, requiring a newly owned string. `Cow<'input, str>` can represent both branches; it does not automatically select one for you.

Compare `"#news"` producing borrowed `"news"`, `"news"` producing owned `"#news"`, and empty input producing owned `"#"`. For `"##news"`, exactly one leading marker is removed. Pure string-equality assertions would miss a plausible wrong implementation that always calls `into_owned()` and thus destroys the promised no-allocation path.

A `Cow::Borrowed` result still depends on the input's lifetime; wrapping it in an enum does not grant independent retention. Only the `Owned` path has its own storage. Enqueuing an arbitrary borrowed result for later use would repeat the lifetime mistake explored by `ConfigView` in the previous lesson.

Acceptance needs two groups of assertions: textual output and the Borrowed/Owned variant with its data origin. Explain which input condition triggers an allocation before running the tests. That turns the claim of a potentially avoided copy into a meaningful API tradeoff supported by evidence.

## Reference implementation

Review after your own attempt.

```rust
use std::borrow::Cow;

pub fn normalize_topic<'input>(topic: &'input str) -> Cow<'input, str> {
    if let Some(suffix) = topic.strip_prefix('#') {
        Cow::Borrowed(suffix)
    } else {
        Cow::Owned(format!("#{topic}"))
    }
}

#[test]
fn normalize_topic_contract() {
    use std::borrow::Cow;

    assert!(matches!(normalize_topic("rust"), Cow::Owned(value) if value == "#rust"));
    let raw = String::from("#你好");
    let result = normalize_topic(&raw);
    assert!(matches!(&result, Cow::Borrowed(value) if *value == "你好"));
    let Cow::Borrowed(value) = &result else { panic!("expected a borrowed slice") };
    let start = raw.as_ptr() as usize;
    let end = start + raw.len();
    let part_start = value.as_ptr() as usize;
    assert!((start..=end).contains(&part_start));
    assert!(part_start + value.len() <= end);
    assert!(matches!(normalize_topic(""), Cow::Owned(value) if value == "#"));
    assert!(matches!(normalize_topic("##rust"), Cow::Borrowed("#rust")));
}
```
