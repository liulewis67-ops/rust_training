# M07-L04：From/TryFrom、newtype 与不变量

> **本节核心问题：** AccountId 和 ByteCount 都是 u64，为什么仍值得定义成不同类型？

## 学习目标

- 用 newtype 给基础类型增加领域含义，并通过私有字段防止调用方绕过约束。
- 仅在转换总能成功且不丢失领域信息时实现 `From`；可能失败的转换使用 `TryFrom` 和明确错误。
- 组合多个 fallible conversion，让构造流程在任一字段无效时返回原因，而不产生不完整领域对象。
- 评审 `as` 截断、饱和替代或 panic 转换，改为保留错误信息的安全 API。

## 先修与环境

完成 M07-L03，能读 trait impl、关联错误类型和泛型行为。本节只使用标准库 `From`、`TryFrom` 和本地错误枚举，不依赖外部 crate。newtype 是持有单个字段的 tuple struct，在类型系统中仍是区别于内部类型的新类型。

## 场景：防止把账户编号误当成重试次数

两个字段都用无符号整数保存，却代表不同的领域含义。若 API 只写 `u64`，调用方容易把参数传错。通过带私有字段的 newtype，可以将“这是什么值”和“怎样构造才合法”放进类型边界。

**先预测：** 如果业务编号必须大于 0，直接对任意 `u64` 实现无条件 `From<u64>` 是否仍能保证不变量？失败转换应该怎样表达？

## 核心知识点一：newtype 让领域含义进入类型系统

两个 `u64` 在机器表示上相同，但代码里可能一个是账户编号，一个是字节数。仅靠名字和注释很容易把它们传反。newtype 为值建立不同的静态类型：

```rust
/// Identifies one account in this domain.
#[derive(Debug, PartialEq, Eq)]
struct AccountId(u64);

/// Counts retries for a queue item.
#[derive(Debug, PartialEq, Eq)]
struct RetryCount(u8);
```

`AccountId` 与 `u64` 不能互换使用。内部字段保持私有后，模块外代码不能直接写 `RetryCount(255)`；只能通过模块公开的转换或构造 API 获得该类型。若把字段声明成 `pub`，就会重新开放绕过不变量的路径。

如果任意 `u64` 都是该程序可接受的账户编号，则数字到 `AccountId` 是无失败、无损的语义包装，可以实现 `From<u64>`：

```rust
/// Wraps any accepted numeric account identifier without changing it.
impl From<u64> for AccountId {
    /// Creates the domain type while preserving the original value.
    fn from(value: u64) -> Self {
        Self(value)
    }
}
```

实现 `From<T> for U` 会自动提供 `Into<U> for T`。标准库约定 `From` 不应失败；如果转换可能失败，不要在 `From` 实现里 panic、截断或静默改写数据来藏起错误。

## 核心知识点二：有约束的构造使用 TryFrom

假设队列重试次数只能在 `0..=5`，标签不能为空白。两种验证都可能失败，因此 newtype 的外部构造必须检查输入：

```rust
/// Describes the validation errors exposed by queue configuration.
#[derive(Debug, PartialEq, Eq)]
enum ConfigError {
    /// The label contains no non-whitespace characters.
    EmptyLabel,
    /// The retry count is outside the accepted range.
    RetryLimitExceeded(u8),
}

/// Stores a non-empty label after removing surrounding whitespace.
#[derive(Debug, PartialEq, Eq)]
struct Label(String);

/// Validates and normalizes a candidate label.
impl TryFrom<String> for Label {
    type Error = ConfigError;

    /// Rejects blank text and stores the trimmed form.
    fn try_from(value: String) -> Result<Self, Self::Error> {
        let trimmed = value.trim();
        if trimmed.is_empty() {
            return Err(ConfigError::EmptyLabel);
        }
        Ok(Self(trimmed.to_owned()))
    }
}

/// Validates the retry count before storing it as a domain value.
impl TryFrom<u8> for RetryCount {
    type Error = ConfigError;

    /// Accepts only values from zero through five inclusive.
    fn try_from(value: u8) -> Result<Self, Self::Error> {
        if value > 5 {
            return Err(ConfigError::RetryLimitExceeded(value));
        }
        Ok(Self(value))
    }
}
```

`TryFrom` 的关联类型 `Error` 说明失败会返回什么。调用 `Label::try_from` 或 `RetryCount::try_from` 得到 `Result`，调用者必须处理 `Err`。`From` 到 `TryFrom` 不是仅换一个函数名：前者表达总能完成，后者让失败成为 API 的显式结果。

## 核心知识点三：用 TryFrom 组合成有效配置

```rust
/// Holds unvalidated input received at an application boundary.
struct RawQueueConfig {
    account_id: u64,
    label: String,
    retries: u8,
}

/// Stores only values that passed their domain validation.
#[derive(Debug, PartialEq, Eq)]
struct QueueConfig {
    account_id: AccountId,
    label: Label,
    retries: RetryCount,
}

/// Converts untrusted fields into a fully validated queue configuration.
impl TryFrom<RawQueueConfig> for QueueConfig {
    type Error = ConfigError;

    /// Stops at the first invalid field and preserves its error.
    fn try_from(raw: RawQueueConfig) -> Result<Self, Self::Error> {
        let label = Label::try_from(raw.label)?;
        let retries = RetryCount::try_from(raw.retries)?;
        Ok(Self {
            account_id: AccountId::from(raw.account_id),
            label,
            retries,
        })
    }
}

/// Checks successful conversion and both validation failures.
fn main() {
    let valid = QueueConfig::try_from(RawQueueConfig {
        account_id: 42,
        label: String::from("  import  "),
        retries: 3,
    })
    .unwrap();
    assert_eq!(valid.account_id.0, 42);
    assert_eq!(valid.label.0, "import");
    assert_eq!(valid.retries.0, 3);

    let empty_label = QueueConfig::try_from(RawQueueConfig {
        account_id: 42,
        label: String::from("  "),
        retries: 3,
    });
    assert_eq!(empty_label, Err(ConfigError::EmptyLabel));

    let invalid_config_retries = QueueConfig::try_from(RawQueueConfig {
        account_id: 42,
        label: String::from("import"),
        retries: 6,
    });
    assert_eq!(
        invalid_config_retries,
        Err(ConfigError::RetryLimitExceeded(6))
    );

    let excessive_retries = RetryCount::try_from(6);
    assert_eq!(excessive_retries, Err(ConfigError::RetryLimitExceeded(6)));
}
```

此示例的错误传播使用 `?`，因为每个 fallible conversion 都返回同一个 `ConfigError`。验证全部完成后才创建 `QueueConfig`，因此无效中间值不会成为一个看似已验证的对象。生产 API 通常会提供只读访问方法，而不是直接暴露内部字段；代码在同一示例模块访问私有字段只是为了让断言简洁。

若输入是 `u32`，通过 `as u8` 会截断超出范围的数据；不要先截断再构造受限类型。若数值越界，应保留原值并返回错误。`TryFrom` 给边界调用方决定如何反馈、记录或恢复的机会。

## 与 Java / Go 对比：领域值对象和转换边界

Java 可以用专门的 record/value object，Go 可以声明新命名类型，Rust 则常用 newtype。类型本身阻止无意义的混用，`TryFrom` 对可能失败的构造返回带原因的 `Result`。

- 确定不会失败且语义保真的转换才考虑 `From`。
- 有业务范围/格式校验时优先 `TryFrom`。
- 不能依靠 `as` 截断或 panic 创建“看似有效”的值。

原则是让非法领域状态难以被调用方构造，而非给原始整数换一个别名。

## 检验理解

**先预测再执行：** 创建一个仅允许正数的 newtype，通过 `TryFrom` 拒绝 0；写成功和失败的断言。再尝试用 `as` 直接变成一个窄整数，说明这种写法为何可能丢失领域信息。

**验收标准：** 能区分 `From` 和 `TryFrom` 的使用条件，说明私有字段如何保护不变量。

## 分层提示

1. **定位提示**：列出字段允许的全部值；哪些输入总能转换，哪些可能违反约束？
2. **类型提示**：为各领域含义选择独立 newtype，并检查字段是否私有、外部能否直接构造。
3. **转换提示**：无损包装可用 `From`；需要检查条件时用 `TryFrom`，在 Error 中保留失败原因。
4. **参考方案**：先验证 `Label` 与 `RetryCount`，再在 `QueueConfig::try_from` 中传播任一失败，验证成功后才构造最终值。

## 本节小结

- 从调用方真正需要的行为出发，再设计抽象，而不是把所有类型强行统一。
- 让类型约束、转换失败和接口边界可被编译器与测试验证。
- 对性能与扩展性作工程取舍时记录可验证的假设，避免无条件结论。
