# M01-L04：Git、格式化、Clippy 与最小测试

> **本节核心问题：一段代码“能编译”之后，怎样让团队相信这次修改值得合并？** 用最小的测试和清楚的 Git 差异交付证据。

## 学习目标

完成本节后，你能够：

- 区分代码格式、lint、编译检查和行为测试的覆盖范围。
- 写出一项调用真实函数、具有可观察断言的 Rust 测试。
- 在存在其他未完成修改的仓库中，仅提交本任务需要的文件。

## 先修与环境

先完成 M01-L03，能运行 Cargo 命令并阅读测试结果。本节使用 **Rust 1.95.0 / Edition 2024**，可下载[完整单元测试项目 ZIP](./m01-l04-sample.zip)验证。

## 场景：功能修好了，但 PR 怎么证明没改坏？

假设有人要求：“用户名统一转成小写。”你修改函数后发现 `cargo check` 通过。此时不能说明新行为正确：需要有能在错误实现上失败的测试，还要保证提交没有夹带其他同事的改动。

## 核心知识点一：四种检查不是互相替代

| 检查 | 常用命令 | 实际回答的问题 |
| --- | --- | --- |
| 格式 | `cargo +1.95.0 fmt -- --check` | 代码是否遵守 rustfmt 排版？ |
| 编译 | `cargo +1.95.0 check --all-targets` | 所选目标能否通过 Rust 编译检查？ |
| Lint | `cargo +1.95.0 clippy --all-targets` | 是否存在 Clippy 发现的可疑写法？ |
| 行为 | `cargo +1.95.0 test` | 被发现和执行的测试是否通过？ |

**注意证据边界：** Clippy 可能报告警告，是否让命令失败取决于选项和项目约定；测试命令即使成功，若只运行 0 项测试，也不能作为行为回归的证据。

Java 的 JUnit / Checkstyle 和 Go 的 `go test` / `gofmt` 也分别承担不同责任。Rust 中的测试代码通常直接与被测 crate 放在一起，省去额外测试运行器配置，但仍必须写出有价值的断言。

## 核心知识点二：让测试对具体行为负责

将以下代码放在 Cargo 项目的 `src/lib.rs`：

```rust
/// Normalize an incoming display name.
pub fn normalize_name(name: &str) -> String {
    name.to_lowercase()
}

#[cfg(test)]
mod tests {
    use super::normalize_name;

    #[test]
    fn lowercases_a_mixed_case_name() {
        assert_eq!(normalize_name("Rustacean"), "rustacean");
    }
}
```

**先预测：** 运行 `cargo +1.95.0 test`，是否会发现该测试？是。`#[cfg(test)]` 使测试模块在测试构建中启用，`#[test]` 标记测试函数，`assert_eq!` 对实际返回值和约定结果做比较。

反例：

```rust
#[test]
fn lowercases_a_mixed_case_name() {
    assert!(true);
}
```

反例能通过，但不调用目标函数。**验证测试本身有用的方法：** 暂时把期望值改错，确认测试会失败，再恢复正确期望并重跑。不要把故意失败的测试留在最终提交里。

## 核心知识点三：Git 提交要让变更范围可追溯

一个可审查的工作循环：

```text
git status --short --branch
git diff
cargo +1.95.0 fmt
git diff
cargo +1.95.0 check --all-targets
cargo +1.95.0 clippy --all-targets
cargo +1.95.0 test
git status --short
git add src/lib.rs
git diff --cached
git commit -m "test: cover mixed-case name normalization"
```

这里的 `src/lib.rs` 仅作示例；按真实任务修改和暂存对应路径。`cargo fmt` 会改写源文件，格式化后重新看 diff，避免混入无关格式变更。**不要使用 `git add .` 无意暂存其他人的工作，也不要为了“全绿”删除测试或屏蔽 lint。**

如果某条检查失败，保留诊断、修复原因，再重跑相关检查。Git 只记录快照，不能替你证明内容正确；审查 `git diff --cached` 才能确认本次提交到底包含什么。

## 检验理解

审核记录只有以下信息：

```text
cargo fmt -- --check   ok
cargo test             ok (0 tests)
git diff               empty
```

**预测：** 是否能据此批准“已完成回归验证”？不能。0 个测试表示没有相关行为证据；空 `git diff` 也可能只表示当前没有**未暂存**改动，应核对 `git status`、`git diff --cached` 和提交历史。

## 本地练习

下载 [M01-L04 示例项目](./m01-l04-sample.zip)，亲自运行测试并临时制造一次失败，恢复后按本节质量检查顺序复验。下方还有三道题：**修复空断言 → 编写提交前检查流程 → 审核证据边界**。

**验收标准：** 至少一项真实测试通过，测试在错误预期下确实失败；最终暂存差异只包含任务文件。

## 实践迁移：从修复代码到最小可审 PR

**先预测：** 修复了一个折扣函数，同时工作区里还有无关的 README 改动。直接 `git add .` 会让审阅者看到什么？

**动手改造：** 为折扣边界增加真实断言，分别运行 fmt、Clippy、check 和 test，只暂存本题源码与测试。

**反例与边界：** 故意把函数改成始终返回同一折扣值，确认测试能失败；然后恢复实现，检查 `git diff --cached` 是否含无关文件。

**验收证据：** 提供测试失败/恢复结果、暂存区差异以及一句说明为何这次改动无需重构全项目。

## 本节小结

- rustfmt、Clippy、编译器和测试各自回答不同的问题。
- 真实回归测试必须调用实际行为，并在违约时失败。
- Git 提交前要检查差异与暂存范围，不能只看工具退出码。
