# M01-L03：build/check/run/test 与诊断阅读

> **本节核心问题：看到一句“Cargo 失败了”，你应该先查哪里？** 最重要的是判断失败发生在什么阶段。


## 核心机制的进一步推导

Cargo 的 check、test、run 分别回答类型检查、断言与运行行为三个不同问题，不能用一个命令的成功代替全局正确性。

**分层练习：** 分别构造一个正确例、一个有意失败的反例和一个修复版本；在运行前预测结果，记录编译诊断或测试证据，解释修复如何保留原本的接口契约，而不是仅消除错误提示。

## 工程推进：拆解失败阶段

**从哪里来：** 上一节 M01-L02 已交付「固定的构建说明及 Cargo 工程」。

**当前问题：** 有了工程，构建、测试和运行失败却会被混淆。

**本节决策：** 按 check、test、run 分别定位第一处失败。

**完成产物：** 可复现的诊断记录。**验证证据：** 每类失败均有独立命令和证据。

**为什么下一节需要它：** 在 M01-L04，将继续面对「修复若夹带无关修改，就无法可靠审查。」。

## 学习目标

完成本节后，你能够：

- 针对目标选择 `cargo check`、`build`、`run` 和 `test`。
- 区分编译错误、测试断言失败和程序运行失败。
- 从诊断中提取命令、失败阶段、文件位置及可复现条件，再验证修复是否有效。

## 先修与环境

先完成 M01-L02，能进入含 `Cargo.toml` 的项目目录。本节配套 [三类失败样例 ZIP](./m01-l03-samples.zip) 已按 **Rust 1.95.0 / Edition 2024** 准备。需先安装 `rustup toolchain install 1.95.0`；下面命令均在具体 Cargo 项目根目录执行。

## 场景：同一行“失败”，可能是三个不同问题

想象你在修改一个后端工具：

1. 类型写错，程序**还没有编译成功**。
2. 程序能编译，但测试发现结果不符合约定。
3. 程序能启动，遇到无效输入时 panic。

它们不是同一层问题。第一步先判断命令执行到了哪里，而不是盲目修改报错附近所有代码。

## 核心知识点一：四条命令对应不同问题

| 你的问题 | 常用命令 | 能得到什么 | **不能**推出什么 |
| --- | --- | --- | --- |
| 改完代码，类型/借用规则能过吗？ | `cargo check` | 快速编译检查 | 最终二进制已生成 |
| 能生成目标产物吗？ | `cargo build` | 构建结果、必要时的链接产物 | 行为一定正确 |
| 程序实际输出什么？ | `cargo run` | 构建并启动默认/指定二进制 | 所有输入都正确 |
| 已有回归用例通过吗？ | `cargo test` | 发现并运行测试 | 未测试的行为也正确 |

命令通常可以加本节锁定工具链，例如 `cargo +1.95.0 check`。**快速迭代不意味着永远只执行 check**：改了对外行为，要补相关测试；发布前要按项目质量流程做更完整的检查。

## 核心知识点二：从失败类型决定下一步

### A. 编译失败：还没有跑到你的业务逻辑

```rust
fn parse_count() -> u32 {
    let count: u32 = "3";
    count
}
```

**预测：** 这是预计编译失败的片段。`"3"` 是字符串切片，不能赋给 `u32`；错误通常包含 `E0308`。应先读主消息、指向源码的行号和两侧实际类型，不要把它归为“运行异常”。

修复方向是明确约定：如果输入就是文本，须解析或改变函数输入类型；不能仅为了消除错误就随意修改返回契约。

### B. 测试失败：断言检查了实际行为

```rust
#[test]
fn addition_has_expected_result() {
    assert_eq!(2 + 2, 5);
}
```

**预测：** 测试本身可以编译，但运行时断言失败。应检查测试的 `actual` 与 `expected`，确认需求后将正确的期望值写为 `4`，再重跑测试。

`cargo test` 输出“0 tests”不代表行为已验证：可能没有写测试、测试没有被发现，或选错目标。

### C. 运行失败：编译通过不代表输入安全

```rust
fn main() {
    let input = "not-a-number";
    let number: u32 = input.parse().expect("示例要求有效整数");
    println!("{number}");
}
```

代码能编译，但执行时因为输入解析失败而 panic。此处 `expect` 用来展示故障阶段，不是建议在生产服务里无条件使用它。先固定同一输入，再检查执行路径与错误策略；`Result` 的系统处理会在后续模块学习。

## 核心知识点三：用一张诊断记录缩短排查路径

每次遇到失败，记录：

1. **命令与目录**：在什么 `Cargo.toml` 下运行了什么？
2. **阶段**：编译、测试还是实际运行？
3. **证据**：首个有因果关系的错误、文件/行号、测试名、预期与实际。
4. **修复假设**：为什么这项改动能解决根因？
5. **复验**：重跑原失败命令，再运行受影响的测试或程序输入。

对于习惯 Java/Go 的后端工程师，可以类比：`javac`/Maven 编译、`go test` 和程序运行也是不同检查阶段。Rust 编译器给出更丰富的所有权诊断，不意味着你可以跳过行为测试。

## 代码验证：亲眼看到三个阶段

下载 [M01-L03 阶段样例 ZIP](./m01-l03-samples.zip)。解压后遵照包内 README，**分别**进入 compile-fail、test-fail、runtime-fail 项目：

- **compile-fail**：先运行 `cargo +1.95.0 check`，记录编译诊断。
- **test-fail**：运行 `cargo +1.95.0 test`，记录失败断言。
- **runtime-fail**：运行 `cargo +1.95.0 run`，记录程序失败。

样例的初始失败是有意设计的。修复后分别预期输出 `3`、通过 1 项测试、输出 `42`；按样例中的说明操作，**不要把预期失败的状态直接作为最终完成结果**。

## 原理推导与反例辨析：拆解失败阶段

**问题：** 有了工程，构建、测试和运行失败却会被混淆。

**原理与推导：** 把失败映射到编译检查、断言测试和程序运行三层：每一层验证的性质不同，后面的成功不能代替前一层的证据。

**示例与证据：** 对照本节已有代码或起始工程，检验：每类失败均有独立命令和证据。

**反例：** 反例是看见 cargo run 输出正常就断言测试均通过；一个没有覆盖错误输入的程序仍可正常启动。

**独立练习：** 分别制造一个类型错误、一个期望值错误和一个运行时边界错误；预测并记录首次暴露故障的命令与修复后证据。

**复盘：** 复盘时给每个故障一个可复现的最小命令，而不是简单贴一整屏终端日志。

## 可复现的正反例：诊断的三个阶段

`src/m01_diagnostics.rs` 把合法数值、非法数值和显式 `unwrap()` 分开测试：合法输入得到计算结果；非法输入原本是 `Err`；只有主动 `unwrap()` 才变成运行时 panic（以 `#[should_panic]` 验证）。`compile_fail/m01_diagnostic_type.rs` 则在程序运行前触发 **E0308**。不能把预期 panic 的测试通过误解为业务输入处理正确。

从仓库根目录运行 `cargo +1.95.0 test --offline --manifest-path content/samples/verified-lesson-drills/Cargo.toml m01_diagnostics::`，另用 `node scripts/verify-lesson-drills.mjs` 同时检查有意编译失败的文件。先预测再运行，注意区分编译错误与运行时 panic。

## 检验理解与本地练习

先不翻答案：为什么 `cargo check` 通过后，`cargo run` 仍可能失败？回答时分别考虑链接、运行环境、输入与 panic。随后完成下方三题：**识别阶段 → 补真实测试 → 按目标选命令**。

**验收标准：** 你能为三种故障各保留一条清晰诊断、解释修复理由，并在相同输入或测试上复验。

## 实践迁移：把一次失败拆成可复现阶段

**先预测：** `cargo run` 退出非零，终端既出现编译诊断，又有测试失败的旧截图。现在首先该相信哪个阶段的证据？

**动手改造：** 在同一工作区依次执行 `cargo check`、`cargo test`、`cargo run`，为每一步记录实际命令、退出码和首次关键诊断。

**反例与边界：** 制造一个“能编译但断言失败”的输入，再对比真正的编译失败；不要用 `cargo check` 通过证明业务正确。

**验收证据：** 提交三种失败类型的最小复现记录，每类对应一个修复后重新验证的命令。

## 本节小结

- `check` 查编译；`build` 产生产物；`run` 执行；`test` 验证已写出的行为断言。
- 编译、测试与运行失败必须分别定位；通过某一关不等于整体正确。
- 诊断价值来自“阶段 → 证据 → 根因假设 → 复验”的闭环。
