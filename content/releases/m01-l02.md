## 先修与环境

已完成 M01-L01，能在终端切换目录。本节使用 **Rust 1.95.0 / Edition 2024** 作为课程样例复现基线。安装课程工具链：

```text
rustup toolchain install 1.95.0
```

后续命令中的 `+1.95.0` 显式选择该工具链；不要因为这项课程设置而随意更改其他项目的全局默认版本。

## 核心知识点一：三层工具，各管一件事

| 工具 | 做什么 | 出错时先看什么 |
| --- | --- | --- |
| `rustup` | 下载、选择工具链与组件 | 当前目录工具链、覆盖规则、组件是否安装 |
| `rustc` | 编译 Rust 源文件 | 编译器版本与具体错误信息 |
| `cargo` | 组织 package、依赖、构建与测试 | 工作目录、清单、目标与锁文件 |

在终端运行：

```text
rustup show
rustc +1.95.0 --version
cargo +1.95.0 --version
```

**先预测：** 如果当前目录的默认工具链是另一个版本，`rustc +1.95.0 --version` 会输出谁的版本？答案是显式指定的 1.95.0（前提是已安装）；`rustup show` 用来观察当前目录的默认/覆盖选择。

### 与 Java / Go 的对比

可以把 `rustup` 类比为管理 JDK/Go 版本的工具，把 `rustc` 类比为编译器，把 Cargo 类比为项目构建和依赖工具的组合。但不要误解为 Cargo 等于 Maven：Cargo 还定义 crate/package/workspace 的默认组织约定。

## 核心知识点二：工具链、Edition、package 版本不能混用

假设看到以下清单：

```toml
[package]
name = "hello-rust"
version = "0.1.0"
edition = "2024"
```

这里有 **三个不同的版本概念**：

- **工具链版本**：执行代码的编译器和工具链，例如 Rust 1.95.0，由 rustup/命令选择。
- **Edition**：当前 crate 采用的语言兼容规则，例如 `2024`，由清单声明。
- **package 版本**：`0.1.0`，描述这个包本身的发布版本。

多个 Edition 的 crate 可以在同一个依赖图中配合。切换 Edition 不等于安装编译器；升级工具链也不会自动把项目的 Edition 改掉。

## 核心知识点三：从清单读懂项目

```text
hello-rust/
├── Cargo.toml       # package 名称、Edition、依赖声明
├── Cargo.lock       # 已解析的依赖版本，通常由 Cargo 生成
└── src/
    └── main.rs      # binary crate 的常见入口
```

如果要构建库，通常使用 `src/lib.rs`；如果根清单声明 `[workspace]`，还需要检查成员包。应用程序通常提交 `Cargo.lock` 以固定依赖解析结果；它与声明依赖约束的 `Cargo.toml` 不可互相替代。

**小判断：** “依赖变更导致构建不一致，所以直接删除 Cargo.lock”是正确排查办法吗？不是。应先比较清单、锁文件 diff 和执行过的更新命令，避免无意重新解析大量依赖。

## 代码验证：从空目录创建并运行

选择一个尚不存在的 `hello-rust` 子目录，在其父目录运行。

**PowerShell（Windows）：**

```powershell
cargo +1.95.0 new hello-rust --edition 2024
Set-Location hello-rust
Get-Content Cargo.toml
cargo +1.95.0 run
```

**Bash（Linux / macOS）：**

```bash
cargo +1.95.0 new hello-rust --edition 2024
cd hello-rust
cat Cargo.toml
cargo +1.95.0 run
```

预期程序输出 `Hello, world!`。观察 `Cargo.toml` 的 Edition 和源文件 `src/main.rs`，并查看构建后的 `Cargo.lock`。这些命令针对单独创建的练习目录，不要在已有项目里重复创建同名目录。

## 常见错误：从症状定位层级

| 现象 | 先检查 | 不应该先做 |
| --- | --- | --- |
| `cargo` 命令无法识别 | 安装和 PATH、重启终端 | 修改 Edition |
| 提示缺工具链/组件 | `rustup show` 与项目的 `rust-toolchain.toml` | 无条件切换全局 nightly |
| 找不到 `Cargo.toml` | 当前目录是否在 Cargo 项目内 | 删除依赖锁文件 |
| 依赖结果变了 | `Cargo.toml`、`Cargo.lock` 和 diff | 无条件删除整个锁文件 |

## 原理推导与反例辨析：构建可复现环境

**问题：** 试点结论需要在另一台机器复现。

**原理与推导：** rustup 管理编译器版本，Cargo 管理包与工作流，Edition 影响代码解释规则；三者不是同一层配置。

**示例与证据：** 对照本节已有代码或起始工程，检验：新环境能运行 cargo check。

**反例：** 反例是只记录 `cargo --version` 却遗漏 `rustc --version` 与项目 edition；另一个环境可能用不同语义或工具链完成构建。

**独立练习：** 在全新目录建立 lib 与 bin 的最小 Cargo 工程，记录 rustc、Cargo 和 edition；切换工具链后比较 `cargo check` 的可复现性。

**复盘：** 能准确指出 Cargo.toml、src/lib.rs 与 src/main.rs 分别承担什么职责，才算理解工程入口。

## 检验理解与本地练习

先不看下方的答案，解释：**把 `Cargo.toml` 的 `version` 改成 `1.95.0` 能解决缺少工具链组件的问题吗？为什么？** 随后完成三道练习：辨认版本 → 修复错误排查建议 → 创建最小项目。

**验收标准：** 项目能够输出 `Hello, world!`；你能指出工具链、Edition、package 版本和锁文件各自所在的位置，并给出不破坏其他项目的排障顺序。

## 实践迁移：从可运行机器迁移到干净环境

**先预测：** 本机 `cargo run` 通过，换一台机器出现工具链版本不符。你能只凭 `edition = "2024"` 推断运行的是 Rust 1.95.0 吗？

**动手改造：** 在全新目录运行 `rustc --version`、`cargo --version` 和 `rustup show active-toolchain`，再检查 `Cargo.toml` 中的 edition 与 package 信息。

**反例与边界：** 分别考虑“未安装工具链”“进入了错误目录”“锁文件与依赖解析不一致”，不要把所有问题归为编译器 bug。

**验收证据：** 写出四项实际输出及对应的检查命令，另记录一次能复现的 `cargo check` 结果。

## 本节小结

- `rustup` 管工具链，`rustc` 管编译，Cargo 管项目和依赖工作流。
- Edition 不等于工具链版本，也不等于 package 版本。
- 先确认目录、项目清单和选中的工具链，再考虑升级或变更依赖。
