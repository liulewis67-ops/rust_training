## 学习目标与先修

完成 M04-L01–L04 后，在本实验独立追踪 owner 在 `render`、`add_badge` 和 `append_period` 之间的路径，区分编译修复与行为验证。

## 实验目标

- 跟踪一段文本从调用点进入多个按值函数，再作为处理结果返回的 owner 路径。
- 修复 API，让调用方拿到原文和按序处理后的文本。
- 通过克隆保留两份数据时，说清楚 clone 创建独立字符串及其成本。
- 使用公开契约测试验证输出内容、变换顺序以及原文保留。

## 行为契约

- `add_badge` 在输入前加上 `[ready] `；`append_period` 在输入后加 `.`。
- `render` 返回 `(original, processed)`：第一项必须与传入文本完全相同，第二项必须先加 badge 再加句点。
- 输入 `build complete` 时，返回值依次为 `build complete` 和 `[ready] build complete.`。
- 函数可按值消费 owned `String` 并返回结果；若同时要返回原文，必须明确保留一份原值。公开测试要求两个返回值均正确。
- 不联网、不读写文件、不使用第三方 crate；不更改公开签名和测试。

## 原理推导与反例辨析：修复文本流水线

**问题：** 真实文本管线可能先消费又重用旧值。

**原理与推导：** 文本流水线的修复重点是所有权契约：函数到底消费字符串、暂时借用，还是产生新的拥有型输出；这些选择会影响调用方能否重复使用输入。

**示例与证据：** 对照原有代码或实验验证：原文与变换结果均正确交付。

**反例：** 在每个 E0382 位置简单加入 clone，可能通过编译却掩盖不必要的复制，也不能解释接口原先为何设计错误。

**独立练习：** 先给管线每个函数标注输入/输出所有权，修复首次失效的绑定，再用测试证明两个要求的输出都保留。

**复盘：** 验收需提供一张所有权变化表和反例代码，说明为何选择 move、borrow 或 clone。

## 起始快照中的预期故障

起始 `render` 调用 `add_badge(source)` 后仍试图将 `source` 放入返回值；参数按值消费了 `String`，因此编译器应报告 E0382。只改为 `source.clone()` 会使两份值都可用，但要确认结果确实按顺序经过两个阶段并且原文未改变。clone 对 `String` 可能分配并复制内容；若函数签名或业务契约不同，也可用显式返回/重建设计表达数据流，但本实验不可改公开签名。

## 分层提示

1. 在 `render` 调用每个按值函数前，写出当前 owner。
2. 检查调用方需要几个字符串结果；一份 owned 值不能同时转移到两个返回槽。
3. 只在契约确实需要原文和结果两份数据时，显式创建第二份 `String`。
4. 顺序组合两个阶段的返回值；最终同时返回原文 owner 与转换后 owner。

## 参考实现

以下 `src/lib.rs` 保留公开签名并实现两个处理阶段：

```rust
/// Adds a status badge to an owned message.
pub fn add_badge(mut text: String) -> String {
    text.insert_str(0, "[ready] ");
    text
}

/// Adds terminal punctuation to an owned message.
pub fn append_period(mut text: String) -> String {
    text.push('.');
    text
}

/// Returns the original input alongside its transformed form.
pub fn render(source: String) -> (String, String) {
    let processed = append_period(add_badge(source.clone()));
    (source, processed)
}
```

输入字符串需要出现在两个返回值中，所以这里显式克隆一次；`source` 保留为原文 owner，克隆出的字符串依次移动到 `add_badge` 和 `append_period`。公开测试会检查原文未变、两个阶段顺序正确，以及各阶段的单独行为。对更改了数据契约的 API，应先重新设计 owner 数据流，而不是默认到处克隆。
