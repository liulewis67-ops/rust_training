# M01-L04 练习：Git、格式化、Clippy 与最小测试

先独立作答，再展开公开提示与参考答案。完整单元测试项目可从本节课下载并在本地复现。

## 练习一 · 修复：让测试保护具体行为

### 题面

一个函数把用户名规范化为小写，但已有测试只写了：

```rust
#[test]
fn normalizes_name() {
    assert!(true);
}
```

请将它改成能保护“`"Rustacean"` 被规范化为 `"rustacean"`”这一约定的测试。再说明如何运行目标测试，以及怎样用一个故意错误的期望值确认断言确实执行。

### 作答契约

- 测试必须调用实际的规范化函数，并比较有意义的预期值。
- 测试名应描述情境或预期行为。
- 说明运行测试和确认测试被发现的办法。
- 错误期望值应使测试失败；验证后恢复正确值并重跑。

### 分层提示

1. `assert!(true)` 与函数输出没有联系。
2. 把输入传给函数，再用 `assert_eq!` 比较实际值和期望值。
3. 测试应放在 Cargo 能发现的位置，并使用 `#[test]`。
4. 可按题意写成 `assert_eq!(normalize_name("Rustacean"), "rustacean")`；函数名以项目实际接口为准。

### 参考答案

```rust
#[cfg(test)]
mod tests {
    use super::normalize_name;

    #[test]
    fn lowercases_a_mixed_case_name() {
        assert_eq!(normalize_name("Rustacean"), "rustacean");
    }
}
```

在下载项目中运行 `cargo +1.95.0 test` 并确认该测试出现在运行结果中。将临时预期值改成另一个字符串后，测试应失败；随后恢复 `"rustacean"` 并再次运行。项目若采用不同模块结构，应按其可见性和测试布局调整导入。

### 自评规程

- 测试调用目标函数并断言返回值：2 分。
- 测试名表达行为，测试可被发现：1 分。
- 描述错误期望值的负向验证及恢复后的复跑：1 分。

## 练习二 · 实现：建立清楚的提交前复查流程

### 题面

你在已有仓库中改了一处函数并添加回归测试。请写出一组适合交付前执行的步骤和命令，至少覆盖：

1. 查看当前分支、工作区和差异；
2. 格式化并检查格式改动；
3. 运行测试与 Clippy；
4. 再看差异并只提交本任务文件。

假定仓库已有未完成的无关改动。说明你怎样避免把它们一起提交，以及某条命令失败时如何处理。

### 作答契约

- 步骤体现“先检查状态、执行适当检查、复看差异、限定提交范围”。
- 不覆盖或丢弃他人的未完成修改。
- 将格式、lint、测试视为不同检查，并在修复后重跑失败命令。
- 提交前确认暂存区只含本任务内容。

### 分层提示

1. `git status` 与 `git diff` 能帮助确认工作区和未暂存改动。
2. `cargo fmt -- --check` 是格式检查；`cargo fmt` 会修改格式。
3. `cargo test` 和 `cargo clippy` 分别检查测试行为与 lint。
4. 可用路径明确的 `git add` 暂存所需文件，再看 `git diff --cached`。

### 参考答案

一种可复查流程：

```text
git status --short --branch
git diff
cargo +1.95.0 fmt
git diff
cargo +1.95.0 test
cargo +1.95.0 clippy
git status --short
git add src/target.rs src/target_tests.rs
git diff --cached
git commit -m "fix: normalize mixed-case names"
```

若项目约定只检查格式而不自动改写，可先用 `cargo fmt -- --check`，失败后再格式化并检查格式 diff。路径按真实仓库调整；不要用 `git add .` 把无关改动一并暂存。任一命令失败时保留诊断、定位并修复原因，再重跑失败命令及相关检查；不可删除测试或屏蔽 lint 来制造通过结果。

### 自评规程

- 覆盖状态、差异、格式、测试、Clippy：2 分。
- 暂存范围受控且提交前查看暂存差异：1 分。
- 失败后修复并重跑，未丢弃无关修改：1 分。

## 练习三 · 设计评审：哪些检查支持什么结论？

### 题面

评审者看到如下交付记录：

```text
cargo fmt -- --check   通过
cargo clippy           通过
cargo test             通过，0 tests
git diff               空
```

请指出这份记录能支持和不能支持的结论，列出至少三项需要追问或补充的证据，并给出使交付可复查的最小后续步骤。

### 作答契约

- 不把格式和 lint 通过推断成行为正确。
- 注意 `0 tests` 表示没有行为测试执行。
- 注意空 diff 可能意味着没有工作区改动，也可能检查错了目录/状态；需要结合仓库与提交状态核实。
- 提出的后续步骤能确认目标改动、真实测试和提交内容。

### 分层提示

1. 每条命令只对其覆盖的问题提供证据。
2. 检查测试是否存在、是否被 Cargo 发现以及测试运行目标。
3. 查看分支、`git status`、相对 HEAD 的差异和最近提交。
4. 提交结论应与实际检查范围匹配，不确定时明确保留疑问。

### 参考答案

记录表明格式检查退出成功，Clippy 被记录为通过；但没有保存 Clippy 诊断或项目警告策略，不能据此断定没有 lint 警告。二者都不表明本次行为修改正确，也不表明有任何回归测试运行。`cargo test` 的退出成功结合 `0 tests` 不能证明被测行为正确。空的 `git diff` 只说明当前查看范围没有未暂存差异，不能单独证明改动已保存或目标修改确实存在。

应追问：当前分支和工作区状态是什么；目标文件相对 HEAD 或预期基线是否存在差异；为什么没有测试被发现；是否已暂存或提交；提交内容是否只包含本任务。最小后续步骤是检查 `git status --short --branch`、`git diff HEAD` 和 `git diff --cached`，确认目标变更；补充会调用目标行为的测试并确认测试计数大于零；运行相关测试；最后审查暂存差异后再提交。

### 自评规程

- 正确解释格式、lint、零测试和空 diff 的证据边界：2 分。
- 至少提出三项具体追问：1 分。
- 后续步骤能够查明目标变更并执行真实行为验证：1 分。
