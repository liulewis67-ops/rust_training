# M03-L03：`Option` 与缺失值

> **本节核心问题：** 查询不存在的工单时，为什么返回空字符串通常不如返回 Option？

## 学习目标

- 用 `Option<T>` 表示一次查询可能有值，也可能没有值。
- 构造 `Some(value)` 与 `None`，并按各自形态读取或处理结果。
- 用穷尽 `match` 处理成功与缺失两条路径。
- 识别 `unwrap()` 在无值时会 panic，不把“查询未命中”当成永远不可能发生。

## 先修与环境

完成 M03-L02，能构造枚举变体、按变体匹配并读取携带数据。本节使用标准库 `Option` 表达可缺失的查询结果；不引入 `Result` 或错误传播。

## 场景：根据编号查询工单名称

工单编号不一定存在。`""` 既可能是一个真实内容，也可能被误用来表达“查不到”。`Option<T>` 让调用方在类型上区分 `Some(value)` 与 `None`。

**先预测：** `ticket_title(99).unwrap()` 在没有命中时会怎样？本节要建立缺失路径的完整处理，而不是用 panic 把正常未命中当异常退出。

## 核心知识点一：查询可能没有结果

按编号查名称，可能命中已有记录，也可能查不到。与其用特殊数字或空字符串假装“没有值”，可以让返回类型直接表示两种情况：

```rust
/// Looks up a display name for a small set of ticket codes.
fn ticket_title(code: u16) -> Option<&'static str> {
    match code {
        10 => Some("standard"),
        20 => Some("priority"),
        _ => None,
    }
}

/// Produces a message for either a found or missing ticket.
fn ticket_message(code: u16) -> &'static str {
    match ticket_title(code) {
        Some(title) => title,
        None => "not found",
    }
}

/// Prints one found result and one missing result.
fn main() {
    println!("{}", ticket_message(10));
    println!("{}", ticket_message(99));
}
```

`Option<T>` 是标准库枚举：`Some` 携带一个 `T` 类型的值，`None` 表示没有值。查询函数把“可能没有标题”写进了返回类型。若调用方要按当前契约安全地产生消息，应显式处理“有标题”和“没找到”两条路径；直接调用 `unwrap()` 仍能编译，但会把缺失处理变成运行时 panic。`Some` 和 `None` 已在 prelude 中，无须导入。

## 核心知识点二：用 `match` 同时处理两种情况

`match` 会要求覆盖 `Option` 的两种变体。`Some(title)` 把内容绑定到 `title`；`None` arm 没有可绑定的内容。调用方可以返回缺省展示文本、略过该项，或把缺失继续交给上层处理；应该按当前函数的契约选择，不要悄悄伪造一条查询结果。

```rust
/// Returns a short note only when the code has a note.
fn optional_note(code: u16) -> Option<&'static str> {
    match code {
        10 => Some("renewal available"),
        20 => Some("priority handling"),
        _ => None,
    }
}

/// Converts an optional note into an explicit display label.
fn note_label(code: u16) -> &'static str {
    match optional_note(code) {
        Some(note) => note,
        None => "no note",
    }
}
```

不要为了让调用点变短，就删除 `None` 路径或把空字符串当成内部哨兵。`Option` 让“可能缺少”成为函数签名的一部分；当调用方使用 `match` 时，编译器会检查两种变体都已覆盖，但类型本身不会禁止 `unwrap()`。

## 核心知识点三：`unwrap()` 的失败路径

`unwrap()` 只在值为 `Some` 时返回内部值；遇到 `None` 会 panic。已证明某个值必然存在的极小内部不变量，有时可以允许 panic，但外部查询输入通常不能保证命中。下面的函数能够编译，却会在输入 99 时崩溃：

```rust
/// Searches titles before the demonstration panic path.
fn lookup_title(code: u16) -> Option<&'static str> {
    match code {
        10 => Some("standard"),
        20 => Some("priority"),
        _ => None,
    }
}

/// Panics when the ticket code has no matching title.
fn title_or_panic(code: u16) -> &'static str {
    lookup_title(code).unwrap()
}

/// Demonstrates the missing-query panic path.
fn main() {
    println!("{}", title_or_panic(99));
}
```

修复方向是让函数返回 `Option<&'static str>`，或在调用处用 `match` 明确处理 `None`。不要用 `unwrap_or` 换个默认值掩盖没有设计的行为；只有产品契约明确规定缺省值时，才提供该值。

## 检查顺序

1. 查看函数返回类型是否承认查询可能缺失。
2. 找出调用点是否覆盖 `Some` 与 `None`。
3. 为两个分支分别选择符合契约的行为；不要假设样例输入等于所有输入。
4. 用至少一个命中值和一个未命中值验证；再确认缺失路径没有无条件 `unwrap()`。

## 与 Java / Go 对比：缺失是类型信息

Java API 可能使用 `null` 或 `Optional<T>`，Go 经常返回 `(value, ok)` 或配合错误值。Rust 的 `Option<T>` 明确表示“可能没有值”，通过 `match` 处理两种路径。`None` 不是业务错误的万能替代品：需要区分失败原因时仍要设计 `Result` 等类型。

## 检验理解与本地练习

**先预测再运行：** `ticket_title(10)` 与 `ticket_title(99)` 分别返回什么？在 `None` 分支调用 `unwrap()` 会怎样？改为显式 `match`，并在本地测试命中与未命中。

**验收标准：** 能清楚区分“有值但内容为空”和“没有值”，不会默认假设查询必然成功。

## 实践迁移：缺失并不是空字符串

**先预测：** 工单名称可能真的是空串。若查询未命中也返回 `""`，调用方能区分这两种情形吗？

**动手改造：** 让查询函数返回 `Option<&str>`，把命中、存在但内容为空、缺失三个输入分别写成断言。

**反例与边界：** 对 `None` 使用错误处理而不是无条件 `unwrap`；检查结果只借用输入中的工单。

**验收证据：** 提交三种结果及明确的调用方匹配分支，说明为何不是用哨兵字符串。

## 本节小结

- 从业务需求定义字段与状态，而不是先暴露一堆可随意修改的值。
- 用类型、匹配与方法签名标出合法操作和不允许的路径。
- 编译检查发现结构问题，行为测试验证业务承诺；两者都不可省略。
