# M08-L05：实验——日志聚合统计

> **实验核心问题：** 按服务名聚合日志时，重复键为什么不能直接覆盖？如何在使用 HashMap 的同时保证稳定输出顺序？

## 工程推进：修复日志聚合

**从哪里来：** 上一节 M08-L04 已交付「可验证的迭代汇总逻辑」。

**当前问题：** 重复服务名会被 insert 覆盖且 HashMap 输出无序。

**本节决策：** 借助 entry 累加，再按服务排序。

**完成产物：** 确定顺序的服务统计。**验证证据：** 重复 api 的字节数与计数准确。

**为什么下一节需要它：** M08-L06 将面对「拒绝记录、无值、有效零值必须区分。」。

## 实验目标

实现一个按服务名汇总事件数与字节数的函数，并解释：

- 空输入为什么产生空报告；
- 重复服务名为什么必须累加而不是覆盖；
- 如何借用输入中的 `&str` 键，避免为了聚合而复制服务名；
- 为什么内部使用 `HashMap` 时仍要明确规定输出顺序。

## 输入与输出契约

起始工作区提供 `LogEvent { service: &str, bytes: u64 }` 和待完成的 `aggregate`。假设单个服务的事件数及字节总和均可由目标类型表示。本实验不解析原始日志文本，也不执行文件 I/O。

对输入中的每个不同服务名，结果恰有一行：`event_count` 是其事件个数，`total_bytes` 是这些事件的字节数之和。空输入返回空 `Vec`。服务名区分大小写，Unicode 字符串按原样保留。

输出行按 `service` 的 Rust `str` 字典序升序排列。这个顺序属于实验接口契约；不得依赖 `HashMap` 的遍历顺序，也不得在测试里直接比较无序 map 的遍历结果。

## 先预测，再修改

输入依次是 `("api", 10)`、`("web", 2)`、`("api", 5)`。假设 bytes 单位为字节，最终应该恰好返回两个汇总：api 有 2 条、15 字节；web 有 1 条、2 字节。要求按服务名排序，不可依赖 HashMap 某一次迭代巧合有序。

与 Java 的 `Map.merge`、Go 的 `map` 聚合一样，按键更新和报告排序是两件事。Rust 的 `entry` API 可以组织更新逻辑，但不会替你保证遍历顺序。

## 工作步骤

1. 先运行公开测试并记录失败测试及实际值。起始错误是重复键调用 `insert` 覆盖旧累计值。
2. 将每个输入事件归并到以借用 `&str` 为键的 map。可以使用 `entry` API；新键初始事件数为 1、字节数为当前事件值，旧键分别递增和累加。
3. 把聚合项转换成 `Vec<ServiceSummary>`，再按服务名排序后返回。
4. 运行格式、编译和公开契约检查。说明 map 键借用自输入，返回结果不能超出相关输入字符串的生命周期。
5. 试一项错误变体：直接收集 `HashMap::into_iter()` 结果，不排序。用乱序输入和有序期望值说明输出契约没有被满足；不要写依赖某次随机排列的测试。

## 分层提示

1. **重复键**：`insert` 会怎样处理已经存在的键？比较 `entry(...).and_modify(...).or_insert(...)`。
2. **借用**：map 的键是否必须是 `String`？输入切片和输出汇总分别拥有谁的生命周期？
3. **顺序**：聚合结构负责高效按键更新；哪个结构更适合表达有序报告？
4. **验证**：分别覆盖空输入、同键重复、不同键及 Unicode；比较已排序的期望行。

## 参考实现

参考工程的 [完整 `src/lib.rs`](https://github.com/liulewis67-ops/rust_training/blob/main/content/samples/m08-reference/src/lib.rs) 使用 `HashMap::entry` 累加重复服务名，收集为 `Vec` 后显式排序。

entry.0 += 1;
entry.1 += event.bytes;

## 实践迁移：分组统计的重复键与稳定顺序

**先预测：** 输入依次为 `api:10`、`web:2`、`api:5`，HashMap 直接 insert 是否会自动把 api 的字节数累加到 15？

**动手改造：** 使用已验证的 M08 starter，在 `entry` 更新路径处理同名服务，最后将结果显式排序并检查公开测试。

**反例与边界：** 覆盖空输入、重复服务、Unicode 名称；不要通过只检查 map 长度忽略累加错误。

**验收证据：** 保存原始失败的测试名称与修正后的通过结果，说明统计顺序为何不能依赖 HashMap。
