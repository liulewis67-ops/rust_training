> **独立检查：** 工单文本要先读取 UTF-8 字节长度，再交给格式化函数消费。要求只读取时借用，需要转移时 move。

## 契约

- `publish_ticket(String)` 返回 `(原始 UTF-8 字节数, "[ticket] " + 原文本)`。
- 只为读取长度时使用共享借用；将文本交给 `render_ticket` 时移动所有权。
- 借用检查必须先完成，随后才移动 `source`；不能在移动后再次读取它。
- 输入 `"build"` 返回 `(5, "[ticket] build")`；输入 `"é"` 的长度为 2 个 UTF-8 字节，返回 `(2, "[ticket] é")`。
- 两项结果都必须来自传入数据；不能硬编码公开样例、漏掉格式化、用 `0` 代替长度或改公开签名。
- 代码必须编译，不使用 `unsafe` 或第三方 crate。

## 任务分解与验收

1. 从 `source` 只读取得字节长度。
2. 把 `source` 按值传给 `render_ticket`。
3. 组合之前已计算出的长度与格式化后的 owned 文本。
4. 通过代码检查和至少三组输出断言，验证没有为了保存字节数而克隆全文。

**与 Java/Go 对比：** 相比先构建中间字符串再交给另一函数，Rust 可以在签名中表达“先借用查看，再交出 owner”。`String::len()` 返回 UTF-8 字节数，并非 Unicode 字符数；这在 Java/Go 与 Rust 的文本处理中都要明确区分。

## 原理推导与反例辨析：提交工单审计

**问题：** 消费工单前还需要读取其 UTF-8 字节信息。

**原理与推导：** 工单审计要求先观察数据再移交拥有权：只读元数据可借用计算，但正式交付后的旧绑定不能继续读。

**示例与证据：** 对照原有代码或实验验证：UTF-8 字节数和 move 断言正确。

**反例：** 先消费 String 后才统计它的 UTF-8 字节长度，会遇到 moved value；把字节长度误当字符数也可能违反题目语义。

**独立练习：** 先预测审计与移交的正确操作顺序，验证 ASCII 与非 ASCII 工单标题的字节长度和交付结果。

**复盘：** 复盘区分“读借用在什么时候结束”和“拥有值在什么时候被移交”。

## 参考实现

```rust
/// Returns the original UTF-8 byte count and the rendered ticket.
pub fn publish_ticket(source: String) -> (usize, String) {
    let byte_len = source.len();
    let ticket = render_ticket(source);
    (byte_len, ticket)
}

/// Consumes a ticket body and returns its rendered form.
fn render_ticket(body: String) -> String {
    format!("[ticket] {body}")
}
```

`source.len()` 只读取长度，方法调用隐式共享借用字符串；该表达式结束后借用结束，随后 `source` 按值移动给 `render_ticket`。测试 `é` 时长度是 2，因为 `String::len()` 返回 UTF-8 字节数。
