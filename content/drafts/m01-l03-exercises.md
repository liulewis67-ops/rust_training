## 练习一 · 预测：失败发生在哪个阶段？

### 题面

对照以下三条简化终端记录，分别说明失败发生在编译、测试还是程序运行阶段，并给出下一条最有信息量的命令或检查：

1. `error[E0308]: mismatched types`，随后显示 `could not compile`。
2. 程序与测试目标均已编译，测试显示 `assertion failed`，并列出 expected 与 actual。
3. 构建成功，程序启动后在解析输入时 panic 并显示回溯。

另外，从 `cargo check`、`cargo build`、`cargo run`、`cargo test` 中分别挑出适合快速编译反馈、生成构建产物、观察程序输出和验证行为的命令。

### 作答契约

- 三条记录阶段判断正确。
- 四个 Cargo 命令各自对应正确用途。
- 不把“有 0 个测试且命令成功”解释成行为已验证。
- 每个修复之后都要重跑覆盖相应行为的检查。

### 分层提示

1. `E` 开头的 Rust 错误码来自哪一阶段？
2. 断言运行需要构建成功；panic 则发生在程序执行之后。
3. 记住 `check` 做快速编译检查，`run` 会启动程序，`test` 会运行发现的测试。
4. 查看下方参考映射，并指出你如何验证“0 个测试”的情况。

### 参考答案

1. 编译阶段失败；先运行 `cargo check` 并检查错误码、主消息和源码位置。
2. 测试阶段失败；查看失败测试的预期/实际值，运行对应测试目标并修正行为或确认契约。
3. 运行阶段失败；保留输入和回溯，按程序逻辑定位 panic 原因，再用同一输入重跑。

`cargo check` 快速检查是否可编译；`cargo build` 构建程序；`cargo run` 构建并启动程序；`cargo test` 编译和运行被发现的测试。若显示 0 个测试，先确认测试是否存在且被正确发现，不能把没有执行测试当作行为通过。

### 自评规程

- 正确区分三种失败阶段：2 分。
- 四条命令映射正确：1 分。
- 对 0 个测试作出谨慎解释：1 分。

## 练习二 · 修复：让回归断言真正运行

### 题面

某项目中的函数应将百分比限制在 0 到 100，但练习者运行 `cargo test` 后得到：

```text
test result: ok. 0 passed; 0 failed; 0 ignored
```

请解释这份输出能证明什么、不能证明什么。接着为 `clamp_percent(101)` 应返回 `100` 补一个能被测试运行器发现的测试；说明你如何证明该测试不只是“总能通过”的空测试。

### 作答契约

- 不改弱函数契约，不以 0 个测试的成功作为正确性证据。
- 测试必须调用目标函数并断言边界结果。
- 指出需要 `#[test]` 标记和 test module 结构，使 Cargo 能发现测试。
- 说明应再运行 `cargo test`，并检查通过计数大于零。

### 分层提示

1. 这条输出里的 `0 passed` 是没有失败，还是没有发现测试？
2. 测试至少要调用函数一次，并对返回值作断言。
3. Rust unit test 函数要用属性标记；测试模块常放在 `src` 同一文件中。
4. 参考答案给出一段最小测试结构。

### 参考答案

```rust
#[cfg(test)]
mod tests {
    use super::clamp_percent;

    #[test]
    fn clamps_values_above_one_hundred() {
        assert_eq!(clamp_percent(101), 100);
    }
}
```

原输出只说明运行器没有报告失败，不能证明本题行为正确。补上调用与断言后，重跑 `cargo test` 并确认测试被发现。若临时把期望值改成 `99` 后测试仍然通过，应继续查找测试是否运行或断言是否有效，然后恢复题目正确契约并再次验证。

### 自评规程

- 说明 0 个测试不构成行为证据：1 分。
- 写出会调用目标函数的真实边界测试：2 分。
- 说明如何确认测试被发现并验证断言有效：1 分。

## 练习三 · 实现：为不同目标选择检查命令

### 题面

把下面的开发者目标与最适合开始的 Cargo 命令配对；可以添加第二条命令，但需说明原因。

| 目标 | 首选命令 |
|---|---|
| A. 写完一小段代码，想尽快发现类型错误 | ? |
| B. 需要生成可交付的本地构建产物 | ? |
| C. 想观察程序对给定输入的实际输出 | ? |
| D. 修复行为后，想验证已有回归用例 | ? |

最后写出一条诊断处理规则：如果目标命令失败，你会保留什么信息、怎么定位到根因，以及修复后如何验证。

### 作答契约

- A–D 分别选择适当命令。
- 说明不同命令验证范围不同，不把一次通过扩大解释为完整正确性证明。
- 诊断记录包含命令、输入（如有）、失败阶段和关键输出。
- 修复后重跑原失败命令，并补充可能受影响的行为检查。

### 分层提示

1. 先写清自己要回答的是“能否编译”“是否生成产物”“运行输出”还是“行为是否符合”。
2. 频繁反馈优先考虑 `check`；要看输入输出需启动程序。
3. 测试检查选定行为，但仍受测试覆盖范围限制。
4. 查看参考命令表，并补上修复后的复验步骤。

### 参考答案

| 目标 | 首选命令 |
|---|---|
| A | `cargo check` |
| B | `cargo build` |
| C | `cargo run` |
| D | `cargo test` |

记录失败命令及其输入和关键诊断，从第一处有因果关系的错误开始定位；结合任务契约修复后重跑原失败命令，并运行受影响的测试。若测试运行器未发现任何测试，要先修复测试发现问题，不能用退出码 0 代替验证。

### 自评规程

- 命令映射四项正确：2 分。
- 能说出每条命令的验证边界：1 分。
- 诊断和复验步骤可执行：1 分。
