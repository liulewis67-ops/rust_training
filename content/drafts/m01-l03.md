# M01-L03：build/check/run/test 与诊断阅读

## 先修与环境基准

先修 M01-L02；需要知道当前目录属于哪个 Cargo 项目，并能读懂一个简单函数和断言。

## 学习目标

读完本节后，你可以根据正在回答的问题选择 `cargo check`、`cargo build`、`cargo run` 或 `cargo test`，并区分编译错误、测试失败和程序运行失败。

## 先问：我现在要知道什么？

开发时不必每次都重复整个流程。改完源码，想尽早知道类型和借用是否通过，可以先运行 `cargo check`。它会检查是否能编译，但不会生成可供运行的最终可执行文件，通常比完整构建更适合频繁反馈。

需要构建程序时运行 `cargo build`。这是检查构建和生成程序的一步，能发现更完整构建阶段的问题。想立即启动程序，可以用 `cargo run`，让 Cargo 负责需要的构建后再运行目标。

当你要判断行为是否符合预期时运行 `cargo test`。测试失败和编译失败不是一回事：测试目标本身需要先能编译；编译成功后，断言失败才说明执行结果与测试期望不同。没有测试时，`cargo test` 的成功只能说明没有失败的已发现测试，不能证明软件没有缺陷。

## 把故障定位到正确阶段

**编译失败**：编译器报告源码或类型问题，目标程序还没有按预期构建。先从错误码、主消息和源码位置入手，再查看相邻代码。编译器给出的建议值得参考，但仍要对照任务契约；机械套用建议可能改变程序设计。

**测试失败**：程序和测试都已编译，测试运行后观察到不符合预期的结果。先看失败的是哪个测试、预期值与实际值，再确认测试检查的行为是不是本次任务目标。测试本身可能写错，因此不要只改实现让一个含糊断言变绿。

**运行失败**：构建成功，启动或处理输入时发生错误，例如输入文件不存在、程序返回失败状态，或触发 panic。记录运行命令和输入，区分环境问题与程序逻辑问题。panic 表示程序在某个执行路径上无法继续；它不是普通的编译器诊断。

## 一条短反馈循环

从小改动开始：先 `cargo check` 看编译器反馈；涉及构建配置、链接或目标产物时再 `cargo build`；需要观察输出时 `cargo run`；改变行为后运行相应的 `cargo test`。有失败时保存完整诊断，修复最靠近根因的地方，然后重跑能覆盖该行为的检查。

并不是每次都必须机械执行四个命令。选择检查的原则是覆盖这次改动可能影响的阶段。提交前要运行项目约定的完整质量入口，而这个入口可能比本节列出的命令更多。

## 阅读诊断时先找信号

1. 看执行的是哪个命令，它失败在编译、测试还是程序运行。
2. 找第一个有因果意义的错误，而不是只盯着输出最末尾的总结行。
3. 对照文件、行号和当前改动，确认错误是否来自本次修改。
4. 查看错误码和编译器的相关位置标注；把建议当作待评估的修复方案。
5. 修复后重跑原失败命令，并补跑可能受影响的行为检查。

诊断文本是给开发者定位的线索，不是完整根因报告。错误经常发生在问题真正引入之后才暴露，例如一处类型变化影响另一个调用点；沿调用关系向前检查，避免只改报错那一行。

### 正常例：由编译到行为检查

在包含目标 `Cargo.toml` 的项目目录中，先运行 `cargo check`。如果快速编译检查通过，而本次改动增加了可观察行为，再运行相关的 `cargo test`；需要看程序实际输出时用 `cargo run`。通过的结论只覆盖各命令实际执行的目标和已有检查。

### 错误例：相同“失败”来自不同阶段

下面第一段是预期编译失败的片段，第二段是能编译但预期测试失败的测试；它们用于比较诊断阶段，不应作为通过样例提交：

```rust
fn parse_count() -> u32 {
    let count: u32 = "3";
    count
}
```

```rust
#[test]
fn addition_has_expected_result() {
    assert_eq!(2 + 2, 5);
}
```

第一段把字符串赋给 `u32`，应在编译阶段因类型不匹配而失败；修正类型或解析逻辑后才有可执行目标。第二段可编译，测试运行到断言时失败；把期望值改成 `4` 后重跑测试。标签表示教学上的预期结果，不是已在 R1 实测的格式或终端输出；正式课包需分别验证片段是否按预期失败，并提供可复制的完整项目上下文。

运行阶段也可能在构建成功后失败，例如程序显式执行 `panic!("input could not be parsed")`。这类失败要从实际输入和执行路径排查，不能把 panic 当作类型错误来处理。

以上三类诊断各有独立的可运行项目和预期失败版本，见 [M01-L03 阶段样例 ZIP](./public/m01-l03-samples.zip)。按每个项目的 README 分别进入对应目录，运行、诊断并修复后重跑相应命令。

## 本节小结

- `check` 常用于快速编译反馈；`build` 生成构建产物；`run` 构建并执行；`test` 编译并运行测试。
- 编译、测试、运行是不同阶段；“命令退出成功”要结合命令实际检查的内容理解。
- 先定位失败阶段，再根据诊断和任务契约修复，并重跑覆盖该行为的检查。
