# M04-L05：实验——修复文本流水线

下载[实验起始项目 ZIP](./public/m04-l05-starter.zip)，解压到新目录后阅读 `README.md`、文件清单与公开契约测试。起始 `render` 将 owned `String` 移入第一阶段后，又尝试把旧绑定与处理结果一起返回，因此项目先因 E0382 无法编译。

## 实验目标

- 跟踪一段文本从调用点进入多个按值函数，再作为处理结果返回的 owner 路径。
- 修复 API，让调用方拿到原文和按序处理后的文本。
- 通过克隆保留两份数据时，说清楚 clone 创建独立字符串及其成本。
- 使用公开契约测试验证输出内容、变换顺序以及原文保留。

## 行为契约

- `add_badge` 在输入前加上 `[ready] `；`append_period` 在输入后加 `.`。
- `render` 返回 `(original, processed)`：第一项必须与传入文本完全相同，第二项必须先加 badge 再加句点。
- 输入 `build complete` 时，返回值依次为 `build complete` 和 `[ready] build complete.`。
- 函数可按值消费 owned `String` 并返回结果；若同时要返回原文，必须明确保留一份原值。公开测试要求两个返回值均正确。
- 不联网、不读写文件、不使用第三方 crate；不更改公开签名和测试。

## 实验步骤

1. 解压 ZIP，记录压缩包 SHA-256、`starter-manifest.json` 和 `rustc --version`、`cargo --version`。
2. 先执行 `cargo check --offline`，定位 `render` 中发生 move 的调用，以及之后仍使用旧绑定的位置。
3. 修复实现，使调用方同时得到原文与流水线结果；不要通过删除返回原文的契约或硬编码样例文本来绕过错误。
4. 运行 `cargo test --offline`，核对两阶段的顺序及两份返回内容。
5. 验证一种错误方案：返回原文和处理结果，但直接把 `source` 移入 `add_badge`。该方案应无法编译；另一种错误方案是只返回原文或跳过某个阶段，公开测试应失败。
6. 执行 `cargo fmt -- --check`、`cargo check --offline`、`cargo test --offline`。
7. 将发行 ZIP 再解压到另一个空目录，按 manifest 逐文件核验 SHA-256，重跑验证命令并保存结果。

## 起始快照中的预期故障

起始 `render` 调用 `add_badge(source)` 后仍试图将 `source` 放入返回值；参数按值消费了 `String`，因此编译器应报告 E0382。只改为 `source.clone()` 会使两份值都可用，但要确认结果确实按顺序经过两个阶段并且原文未改变。clone 对 `String` 可能分配并复制内容；若函数签名或业务契约不同，也可用显式返回/重建设计表达数据流，但本实验不可改公开签名。

## 提示

1. 在 `render` 调用每个按值函数前，写出当前 owner。
2. 检查调用方需要几个字符串结果；一份 owned 值不能同时转移到两个返回槽。
3. 只在契约确实需要原文和结果两份数据时，显式创建第二份 `String`。
4. 顺序组合两个阶段的返回值；最终同时返回原文 owner 与转换后 owner。

## 重置与验收边界

保存发行起始 ZIP 和 manifest，不要用修复后的文件覆盖它。重新开始时解压到另一个新目录，对照 ZIP 哈希和逐文件清单，再从错误快照复现失败及修复。作者侧重解压和哈希复核只证明本地快照可重复验证，不等同 R1 隔离、防篡改或平台重置服务。
