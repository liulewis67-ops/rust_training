## 项目契约

每条非空输入行格式如下：

~~~text
timestamp_ms|LEVEL|message
~~~

- timestamp_ms 是 Unix epoch 毫秒的无符号整数。
- LEVEL 精确匹配 ERROR、WARN、INFO 或 DEBUG。
- message 是第二个竖线之后的原文，可为空、可包含更多竖线，也可包含 Unicode。
- 完全空行跳过；仅含空格的行不是空行，应按格式错误报告。
- 第一条坏行使整次运行失败。错误包含 1-based 行号和错误类别；失败时 stdout 不包含部分汇总。
- --level 可重复出现；未提供时包含全部级别。--from-ms 为含边界的下限，--until-ms 为不含边界的上限。--contains 对 message 做区分大小写的子串匹配。多个条件按 AND 组合。
- 输入路径通过 --input 指定。未指定或路径为 - 时读取 stdin；否则从文件读取。
- 默认 text 输出为固定字段顺序；--format json 输出固定 JSON 字段顺序。正常报告只写 stdout，错误只写 stderr。
- --help 以退出码 0 写 usage 到 stdout。参数错误退出码 2；文件、读取或日志解析失败退出码 1。

可自行制作 `fixtures/public.log`、`expected.txt`、`expected.json` 作为小规模公开输入与预期输出；这些名称是计划中的项目文件，仓库尚未正式提供。不能用小样本测试替代后续独立的容量和资源验收。

## 四个 P1 阶段卡

### P1.1 解析核心

维护 log-core library 和公开解析错误类型。检查 Unicode、空行、分隔符出现在 message 内、缺字段、时间戳溢出、未知级别与坏行行号。解析测试不应依赖 CLI；CLI 也不应重复实现解析。

### P1.2 命令行交互

实现 --help、--input、可重复 --level、两个时间边界、--contains 和 --format。分别验证有效/无效参数、文件和 stdin。验证成功输出只到 stdout；错误只到 stderr；参数错误和输入错误返回不同的契约退出码。

### P1.3 稳定处理

使用 BufRead 逐行处理，只保留过滤器和固定大小的聚合计数，不把所有记录或整份输入复制到内存。正确性 suite 覆盖过滤组合、空输入和边界；实际资源验收还需要固定工具链、数据规模、目标平台和内存预算。当前缺少经审核的基准数据与隔离环境，因此只能记录本地测量，资源指标标为“待验收”，不能以小样本速度当作最终结论。

### P1.4 可复现交付

完成 README、公开样本、预期输出、Cargo.lock、格式/测试/Clippy/API 文档命令与示例。从干净的工作区副本执行 locked/offline 命令，不手改 lockfile。审查错误实现并保留契约失败证据；若未来发布正式 ZIP 再补档案哈希。

## 分阶段验收

| 阶段 | 交付物 | 必须验证的行为 |
| --- | --- | --- |
| P1.1 解析核心 | `log-core` library、结构化错误与单元测试 | Unicode、首两个分隔符、错误行号、空行与时间戳越界 |
| P1.2 CLI 交互 | `log-cli` binary 和进程集成测试 | 文件/stdin、参数失败、stdout/stderr 与退出码 |
| P1.3 稳定处理 | BufRead 流式过滤与固定大小统计 | 多重过滤、边界值、空输入和大输入下的资源增长趋势 |
| P1.4 交付 | README、Cargo.lock、可复现命令与例子 | 从全新目录构建、测试、Clippy 和文档生成 |

**先预测，再实现：** `10|ERROR|磁盘|已满` 是四个字段还是包含额外分隔符的三字段日志？当解析到第 500 行才遇到错误时，stdout 是否应该已经输出前 499 行的汇总？用完整契约确定答案。

**与 Java/Go 对比：** 类似 Java 的模块化 CLI/服务层划分与 Go 的 `cmd/` + `internal/` 结构，Rust workspace 将 library 与 binary 分离。关键不是目录数量，而是让解析核心独立测试，使 CLI 只在边界处理文件、标准流和错误呈现。

1. 在本地自行创建包含 `log-core` 和 `log-cli` 的 Cargo workspace，先建立干净的 Git 基线，明确没有第三方依赖和已发布 ZIP。
2. 完成解析器及单元测试，确认错误包含 1-based 行号；不允许因为数据错误而返回空成功报告。

## 参考命令

~~~text
cargo fmt --all -- --check
cargo check --workspace --locked --offline
cargo test --workspace --locked --offline
cargo clippy --workspace --all-targets --locked --offline -- -D warnings
cargo doc --workspace --no-deps --locked --offline
cargo run -p log-cli --locked --offline -- --input fixtures/public.log --format json
~~~

以上命令以练习者创建了相应 workspace 与 fixtures 为前提；它们不是仓库当前已发布的可执行起始工程。输入错误时 stdout 应为空，诊断只出现在 stderr。

## 分层提示

1. **解析器**：按两个分隔符拆成三个字段；message 中余下的分隔符属于消息本身。
2. **CLI**：将参数解析、文件打开、日志业务与结果渲染分开；不要为了测试二进制而把全部逻辑塞入 main。
3. **错误边界**：库返回可匹配错误；CLI 为人写 stderr 和状态码；stdout 保持可管道消费。
4. **流式处理**：聚合状态大小应随级别种类增长，而不是随日志条数增长；输入读取、过滤、聚合须在单条记录生命周期内完成。
5. **测量**：先固定工作负载和内存预算再运行，记录工具链、隔离版本和负载哈希；没有可信的基准数据只能报告功能预检。
6. **重置**：从未修改的 Git commit 或干净工作副本重置，不在修复目录里覆盖唯一基线。
