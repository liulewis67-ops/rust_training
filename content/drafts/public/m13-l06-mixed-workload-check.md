# M13-L06 独立检查：给混合工作负载选择执行方式

请独立阅读本题，不要打开 M13 的私有评测与教师参考。可查阅 Rust/Tokio 官方文档。本检查观察你能否同时保证结果正确、资源有上限并说明取舍；只答 API 名称或只给出能运行的伪代码都不够。

## 场景

一批请求包含 12 个有稳定 `sequence_id` 的工作项：

| 工作项 | 数量 | 工作性质 | 结果契约 |
|---|---:|---|---|
| 远端 metadata fetch | 3 | Tokio 异步 HTTP I/O，等待时间不定 | 每项返回 metadata，404 是该项的正常 `NotFound` 结果 |
| legacy decoder | 4 | 同步库，单项最多 80 ms，调用会阻塞线程 | 成功返回解码记录；非法输入返回该项的 decode error |
| rank score | 5 | 纯 CPU 计算，单项最多 400 ms，不做 I/O | 每项返回确定的整数分数 |

服务运行在 2-vCPU 配额下，runtime 控制面只有 1 个 async worker。资源预算：最多 3 个远端请求同时在途；decoder 与 score 合计最多 2 个 CPU/阻塞工作同时运行；待分派队列最多 8 项。单项错误不得丢掉其他已接受项的结果。每个被接受的 `sequence_id` 最终应有且只有一个带原序号的成功或错误结果。

## 交付回答

提交一页以内的执行设计，包含：

1. 三类工作各自的执行方式，以及为什么选择这种边界。
2. 并发/队列预算表：远端 I/O、共享 CPU/阻塞工作、等待队列、最大已接纳总数；说明多余到达如何获得背压或拒绝结果。
3. decoder 与 score 如何共同遵守 2 项预算；permit 在何时取得、由谁持有到何时释放。
4. 结果如何对应输入序号并保留单项错误；遇到 404、decode error 和 worker panic 时分别返回什么。
5. 一段简短伪代码或状态转移，展示限额覆盖任务提交入口，且不会一次无界 spawn 全部工作。
6. 两个失效方案及其后果：直接在 async worker 调同步 decoder/CPU 循环；把 Semaphore 放到 blocking closure 内或只设置 Tokio blocking pool 的线程数。

## 约束

- 当前入口只有一个 async worker；不得用增加 runtime worker 数掩盖同步阻塞。
- decoder 与 score 共用两项计算预算。为它们各自建容量为 2 的独立限流器会超配，除非另有一个共同的全局限额。
- admission 必须同时尊重 3 个 I/O 在途、2 个计算在途和 8 个排队项；超额工作需明确 backpressure/reject 行为，不能悄悄排入无界队列。
- 返回结果要有稳定序号；某项错误不能伪装为成功默认值，也不能让其余已接受项静默消失。
- 超时、丢弃 JoinHandle 或调用 `abort` 不保证停止已经开始的同步 blocking closure；描述需要停止时，说明底层工作如何合作退出。
