# M24-L01：从业务需求制定验收

## 学完后

- 将业务意图拆成用户、触发条件、可观察结果和失败边界。
- 用具体样例写出可验证的验收条件，不把实现细节误当业务合同。
- 为每个需求建立从需求 ID 到场景、实现位置、测试和运行观测的追踪关系。
- 在编码前暴露含糊词、权限/隐私假设、边界值与未决决策。

## 从“想要功能”到可观察结果

业务请求通常只描述方向。例如“管理员可以很快导出项目任务报告”没有说明谁是管理员、报告按哪个项目和时间范围筛选、数据何时冻结、“很快”如何度量、无权限或数据为空时显示什么，也没说导出的字段能否包含个人信息。不要先把它翻译成按钮、SQL 或某个 Rust handler；先确认使用者希望完成的工作，以及他们能看到的结果。

每个可验收需求至少关联稳定 ID、用户/角色、场景、可观察 outcome 和 evidence。写 Given/When/Then 时，Given 建立已知上下文，When 描述一次用户/系统事件，Then 断言可从产品边界观察到的结果。随后列成功、拒绝、空值/边界、依赖错误和重试行为。Cucumber 文档也建议把场景写成上下文、事件和可观察结果，并避免把实现细节塞进业务步骤。[Gherkin 参考](https://cucumber.io/docs/gherkin/reference/)

示例（不代表完整报告需求）：

```gherkin
Feature: 项目负责人查看任务完成情况

  Scenario: 负责人导出其有权访问的项目报告
    Given 我是项目 P 的负责人
    And 报告范围为 2026-01-01 至 2026-01-31
    When 我请求导出完成情况
    Then 报告只包含 P 中范围内的任务
    And 每个任务包含状态与完成时间
```

该场景仍要决策：时间区间端点是否包含、时区是什么、未完成任务如何呈现、取消/超时如何报告、任务归属在导出期间变化时取哪个快照、CSV 是否暴露用户邮箱。未决定的业务语义应登记为 open question，不能默默选择实现方便的一边。

## 让验收与实现可追踪

用一行一个 acceptance criterion 的矩阵连接：`requirement_id → scenario_id → API/UI boundary → test_id → production signal/owner`。测试证明特定合同；日志/指标帮助上线后观察；它们互相补充，不能用“测试通过”替代业务结果定义。非功能条件也要给范围和量化目标，例如“p95 小于 X，测量窗口/负载/数据规模/目标环境为 Y”；没有负载和环境的“快”不可验收。

验收写业务 outcome，设计文档再决定 API/schema/transaction。对同一业务要求可能有多个实现；如果验收句子点名某个内部类或数据库列，应检查它是否真的由用户需求要求。反过来，接口、安全、兼容、保留期、权限隔离等技术边界如果影响业务风险，也要作为显式 criterion，而不能只写在实现者脑中。

## 练习 crate

starter 的 `validate_criterion` 漏掉了 `Then` 结果检查；`build_trace_rows` 尚未实现需求到场景/test evidence 的映射。Rust 合同只校验结构和 traceability，不替业务人员决定导出字段、时区、权限或“快”的目标值。

## 分层提示

1. “导出要快”缺哪些负载、窗口、数据规模和目标环境？怎样把它变成能否通过的条件？
2. Given/When/Then 中，哪部分是可观察结果？写“调用 `ReportRepository::fetch`”是否属于业务结果？
3. 一个 criterion 有空 `Then` 或没有 `test_id`，会出现什么验收风险？
4. 一个用户切换所属项目的权限时，正在进行的导出该使用请求开始时还是每页读取时的权限？谁需要决定？
5. 除 happy path 外，列出一个权限失败、空范围、依赖超时和重复请求场景。
6. 需求 ID、test ID 与生产指标分别证明什么？哪一项缺失会让上线后的行为无法定位？
