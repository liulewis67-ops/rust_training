# M21-L04：最小复现、诊断假设与回归测试

## 学完后

- 从偶发或复杂症状缩减出能稳定失败的最小输入与执行路径。
- 写出可反驳的根因假设、预测和验证方式，并区分确认与反证。
- 在修复前保留能复现故障的回归测试，再验证成功、失败和边界路径。

## 先修

完成 M21-L03，理解 observed signals 支持假设但不等于根因。回归测试应表达外部可观察的行为合同，不应只锁定某个实现细节。

## 从症状缩减到最小复现

先固定失败发生的输入、版本、时间窗口和可观察输出。逐步移除不相关请求、日志字段、运行时依赖和数据，直到留下仍稳定失败的最小例子。保留复现步骤、输入快照哈希、依赖版本和预期/实际值；如果删减后故障消失，恢复最后删掉的条件并记录其因果关系。使用合成数据时不要把生产秘密复制到测试 fixture。

最小复现要从**可信原始合同**抽取失败条件，不能只把当前错误结果硬编码成期望。先加一个对当前版本会失败的测试，证明测试确实抓住了问题；再提出假设并预测最小变更会改变哪一个观测；最后修复并运行相关全套回归。如果在修复前测试就通过，或一个大范围重写同时改变多个变量，就无法说明假设是否成立。

## 假设—预测—测试—更新

| 步骤 | 记录内容 |
|---|---|
| 观察 | 原始输入与版本；哪些输出实际偏离合同 |
| 假设 | 一个具体组件或边界如何导致偏差；哪些替代解释仍可能成立 |
| 预测 | 若假设成立，单独改变/隔离什么量后，哪些结果应保持/改变 |
| 实验 | 最小复现、测试替身或隔离环境中的一次可重复操作 |
| 更新 | 结果支持还是反驳假设；新证据和下一步是什么 |

诊断报告要把“queue 变深”“pool acquire p95 升高”与“查询持有连接的原因”分开写。单一时间相关性不证明因果；需要控制输入或通过组件边界直接观察。

## 回归测试的边界

回归应覆盖曾失败的精确边界，以及最小相邻/反向场景。例如阈值规则使用 `>= 250ms`，就测试 `249ms`、`250ms`、`251ms`，避免只测明显远超阈值的输入。集成测试验证 API 对外行为；纯规则用单元测试；数据库事务或 executor 调度的结论必须由对应真实环境验证，不能用一个纯单元测试冒充。

使用固定、有限的 fixture，并给每个断言写清楚为何对应合同。只断言一次返回了 `SlowQuery` 可能让其他同时满足的 `PoolPressure` / `QueueBacklog` 被短路；可观察合同要覆盖所有信号。诊断输出是证据和假设，不应该变成未经验证的“根因标签”。

## 本节最小实验

Starter 中故意把 `query_p95_ms == 250` 当作未超阈值：实现与题面合同只差一个边界。公开测试包含 249、250、251ms 邻接输入以及池/队列finding回归。先只运行精确失败测试并保存输出；再解释假设，修复判定后运行整套检查。这个 fixture 展示最小复现和边界回归，不表示已发现真实 PostgreSQL 缺陷。

## 分层提示

1. 哪种最小数据仍能重现边界故障？哪些字段可以安全删掉？
2. 失败测试如何证明它测试的是用户合同，而不是内部实现名称？
3. `249/250/251` 三个样本各证明了什么？
4. 修复前先新增回归测试有什么意义？
5. 什么结果会反驳“`>` 导致边界漏报”的假设？
6. 一次改阈值并换掉数据结构后所有测试通过，为什么因果证据仍弱？
7. 什么时候需要 R3/PostgreSQL 集成测试，而纯 fixture 不足以支撑结论？

## 来源

- [Rust Book：How to Write Tests](https://doc.rust-lang.org/book/ch11-01-writing-tests.html)：测试的 arrange/act/assert 基本结构及测试运行结果语义。
- [Google SRE：Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/)：提出并反复检验假设、缩减和复现问题的排查方法。

真实线上故障响应、实验变更审批、数据库访问控制与 R3 环境运行仍属平台/团队流程；本 fixture 只演示纯规则回归，不会访问生产或本地数据库。
