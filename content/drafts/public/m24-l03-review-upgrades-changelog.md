# M24-L03：Code Review、版本升级与变更记录

## 学完后

- 把 code review 聚焦在行为、风险和可行动证据，而不是个人偏好。
- 将可复现的缺陷转成最小回归测试，确认修复前失败、修复后通过。
- 固定依赖升级范围，按兼容矩阵验证消费者，并写出准确的变更与迁移说明。

## 评审从合同和差异开始

开始前确认 PR 的目标、相关需求/设计/API 文档、测试证据和变更边界。读 diff 时优先追踪数据流、授权边界、错误/取消/重试、并发状态、资源释放和兼容性。对每条发现描述具体位置、当前可观察行为、预期合同、复现方式、影响和建议动作。严重程度取决于利用/触发条件、影响范围和可逆性；请区分阻断问题、应修复的问题、建议与提问。一个可行动评论让作者知道该改什么以及如何证明修复，不把“我会这样写”当缺陷。

若现象可能影响安全或数据正确性，先找出可证明行为的最小输入与边界，再确认是否已有测试覆盖。先写失败回归用例，检查失败是否来自目标行为，而非构建环境；修复后重复相同用例，并跑相关的 broader suite。拒绝含糊的“多加测试”：指出哪个输入、结果或不变量目前没有保护。Review 不能代替作者运行验证，也不能把未经运行的测试说成通过。

## 示例：把评审意见连到发布说明

```text
[阻断 / src/api/tasks.rs:42]
当前：project_id 来自请求路径，但查询只按 task_id 过滤；用户 A 可以请求项目 B 的任务。
合同：只能读取当前主体有权访问的项目；无权限响应不泄露资源是否存在。
复现：以仅属于 A 的用户请求 B 的 task_id，并检查响应与审计事件。
建议：在读取数据前执行资源归属授权；回归测试同时覆盖 A->B 拒绝和 A->A 成功。
影响：跨项目数据暴露；合并前需运行授权合同。
证据：SEC-42（当前失败测试）、AUTH-17（权限需求）。
```

如果该修复要求升级授权 crate，发布记录应说明变化如何影响 `rust-version`、feature/API 和支持平台；兼容矩阵只保留适用组合并附证据。面向用户的 changelog 可写：“修复项目任务读取前的资源归属检查；无权请求按现有隐藏资源合同拒绝；无需数据迁移。”如果服务原来会泄漏不同状态码，必须如实披露行为变化并确认客户端依赖，而不是用“内部安全重构”掩盖外部结果。

## 依赖升级先界定兼容合同

升级前固定当前版本、目标版本、锁文件变化和变更来源。阅读 release notes 与安全公告，标注源码 API、MSRV、features、序列化、错误类型、性能和平台支持影响。为升级画消费者/生产者兼容矩阵：旧客户端对新服务、新客户端对旧服务，以及旧数据读写/迁移/恢复。不是所有项目都需要每个组合，但跳过项要说明为什么不适用。Cargo 的版本需求和 resolver 会影响可选依赖范围；SemVer 兼容承诺也不替代对本服务行为的验证。[Cargo：Specifying Dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html) [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)。锁文件更新可复现依赖解析，不证明运行行为兼容或升级安全。

按风险由小到大验证：格式/静态检查、单元合同、集成与兼容测试、release build、目标环境 smoke test、必要的性能/恢复测试。破坏性变更需写出迁移阶段、弃用窗口和回滚限制；失败就固定回退点或暂停升级，不要仅因 CI 绿灯扩大部署。安全修复的版本选择还需结合受影响范围、可用修复版本和消费者约束。

## 变更记录准确表达用户影响

发布说明记录对调用者或操作者有影响的新增、修复、行为变化、弃用、安全修复和已知限制，并给出升级动作。明确版本范围、字段默认、错误或权限行为是否变化，以及何时删除兼容路径。不要把实现细节逐行复制为 changelog，也不要将“内部重构”描述成无影响，除非兼容测试覆盖了相关合同。把 release note 链回代码变更、需求、API schema、迁移/运行手册和兼容验证证据。

## 分层提示

1. 一条 review 发现缺少位置、实际/预期行为、复现或影响，作者能采取行动吗？缺什么？
2. 一个潜在跨租户读取没有公开入口复现时，如何构造最小回归合同并保护租户隔离？
3. 更新序列化 crate 后，只跑单元测试能证明旧数据仍可读吗？还需覆盖哪个生产者/消费者组合？
4. 依赖锁文件改变而业务 API 未变时，changelog 是否应记录？如何表达安全或运行时变化？
5. 当目标版本新增 MSRV 或默认 feature 改变时，哪些消费者/平台需要列入兼容矩阵？
6. 上线说明如何让值班人员知道停止条件、回滚点及不可逆的数据变化？

## 来源与边界

Code review 示例、风险矩阵和兼容清单为原创教学素材。真实项目的兼容承诺取决于其 API、数据与支持策略，本课不会为具体 crate 版本背书。依赖升级时应使用该依赖的正式 changelog/release notes 与安全公告。

- [Cargo Book：Specifying Dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html)：Cargo 版本需求语法和解析范围。
- [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)：公开 API 的版本兼容约定。
