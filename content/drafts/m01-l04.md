# M01-L04：Git、格式化、Clippy 与最小测试

## 先修与环境基准

先修 M01-L03，并能在已有 Cargo 项目中运行格式检查、测试和 Git 状态查询。

## 学习目标

读完本节后，你可以用 Git 保存一个范围清晰的修改，使用 rustfmt 统一代码格式，运行 Clippy 获取额外 lint 提示，并用小测试保护一个可观察行为。

## 让改动可以被看懂和复查

Git 保存的是一连串可比较的项目状态。开始修改前确认仓库和当前分支；修改后查看差异，确认只有预期文件变化，再创建有说明的提交。提交信息写出这次改动的目的，便于队友回看、比较和定位回归。

如果工作区混有无关改动，不要把它们一并提交。先看 `git status` 和 diff，分清哪些文件属于当前任务。小而聚焦的提交更容易审查，也更容易在问题出现时缩小排查范围。Git 能保存变更历史，但不会自动证明变更正确。

## 格式化与代码检查回答不同问题

`rustfmt` 根据格式规则重排源码，让团队减少格式争论。格式化后仍应查看 diff，因为自动改写可能很大，也可能混入与行为改动无关的内容。格式检查通过只说明代码符合约定格式，不说明代码逻辑正确。

Clippy 是 Rust 工具链提供的 lint 工具，可提示常见错误、可疑写法和改进机会。它的诊断需要结合代码意图判断：有些建议适合当前场景，有些规则可能不适合项目。不要为消除警告而盲目改写；必要的例外应有清楚范围和理由。

格式化、编译、lint 和测试是互补检查：格式化整理外观，编译器检查类型与语言规则，Clippy 补充 lint，测试观察选定行为。任一项都不能代替其余几项。

## 写一个小而有用的测试

测试从可观察行为出发。先给一个输入和预期结果，再调用实际函数并比较结果。优先覆盖一个正常情形和一个重要边界，例如空输入、最小值或无效输入。测试应在实现出错时失败；空断言或只检查“没有崩溃”的测试无法保护具体约定。

测试名字描述场景和预期结果。失败时，名称、输入和断言一起帮助定位问题。测试变多之后，可以按业务行为组织，而不是让一个测试塞进许多无关断言。稍后会学习单元、集成和文档测试的区别；本节重点是从行为写出最小回归保护。

## 一次可复查的修改

1. 先确认当前仓库状态和任务范围。
2. 做一个小改动，针对行为写最小测试。
3. 运行格式化、构建和相关测试；按团队配置运行 Clippy。
4. 查看差异，确认无意外文件和生成物。
5. 用一句话说明修改目的并提交。

如果检查失败，先保留失败信息并找原因，不要靠删除测试、屏蔽 lint 或重置所有文件来获得绿色结果。若需要调整既有检查规则，记录调整范围和原因。

### 正常例：小测试检查可观察结果

下面的 `src/lib.rs` 片段定义 `normalize_name` 函数，并用单元测试把输入和输出写成可检查的行为契约：

```rust
/// Returns the name using lowercase characters.
pub fn normalize_name(name: &str) -> String {
    name.to_lowercase()
}

#[cfg(test)]
mod tests {
    use super::normalize_name;

    #[test]
    fn lowercases_a_mixed_case_name() {
        assert_eq!(normalize_name("Rustacean"), "rustacean");
    }
}
```

运行 `cargo test` 时应确认测试被发现且断言通过。代码可作为 `src/lib.rs` 内容；它展示函数实现和单元测试，但仍需建立 Cargo 项目清单。可下载[完整单元测试项目 ZIP](./public/m01-l04-sample.zip)查看 Cargo 清单与测试组织。

### 错误例：测试通过但没有检查行为

```rust
#[test]
fn lowercases_a_mixed_case_name() {
    assert!(true);
}
```

这个测试不调用目标函数，即使规范化实现被删除或写错也可能通过。应改为调用实际函数并断言输出；再临时改错预期值，确认测试会失败，然后恢复契约并重跑。不要把负向验证时的失败当作最终验收结果。

格式检查也有明确边界：`cargo fmt -- --check` 发现格式差异时会报告未满足格式要求；执行 `cargo fmt` 后要查看 `git diff`，确认格式化没有掩盖或混入行为变更。Clippy 的 lint 可能以警告形式报告，具体是否导致命令失败取决于项目设置；评审时要查看诊断内容，不能只看退出码。

## 本节小结

- Git 提供可审查的变更历史；提交边界应与任务一致。
- rustfmt、Clippy、编译器和测试检查不同的问题。
- 一个最小测试也要对行为做出断言，并能在目标实现错误时失败。
- 检查通过后仍要看 Git 差异，确认保存的是预期改动。
