# M01-L01：Rust 解决的问题与路线选择

## 先修

本节面向已经接触过至少一种编程语言的学习者；需要能读懂变量、函数和简单条件，并能描述程序的输入与输出。不满足这些条件时，先完成编程基础预备路线，再回来比较语言和学习入口。

## 学习目标

读完本节后，你可以：

- 针对两种不同的产品需求，说明 Rust 是否值得列入候选，以及理由。
- 在做决定前指出还缺少哪些团队、部署和维护信息。
- 为有编程经验的学习者选择主线入口；为编程初学者选择先修路线。

## 从需求开始，而不是从语言口号开始

选择语言是在约束下做工程取舍。先描述要交付的东西、它运行在哪里、出了问题会有什么影响，再看语言和团队能否满足这些条件。单独说“要快”“要安全”或“大家都在用”都不足以得出选择。

Rust 的设计目标之一，是让开发者在控制运行时与系统细节的同时，获得更高层的表达能力。它通过编译期检查帮助发现一类内存与并发错误；这不等于所有程序都没有缺陷，也不能替代测试、权限设计、监控或安全评审。工具链和类型系统会增加学习成本，因此需要把团队熟悉度、招聘与维护能力也放进决策。

## 需求一：需要长期维护的资源受限解析工具

假设团队要交付一个命令行工具：它要处理较大的日志文件，运行在内存有限的设备上；输入格式会逐步扩展，工具也要由多人长期维护。团队已经有 Rust 经验，部署目标和所需依赖都能在开发早期验证。

Rust 值得进入候选名单。理由不是“Rust 一定更快”，而是需求重视对内存和运行时行为的控制、长期修改时尽早发现部分错误，而且团队能承担工具链和学习成本。还要做原型和基准测试，确认解析速度、峰值内存、构建时间、依赖支持与交付流程符合目标。若基准不满足，或关键依赖不可用，就应重新比较其他方案。

这里没有足够信息直接宣布 Rust 胜出：实际输入分布、目标平台、发布频率、运维经验和性能门槛都会改变结论。先把这些问题写成可验证的假设，再用小型纵向样例检查构建、解析、部署和维护流程。

## 需求二：两周内上线的内部报名页面

另一个团队要在两周内交付内部活动报名页面。公司已有成熟的 TypeScript 前端模板和托管服务，页面请求量很低；当前风险主要是活动日期前能否完成并由现有团队接手，而不是 CPU、内存或系统接口控制。

此时没有明显理由为了项目本身改用 Rust。复用团队已维护的技术栈，可能更直接地满足交付时限和维护约束。以后若出现明确的资源控制、可靠性或部署边界问题，再用数据说明是否需要更换组件或语言。采用 Rust 也不是错，但需要指出它解决了哪个实际问题，以及团队会为此付出哪些成本。

## 做一张简短的决策记录

开始试做前，写下以下信息：

1. **交付目标**：用户最终要完成什么操作？
2. **关键约束**：延迟、吞吐、内存、平台、上线时间或合规要求中，哪些有量化门槛？
3. **失败代价**：哪些错误会导致数据损坏、服务中断或安全问题？现有流程如何发现和恢复？
4. **团队条件**：团队是否了解 Rust？谁负责依赖升级、构建和线上排障？
5. **验证办法**：用什么小原型、测试或基准来推翻当前假设？

将每个候选方案的收益、成本和待验证问题并列。没有测量时，把“可能更快”记为待验证假设，而不是结论。

## 选择学习入口

如果你已经会用其他语言编写程序，可以从本课程的工具链和反馈循环开始，再逐步学习值、函数、类型、所有权与借用。遇到编译错误时，先读错误位置、错误类别和相关代码；编译器诊断是学习过程的一部分。

如果你还不熟悉变量、函数、终端、文件和基本程序流程，先走独立的编程基础预备路线。Rust Book 的读者说明也以有其他语言编程经验为前提；从预备知识开始可以少一些同时发生的新概念。

完成本节后，用你自己的一个项目需求写两三句话：Rust 解决什么约束、引入什么成本、你会怎样验证。若还答不上来，下一步不是猜语言，而是补齐需求和团队信息。
