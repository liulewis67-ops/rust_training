# 前端开发规范

版本：v1.0｜日期：2026-10-11｜适用范围：平台前端、前端测试及开发脚本

关联：[技术方案](./technical-design.md) · [后端开发规范](./backend-development-standards.md) · [实施路线图](./implementation-plan.md)

## 1. 执行原则与现有基线

本文作为后续开发和代码评审的执行标准。“必须／禁止”为验收要求，“建议”为默认选择，可在任务记录中说明调整原因。新增与修改的函数必须同步满足注释要求；既有代码随所在模块开发逐步补齐，不用无关的全量改写扩大当前任务。

当前项目使用 React 18、TypeScript 5、Vite 6，包管理器按 `package.json` 的 `packageManager` 固定为 pnpm。I01-R01 已将原型拆为 app/pages/features/components/lib；学习状态在 `src/features/learning/`，存储适配在 `src/lib/browserStorage.ts`。已接入原型 History 路由、lint、格式化及回归测试；新主线导航和 API 客户端尚未交付。下方目标目录按实际功能逐步建立。

开发前阅读对应小阶段、技术方案与两端规范。范围、验收或接口发生变化时同步更新文档；不能以规范文档已完成替代功能验收。依赖升级单独验证，不能在业务开发中顺手升级框架。

## 2. 目录与依赖边界

保留根目录前端工程，按功能逐步拆分，建议目标结构如下；目录在有实际代码时创建：

```text
src/
  app/                  # 应用启动、路由组合、全局 Provider
  pages/                # 页面级组合与路由参数适配
  features/             # catalog、learning、workspace、execution 等业务功能
    workspace/
      components/       # 业务组件
      hooks/            # 工作区行为与生命周期
      api.ts            # 调用统一客户端的工作区接口
      types.ts          # 前端业务模型
  components/           # 与业务无关的通用 UI
  lib/                  # 请求、存储、时间等基础能力
  api/generated/        # 后续由 OpenAPI 生成的类型或客户端
  types/                # 确实跨功能共用的类型
  data/                 # 现有课程数据；按课程方案逐步迁移
  styles/               # 后续拆分的设计变量和基础样式
```

- 依赖方向为 `app/pages → features → components/lib`；通用层不得反向依赖页面或业务模块。
- 页面组织视图，业务 Hook 管理行为，API 层处理通信，存储适配层处理持久化。组件中禁止混入完整请求协议、迁移算法和成绩计算规则。
- 跨功能调用通过明确导出入口，禁止深层引用另一功能的内部文件；不为一处使用建立通用框架。
- 测试靠近被测模块，跨页面端到端测试集中管理。不得手动修改生成代码、`dist/` 或依赖目录。

## 3. 命名、类型与代码风格

| 对象 | 约定 | 示例 |
|---|---|---|
| 组件及组件文件 | PascalCase，文件后缀 `.tsx` | `WorkspaceEditor.tsx` |
| Hook | `use` 前缀，camelCase | `useRunEvents.ts` |
| 普通函数、变量、普通 TS 文件 | camelCase | `loadDraft`、`apiClient.ts` |
| 类型、接口 | PascalCase，不加无意义 I/T 前缀 | `WorkspaceSnapshot` |
| 真正固定的常量 | UPPER_SNAKE_CASE | `MAX_OUTPUT_BYTES` |
| 布尔值 | 表达判断或能力 | `isSaving`、`canSubmit` |
| CSS 类 | kebab-case，体现组件或状态 | `workspace-editor` |

- 保持 TypeScript `strict` 和现有未使用检查开启；类型导入使用 `import type`。
- 外部 JSON、浏览器存储和消息事件按 `unknown` 接收并验证；类型断言不能代替运行时校验。禁止用 `any`、非空断言或 `@ts-ignore` 掩盖模型问题。
- 公共函数、Hook 和 API 适配函数写明参数与返回类型；局部表达式可使用可靠推断。状态使用联合类型，避免多个布尔值构造不可能组合。
- 对象和数组状态按不可变方式更新；基于旧状态计算时使用函数式更新，避免过期闭包。
- 一个函数承担一个明确职责；复杂分支先拆分命名再补注释。禁止将多步业务流程压缩为一行。
- 格式化工具接入前沿用现有两空格、单引号、无分号风格；接入后以共享配置为准，避免同时混用手工风格和多套格式化规则。

## 4. 注释规范（强制）

### 4.1 每个函数必须有注释

覆盖导出函数、私有辅助函数、React 函数组件、自定义 Hook、事件处理器、类方法、异步函数、测试辅助函数及回调。代码由人或 AI 编写均适用。

- 命名函数、组件和 Hook 使用紧邻声明的 `/** ... */` 注释。简单函数至少一句说明用途；复杂函数补充参数约束、返回语义、失败情形和副作用。
- 参数名与类型已清晰表达的内容不重复解释；时间单位、版本含义、空值语义和可能抛错等信息必须写明，可使用 `@param`、`@returns`、`@throws`。
- 匿名回调也要有说明，可在回调前或函数体首行使用 `//`；JSX 中使用合法的 JSX 注释或抽成具名处理器。多步骤回调应抽成已注释的具名函数。
- `useEffect` 的执行回调与清理回调分别说明同步对象和清理责任。测试可由紧邻的场景注释说明测试回调用途。
- 注释默认使用中文，保留准确的英文标识符。函数签名或行为变更时同步修改注释，禁止空注释和“处理数据”等无有效信息的描述。

### 4.2 复杂实现必须有行内注释

“行内注释”指函数实现内部、紧邻相关语句的说明，可独占上一行，不要求挤在语句末尾。以下逻辑必须说明“为什么这样做”和必须保持的约束：

- 异步请求竞争、过期响应丢弃、重连、去重、取消与重试。
- 草稿迁移、revision 冲突处理、离线同步、缓存失效。
- 日期与时区转换、非直观算法、性能优化及浏览器兼容处理。
- 状态机分支、权限相关展示、对不可信内容的处理。

不逐行翻译显然的语法。临时方案使用 `TODO(任务ID): 原因与移除条件`；禁止保留大段注释掉的旧实现。

### 4.3 示例

以下为独立的注释风格示例，不代表接口已实现：

```ts
interface RunEvent {
  seq: number
  text: string
}

/**
 * 合并同一运行任务的日志事件，返回按事件序号排序的新数组。
 * 前置条件：两组事件已通过校验，且属于同一个 run ID。
 * 不修改输入；同序号事件必须具有相同内容。
 */
export function mergeRunEvents(
  current: readonly RunEvent[],
  incoming: readonly RunEvent[],
): RunEvent[] {
  const bySequence = new Map<number, RunEvent>()

  // SSE 重连可能重放事件；保留首次收到的事件，避免输出重复追加。
  for (const event of [...current, ...incoming]) {
    if (!bySequence.has(event.seq)) bySequence.set(event.seq, event)
  }

  return [...bySequence.values()].sort((left, right) => {
    // 按服务端序号恢复顺序，不依赖网络到达时间。
    return left.seq - right.seq
  })
}
```

## 5. React 组件与状态

- 组件保持渲染纯净，禁止渲染期间写存储、发请求或修改外部状态。业务操作在处理器或专用 Hook 中完成。
- Hook 必须按稳定顺序调用，不放入条件、循环或普通辅助函数。
- Effect 用于同步外部系统，必须提供完整依赖；订阅、定时器、事件监听和连接有对应清理。请求需要取消或忽略过期结果，不能靠关闭依赖检查规避问题。这些行为遵循 [React Effect 文档](https://react.dev/reference/react/useEffect)。
- 可从 props 或已有状态计算的数据直接派生，不使用 Effect 维护重复状态。仅在测量或引用稳定性有需求时加入 memo 优化。
- 局部交互状态留在组件；跨页面业务状态进入所属功能；服务端数据通过统一缓存策略读取。禁止把全部业务状态放入单个全局对象。
- 列表使用稳定业务 ID 作为 key；排序、筛选或增删列表禁止用数组下标充当身份。
- 页面必须覆盖加载、空数据、失败、无权限、正常状态；保存另区分保存中、本地已保存、服务端已同步和冲突。

## 6. API 契约与异步交互

- API 基路径为 `/api/v1`，OpenAPI 为两端契约来源。生成工具接入后从契约生成接口类型，禁止独立手抄另一套 DTO；前端展示模型在适配层转换。
- 请求集中处理超时、取消、HTTP 状态、统一错误、会话失效与 request ID；页面不能分别发明错误解析规则。解析响应前考虑空响应和非 JSON 故障响应。
- JSON 字段统一采用后端规范中的 `snake_case`；映射为前端 camelCase 时在 API 适配层一次完成。ID 用字符串，时间传 UTC RFC 3339 字符串，按用户时区展示。
- 创建运行或提交时生成 `Idempotency-Key`；同一次操作因网络中断重试时复用原键，修改输入的新操作使用新键。不能仅依靠禁用按钮防止重复任务。
- 自动重试只适用于允许重试的读取或有幂等保障的写入，使用有上限的退避；权限错误、字段校验失败和 revision 冲突不能无限重试。
- SSE 按任务和事件序号去重，重连时携带游标；事件过期或出现缺口时重新查询权威状态。断流不等于任务失败，离开页面要释放连接。
- 请求取消后显示“取消中”，收到服务端终态后再显示“已取消”；不得将 HTTP 请求中断当成远端沙箱已停止。
- 测试数据和 mock 必须显式区分开发环境，禁止生产失败时退回假成功、假成绩或静态响应。

## 7. 存储与学习数据

- 成绩和正式评测以服务端记录为准；旧 localStorage 数据导入必须保留自报来源，不能自动升级为平台验证结果。
- 主题等轻量偏好可用 localStorage；目标工作区草稿按技术方案使用 IndexedDB。存储访问必须处理不可用、额度不足、损坏数据和版本迁移失败。
- 存储键包含应用、schema 版本和必要的用户／工作区范围；退出或切换账号时清理内存缓存并隔离私有草稿，不能把上一用户的数据展示给下一用户。
- 保存使用 workspace revision 乐观并发；冲突保留本地与远端副本并提供比较，不自动覆盖。运行绑定已冻结快照，后续编辑不修改已提交任务。
- 学习日按用户时区和日历计算，禁止用固定减去 24 小时判断昨天。

## 8. 样式、可访问性与性能

- 延续现有深浅主题，颜色、间距、字体、圆角逐步集中为设计变量；组件样式避免污染全局。不在无关功能中引入第二套 UI 体系。
- 使用语义化按钮、链接、标题和表单；控件有可读名称，支持键盘和可见焦点。弹窗处理初始焦点、焦点约束、关闭与焦点恢复。
- 状态不能仅用颜色表达；错误信息与字段关联，运行结果变化提供合适的辅助技术提示，避免每行流式日志都打断阅读。
- 在窄屏、桌面、深浅主题下验证阅读和编辑流程；代码区域允许独立横向滚动，页面主体不应意外溢出。
- 编辑器和重型图示按需加载；日志和长列表限制展示量，持续输出不能无限占用内存。性能优化记录实际问题与验证结果。

## 9. 前端安全与配置

- 前端可见配置不存放秘密；会话按后端约定使用安全 Cookie，不把长期访问令牌写入 localStorage。
- 所有变更请求配合后端 CSRF／Origin 校验。前端隐藏按钮只改善交互，权限仍由后端校验。
- 学员输出作为文本或结构化数据展示；禁止直接写入 `innerHTML`。课程和笔记富文本仅经可信清洗流程渲染。
- 实验页面按技术方案使用独立预览域与最小 iframe 权限；禁止将任意学员 HTML 注入主站。
- 错误上报不包含密钥、完整源码、私有答案或原始请求体；可携带脱敏的 request ID 定位问题。

## 10. 验证与提交门槛

当前根目录已定义以下命令；在依赖安装完成后执行，本文不代表本次已经运行：

```powershell
pnpm typecheck
pnpm build
```

I01-F02 中建立并记录统一检查入口；格式化、lint、Hook 规则和测试工具在接入、固定版本并验证后才作为实际检查项。I01-F02 已接入 `lint`、`test`、`format:check` 与统一 `check`，实际验证见对应验收记录。首次建立锁文件后提交锁文件，CI 使用固定依赖安装策略。

行为测试优先覆盖草稿损坏与迁移、重复提交、revision 冲突、断线重连、错误与权限状态、账号切换、时间边界；交互测试按用户操作验证，不依赖内部 state 结构。纯文档和简单样式变更采用相应检查，不机械增加测试。

每次提交前检查：

- [ ] 所有新增或修改函数都有有效注释，复杂实现有紧邻代码的行内说明。
- [ ] 目录职责、类型、接口和存储版本符合约定；未引入假成功或客户端权威成绩。
- [ ] 相关类型检查、构建、已接入测试与关键失败路径验证通过并记录证据。
- [ ] 页面变更完成键盘、窄屏和主题验证；资源订阅可释放，错误可理解和恢复。
- [ ] 同步更新契约、文档与对应任务台账，按实施路线图保持一个小阶段一次提交。

注释完整性暂由评审逐项检查；未来自动化只能辅助发现遗漏，不能替代对注释准确性和复杂逻辑解释的检查。
