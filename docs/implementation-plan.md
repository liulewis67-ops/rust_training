## 3. 状态与标记规则

| 状态 | 含义 | 必须附带的信息 |
|---|---|---|
| TODO | 尚未开始或尚未按本任务核验 | 初始验收项未勾选 |
| DOING | 正在实现或制作 | 负责人、开始日期 |
| VERIFY | 实现已就绪，验证/评审/提交未全部完成 | 待验证项与证据 |
| BLOCKED | 因明确依赖或环境问题无法继续 | 原因、解除条件、相关任务/资源 |
| DONE | 验收通过且对应提交成功 | 全部验收勾选、验证记录、完成日期、可定位提交 |
| REOPENED | 原完成任务因回归或失效需重做 | 原证据、失效原因、新修复任务ID |

未制作内容不可标为DONE；原型存在但未按新标准验收也不可标为DONE。文档中的初始“—”表示尚未发生，不能用计划日期冒充完成日期。

里程碑达到DONE，需其所有必需小阶段DONE、里程碑验收清单全通过，并记录整体验证。可以先逐项完成，最后一项提交同时更新里程碑状态，无须为勾选里程碑专门新增一个空提交。一个DOING小阶段通常使其父里程碑进入DOING；部分阻塞时在里程碑记录范围，不掩盖其余进度。

所有任务均为主线必需项。调整范围须写明原因和替代验收，更新总数；不能简单删除未完成项来得到100%。

## 4. 单次commit的工作边界

每次提交包含同一个小阶段所需的实现、相关内容、必要验证、迁移/配置说明与状态更新。涉及前后端的功能要交付一条可用链路；课程提交要完成一整节，不能只交标题或无验证的代码片段。

允许先通过受控功能开关部署尚未公开的完整能力；默认关闭的功能也必须在验证环境跑通。禁止提交启用中的半成品路由、假成功按钮或硬编码通过状态。

基础设施任务可以面向开发者交付完整工具或可复现环境，例如“隔离命令行执行工具”，无需伪装为学生功能。可行性验证交付可运行验证入口、实测记录和结论，不等于相应生产功能已经完成。

推荐提交标题：

- 功能：`feat(I03-F06): 提交正式能力检查`
- 课程：`content(M05-L03): String、str、切片与 UTF-8`
- 基线：`chore(I01-F01): 建立Git与现有原型基线`
- 后续修复：`fix(I03-F06-A): 修复重复回传导致重复计分`

一个提交只绑定一个小阶段ID；不要把多节课程或无关功能混在一次提交。阶段太大时，在动工前拆成例如I08-F03-A/B，各自必须仍有完整行为、依赖、验收和状态；将原项改为非提交父项，更新计数。课程原则上保持一节一提交；必要的通用组件先拆成独立功能任务，再交付课程。

已经完成并进入共享历史的任务若发现问题，新增修复小阶段，原任务记REOPENED并保留历史，不为了保持“一次commit”而重写共享历史。

## 5. 所有小阶段共用的完成门槛

### F：功能/工程提交

1. 交付范围中的完整行为可操作或工具可执行，正常与关键失败路径符合逐项验收。
2. 权限、数据和资源边界在首次交付相关功能时就有效，不能留到公开发布才补。
3. 与改动相关的检查通过；行为变更以合适的自动测试或明确手工复现验证，纯排版不强加无意义测试。
4. 迁移、回退、配置和日志影响已说明；不包含密钥、构建产物或未授权素材。
5. 保存验证命令/步骤、输入、预期与实测结果、环境版本和日期；运行器验证在隔离环境完成。
6. 当前小阶段的实现与台账更新包含在同一提交，提交后工作区和历史符合预期。

### C：一节概念课程提交

1. 目标、先修、原创正文、正常例、错误例、解释、来源与版本齐全，读者能够完成本节目标。
2. 代码标明完整可运行/片段/预期失败；可运行例和失败例按固定环境校验。
3. 本节三道短练习有题面契约、公开验证、分层提示、参考方案和正确/错误解验证。
4. 路线导航、练习、草稿、提示与进度接入实际可用；独立/辅助/自报证据分开。
5. 通过本节专属验收并保存验证记录，单独提交本节。

### L：一节实验课程提交

继承C中的目标、版本、来源和接入要求，但不额外计入短练习数。须有起始模板、任务、验收、重置/恢复说明、参考实现和已知错误变体；实际从零状态走完一次实验。使用完整项目时链接已交付的项目任务包，本课程只实现教学组织与实验接入，不重复实现整套项目。

### A：一节独立检查提交

具有新情境/变式、明确评分规程、受控评测和失败反馈；答案使用情况影响证据类别，平台错误不影响技能；验证本模块6单元/12短题/1实验/1检查的完整性。自评和本地截图不能伪装为平台权威成绩。

每项验收包括“专属清单＋适用共用门槛”。分册中的共用门槛复选框必须在确实检查过后勾选。

## 7. 依赖、执行顺序和风险前置

各分册给出保守的默认提交顺序，任务“执行前置”含顺序约束，不声称每个相邻任务都是不可拆的技术硬依赖。基础工具、隔离运行和数据边界是真实前置；正文可以提前起草，但正式课程完成状态仍要求运行和接入已可用。

准备改变顺序时，先核对所需环境、API、内容schema、评测器和课包，更新前置记录并检查无环。可以提前完成可独立验证的任务；不得因此提前宣布父里程碑或公开发布完成。

开发顺序与学习先修图分开维护。例：M07的学员先修包含M03/M05/M06，M18需要错误处理与HTTP基础；作者制作顺序不应直接成为网站强制学习顺序。

风险在I01用R1/R2/R3代表负载验证；I03形成R1正式能力；I05形成R2；I08形成R3。隔离、权限和资源限制从首次能力上线即生效，I13负责完整部署验收与回归，不是首次安全实现。

## 8. 证据、提交定位与更新流程

建议每个任务使用 `docs/implementation/evidence/<任务ID>.md` 保存验收记录；这些文件在实际验证时创建，本轮不填造报告。记录包含验证对象、版本、命令/步骤、预期、实测、检查输出引用和未解决问题。必要截图和日志应去除秘密。

开始任务：更新状态DOING、负责人、开始日期，复核前置和任务范围。

验证任务：逐项执行专属验收与共用门槛，记录证据；未通过留在VERIFY或DOING，外部条件阻塞则标BLOCKED并写解除条件。

提交任务：选择性暂存当前任务相关内容，将任务与总览计数更新为拟完成状态后提交；只有提交成功且验证完整，DONE才生效。若提交失败，恢复为VERIFY，不对外报告完成。最后一项可同步完成里程碑验收和汇总。

提交定位使用唯一任务ID，例如 `git log --oneline --grep='I03-F06'`。同一次提交无法在自己的内容里可靠写入自身SHA，因此任务中的“提交定位”预填唯一ID；SHA可在下一次文档更新补录，或一直通过唯一ID查询。不要为补SHA反复amend或额外生成232个纯台账提交。

若通过PR的squash合并保持一项一commit，一个PR只承载一个小阶段；包含多个阶段的PR不得合并成一个丢失边界的大提交。是否创建PR由后续仓库协作方式决定，本方案不自动创建外部任务或PR。
