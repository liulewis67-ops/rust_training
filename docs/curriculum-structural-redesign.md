# Rust 课程结构优化：模块内闭环 + M10 综合实战

## 定位与边界

M01–M09 是独立主题的系统性课程，不应强制使用统一业务案例。**结构上的连续性是能力前置关系，不是业务案例连续性。** 每节允许选最适合解释机制的真实小场景；各模块应有自己的问题主线、概念演进和可检验的学习成果。M10 计划作为单独的跨模块综合实战，把前面知识应用到同一个项目中，但**尚未发布**，不得将其显示为可学习的现有课程。

## M01–M09 的知识与能力递进

| 模块 | 核心问题 | 模块内知识递进 | 独立实践方向 |
| --- | --- | --- | --- |
| M01 开发基础 | 怎样可靠地开发、调试和交付 Rust？ | 语言定位 → 工具链与项目 → 构建/测试诊断 → 质量检查 | 修复并交付可测试程序 |
| M02 语法与计算 | 怎样表达正确且边界清晰的计算？ | 类型/可变性 → 表达式/函数 → 控制流 → 组合数据 | 数据单位转换器 |
| M03 数据建模 | 怎样用类型表达领域状态？ | 结构体/方法 → 枚举/match → Option → 模块与 API | 内存任务清单 |
| M04 所有权 | 值在作用域和函数间如何流转？ | owner/Drop → move → Copy/Clone → 参数和部分移动 | 文本流水线所有权审计 |
| M05 借用与切片 | 怎样在不移交所有权时安全访问？ | 共享/独占借用 → 有效区间 → 切片/UTF-8 → 可变 API | 零复制文本查询 |
| M06 生命周期 | 引用何时有效，接口怎样表达依赖？ | 引用有效性 → 标注/省略 → 引用字段 → 'static 与拥有型方案 | 借用配置视图 |
| M07 泛型与 Trait | 如何抽象能力并保持 API 契约？ | 泛型/bound → trait → 静态/动态分发 → 转换与不变量 | 可替换解析器 |
| M08 集合与迭代 | 怎样组织批量数据处理？ | 集合与访问 → 闭包 → 三种迭代方式 → 组合算子 | 日志聚合统计 |
| M09 错误处理 | 如何表达、传播并呈现失败？ | Result/? → 错误链 → 库/应用边界 → panic 与恢复 | 配置解析与错误位置 |

各模块案例相互独立；例子只要适合当前知识点即可。不要求 M03 的任务模型沿用到 M04，不要求 M08 的日志场景在 M09 继续出现。

## 每个模块的教学闭环

1. **建立核心问题**：说明本模块解决什么、已有前置能力是什么；不强行制造同一产品需求。
2. **形成逻辑层级**：L01–L04 用“基础机制 → 具体规则 → 限制与反例 → 工程运用”组织知识；可以因主题微调，但避免罗列互不解释的 API。
3. **用对比例子建立认知**：先给问题与预测，再解释 Rust 规则；给出正确例、错误例和区别；Java/Go 比较仅在能减少迁移误解时使用。
4. **独立模块实验（L05）**：综合本模块能力，给出输入/输出契约、任务分解、本地验收和关键边界。
5. **迁移检查（L06）**：不同于 L05 的场景，验证是否掌握机制，而非照抄参考答案。
6. **精炼复盘**：总结原理、决策依据、适用边界和下一主题的必要先修，不预设统一业务案例。

## 单节教学模板（按需要调整）

- **引入**：提出一个有辨识度的问题与先验误区。
- **目标与先修**：只写本节真正需要的知识。
- **解释路径**：动机 → 机制 → 示例 → 执行/编译证据 → 常见误解或失效条件。
- **应用决策**：怎样在实际函数、类型或模块中使用；有哪些取舍。
- **检查理解**：预测、修复、解释或小练习，明确本地命令和验收标准。
- **总结**：本节关键结论，以及下一节如何在概念上推进。

**不应**机械复制标题、制造不必要的过渡、强制每节同一故事，也不应仅往现有正文插入一段“与上一节的联系”就当成结构重写。要检查知识顺序、重复内容、解释深度、例子与练习的一致性。

## M10：跨模块综合项目（规划中）

M10 与 M01–M09 的教学任务不同。它才负责把已有知识汇集到一个完整工程中；建议以**本地日志分析 CLI**为候选项目，因为它可以验证工具链、类型与状态、资源所有权、文本借用、接口抽象、集合统计和错误处理。最终项目题目需经过范围评估，不在此阶段锁定。

建议按六节规划（**暂不加入公开课程清单**）：

| 课时 | 教学任务 | 使用的前置能力 |
| --- | --- | --- |
| M10-L01 | 明确需求、CLI 输入输出与验收测试 | M01–M03 |
| M10-L02 | 建立数据模型、解析模块和公共 API | M03、M07 |
| M10-L03 | 处理文本所有权、借用和生命周期 | M04–M06 |
| M10-L04 | 实现统计与可组合的数据处理管线 | M08 |
| M10-L05 | 为输入和 I/O 故障设计错误边界 | M09 |
| M10-L06 | 集成测试、性能测量、质量检查与复盘 | M01–M09 |

M10 应提供真正可运行的 starter、阶段任务和可复现验收；在准备完成前，不标记为已发布。

## 质量要求和执行顺序

第一步：修复已经把 M01–M09 描述成同一工程持续演进的文案。第二步：按模块深入审阅 L01–L06，调整章节顺序、概念解释与练习关联，并同步中英文。第三步：规划和实现 M10 的独立实战课程与工程模板。每个模块的完成标准是“知识形成解释链、示例支撑主线、实验验证能力”，而非单纯 Markdown 更长。必须保留稳定课程 ID、现有可工作的测试与代码资产，并执行仓库现有内容和前端校验。

## English editorial contract

M01–M09 are independent topic modules with logical prerequisite progression, not chapters of a single running business project. Within each module, organize concepts as a coherent question → mechanism → example → evidence → limitations → application → independent transfer. Use different examples where pedagogically appropriate. Reserve cross-module integration for a future, unpublished M10 capstone; do not list it as released before its lessons and starter exist.
